## Core results

Five models (GPT-4o, Claude-4.5-Sonnet, Gemini-2.0-Flash, Llama-3.1-8B, Mistral-Small-24B) judge
"does this code meet this requirement?" on ~1,400 paired correct/buggy instances
(HumanEval-X-Bugs, buggy-MBPP, QuixBugs), no test execution, three prompt modes (Direct /
+Explain / Full-with-fix):

- **Over-correction dominates and prompt richness makes it worse.** GPT-4o FNR (rejecting
  *correct* code) rises Direct→Full from 26.2%→73.2% (HumanEval) and 35.9%→87.9% (MBPP) while FPR
  falls to ~0; Claude-4.5: 26.2→36.0 / 58.5→62.3. In absolute terms: MBPP FN 184→451 while FP
  19→0 — richer prompts eliminate a small tail of unsafe acceptance by generating a flood of
  unnecessary rejections. Prompt design is a *decision-boundary control*, not an accuracy
  booster.
- **False-rejection taxonomy (Fig. 4, n=4,190):** Logic Error **48.2%** (broad unfalsifiable
  claims, "often without a falsifiable counterexample"), Added Requirement **14.1%**
  (hallucinated constraints), Boundary Error **13.2%**, Misread Spec **11.7%** — 87.2% combined.
  Style/performance nitpicks are *rare*: overcorrection is semantic overreach, not pedantry.
- **Rationales are not trustworthy:** verdict-rationale contradictions are non-trivial and
  direction is model-specific (GPT-4o: 93% "verdict NO but rationale reads positive");
  fault-awareness on true rejections: symptom match near-ceiling (93–100%) but root-cause match
  only 44–75% — right verdicts for inaccurate reasons.
- **Mitigation — Fix-guided Verification Filter:** treat the model's proposed fix as an
  executable counterfactual; run original vs. fixed against benchmark + spec-constrained
  generated tests; flip spurious rejections. **FNR falls, averaged across models: 54.8→16.3
  (HumanEval), 69.0→28.9 (MBPP), 51.0→24.0 (QuixBugs)** — per-model cuts of 30–67 points — at
  ≤+2.5 points FPR. Works best where test coverage is decent; K=2 re-judge rounds.

## Relevance to A/B/C

- **C — the central evidence.** Individually-plausible findings, systematically wrong: exactly
  our problem statement, measured. The taxonomy predicts what an anchoring bar would filter, and
  the filter gives the measured effect size for demonstrate-failure-first (catalogue C1/C2).
- **B — supporting.** Unverifiable prose claims sit in the same "no falsifiable counterexample"
  class that makes up half the false rejections.
- **D2 — direct:** every elaboration of the reviewer prompt shifted the boundary toward
  rejection — argues for lean reviewer registers and A/B-testing register additions against
  finding precision.

## Supported interventions

1. **Anchoring bar** (C1): reject-without-falsifiable-evidence is 87% of the false-positive mass.
2. **Demonstrate-failure-first / executable counterfactual** (C2): the filter's 30–67-point FNR
   cut is the largest measured mitigation effect in this whole reading list.
3. **Keep reviewer prompts lean; measure before enriching** (D2).
4. Don't trust rationale root-cause attribution when routing fixes — symptom claims are reliable,
   cause claims are ~half wrong (bear on how fix rounds interpret findings).

## Applicability caveats

Small self-contained Python functions with short specs — not multi-file diffs; no test execution
*available* to the judge (our reviewers have gates/tests, i.e. better anchors than the studied
setting — the mitigation direction should transfer, magnitudes may not); Claude-4.5-Sonnet, not
Opus 5; canonical-solution labels imperfect (a "false" rejection can be an alternative spec
reading); Feb 2026 preprint, not yet peer-reviewed.

## Briefing check

Strongly confirmed — this is the load-bearing S7 citation: systematic misclassification of
correct code, the counterintuitive elaborate-prompt effect, and a working execution-grounded
mitigation, all quantified. The one framing correction: the paper's false-rejection profile is
*semantic overreach* (unfalsifiable logic claims, invented requirements) rather than style
pedantry — which matches our loop's experience that findings look individually fair.
