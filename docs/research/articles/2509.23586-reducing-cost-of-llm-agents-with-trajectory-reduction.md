# Reducing Cost of LLM Agents with Trajectory Reduction

## Abstract

Multi-turn agent systems based on Large Language Models (LLMs) have become increasingly popular for
software engineering tasks. While LLM agents demonstrate promising effectiveness, the high
computational cost of input tokens due to ever-growing trajectories remains a significant efficiency
concern. Efficiency has been largely overlooked in existing studies and agent products, and this
paper addresses this gap by introducing an inference-time trajectory reduction approach that reduces
computational costs. By analyzing existing agent trajectories, we demonstrate that useless,
redundant, and expired information is widespread across trajectories. Such waste can be identified
and reduced without compromising the agent's performance. We propose a simple yet effective
trajectory reduction approach, AgentDiet, which automatically removes such waste during agent
execution. We implement AgentDiet on a top-performing coding agent, and our evaluation on two LLMs
and two benchmarks shows that AgentDiet can reduce input tokens by 39.9%-59.7% and the total
computational cost by 21.1%-35.9%, while maintaining the same agent performance. These results
indicate that inference-time trajectory reduction is a promising direction for agent systems.

### <span class="ltx_tag ltx_tag_section">1. </span>Introduction

<div id="S1.p1" class="ltx_para">

Large Language Models (LLMs) have been widely used for various software engineering tasks such as
code generation, testing, and repair (<a href="#bib.bib21" class="ltx_ref">Liu et al. 2024</a>;
<a href="#bib.bib13" class="ltx_ref">Jiang et al. 2023</a>;
<a href="#bib.bib11" class="ltx_ref">Farzandway and Ghassemi 2025</a>;
<a href="#bib.bib2" class="ltx_ref">Ahmed et al. 2024</a>;
<a href="#bib.bib40" class="ltx_ref">Xia et al. 2024</a>;
<a href="#bib.bib41" class="ltx_ref">Xia and Zhang 2024</a>). A prominent trend in the application
of LLMs is agent-based approaches (<a href="#bib.bib6" class="ltx_ref">Bouzenia et al. 2024</a>;
<a href="#bib.bib30" class="ltx_ref">Qin et al. 2024</a>;
<a href="#bib.bib15" class="ltx_ref">Kang et al. 2025</a>;
<a href="#bib.bib36" class="ltx_ref">Wang et al. 2024c</a>;
<a href="#bib.bib44" class="ltx_ref">Yang et al. 2024a</a>;
<a href="#bib.bib47" class="ltx_ref">Zhang et al. 2024</a>), where LLMs are asked to complete
complex tasks through multi-step reasoning and tool calling. For example,
mini-SWE-agent (<a href="#bib.bib44" class="ltx_ref">Yang et al. 2024a</a>) achieves a single-shot
performance of 65% in SWE-bench
Verified (<a href="#bib.bib14" class="ltx_ref">Jimenez et al. 2024</a>) using Claude 4
Sonnet (<a href="#bib.bib4" class="ltx_ref">Anthropic 2025b</a>), indicating that agents can fix
real-world GitHub issues with basic tools such as file editing and bash scripting. Given their
promising performance, LLM agents are integrated into various AI
products (<a href="#bib.bib3" class="ltx_ref">Anthropic 2025a</a>;
<a href="#bib.bib8" class="ltx_ref">Cursor 2025</a>), and 24% of professional developers already use
LLM agents daily or weekly in 2025 (<a href="#bib.bib26" class="ltx_ref">Overflow 2025</a>).

</div>

<div id="S1.p2" class="ltx_para">

Although these agent approaches demonstrate promising performance in terms of effectiveness,
efficiency remains a concern for their
application (<a href="#bib.bib10" class="ltx_ref">Fan et al. 2025b</a>). In a recent survey by
StackOverflow (<a href="#bib.bib26" class="ltx_ref">Overflow 2025</a>), 53% of the participants
believe that the cost of using AI agents is a barrier for them. This efficiency issue has been
largely overlooked in existing studies, leaving a significant gap to address.

</div>

<div id="S1.p3" class="ltx_para">

The root cause of this efficiency issue lies in the workflow of LLM agents, specifically the
ever-growing trajectory. In a typical agent system, once the LLM calls a tool, the tool call and its
result are kept in the trajectory until the agent completes the entire task. Therefore, if the LLM
opens a large file or runs a command that generates verbose output, the computational cost of these
tokens snowballs in each subsequent step (<a href="#bib.bib9" class="ltx_ref">Fan et al. 2025a</a>).
This results in non-negligible waste. For example, in September 2025, the daily token usage of
Claude 4 Sonnet reached 100 billion on the OpenRouter
platform (<a href="#bib.bib25" class="ltx_ref">OpenRouter 2025</a>), and 99% of them were input
tokens accumulated in the trajectory, while only the remaining 1% were generated by the LLM.

</div>

<div id="S1.p4" class="ltx_para">

To address the above efficiency issue, this paper focuses on reducing trajectory tokens for coding
LLM agents. In academia, most existing papers on token reduction focus on single-turn tasks, such as
trimming the retrieved input for
question-answering (<a href="#bib.bib28" class="ltx_ref">Pan et al. 2024</a>;
<a href="#bib.bib7" class="ltx_ref">Chirkova et al. 2025</a>;
<a href="#bib.bib38" class="ltx_ref">Wang et al. 2023</a>;
<a href="#bib.bib23" class="ltx_ref">Louis et al. 2025</a>;
<a href="#bib.bib48" class="ltx_ref">Zhang et al. 2022</a>). These tasks differ from agentic coding
in multiple aspects, limiting the applicability of existing approaches. Specifically: (1) these
approaches reduce all input tokens at once, whereas trajectory tokens gradually accumulate in
agents, making the timing of reduction a new research question; (2) these approaches reduce tokens
in natural language, while coding agents process structured information such as software source
code; (3) some approaches require modifying the LLM inference process or even the model itself,
which is impractical and unsuitable for proprietary LLMs that do not provide such capabilities. To
the best of our knowledge, there is no existing publication on inference-time trajectory reduction
for coding agents. In industry, agent products such as Claude Code and
Cursor (<a href="#bib.bib3" class="ltx_ref">Anthropic 2025a</a>;
<a href="#bib.bib8" class="ltx_ref">Cursor 2025</a>) sparingly apply LLM-based trajectory reduction
(often called “compaction”) only when the context window is full or the user explicitly requests it,
focusing on improving robustness rather than efficiency. As a result, the potential for efficiency
improvement via trajectory reduction remains unknown. This paper reveals this potential by designing
an LLM-based trajectory reduction approach and evaluating it on multiple benchmarks and LLMs.

</div>

#### <span class="ltx_tag ltx_tag_subsection">2.1. </span>Preliminaries

<div id="S2.SS1.p1" class="ltx_para">

> <span id="S2.SS1.p1.1.1.1" class="ltx_text ltx_font_italic">“Agents are models using tools in a
> loop.”</span>

\- Hannah Moran from Anthropic, <span id="S2.SS1.p1.2.1" class="ltx_text ltx_font_italic">Prompting
for Agents</span>

</div>

<figure id="S2.F1" class="ltx_figure">

<figcaption><span class="ltx_tag ltx_tag_figure">Figure 1. </span>Typical workflow of an LLM
agent.</figcaption>
</figure>

<div id="S2.SS1.p2" class="ltx_para">

In recent years, Large Language Models (LLMs) have demonstrated the ability to assist with a wide
variety of tasks. Following established approaches such as
Chain-of-Thought (<a href="#bib.bib39" class="ltx_ref">Wei et al. 2022</a>),
ReAct (<a href="#bib.bib45" class="ltx_ref">Yao et al. 2023</a>), and
CodeAct (<a href="#bib.bib35" class="ltx_ref">Wang et al. 2024a</a>), LLM agents have emerged as a
promising paradigm for integrating LLMs into such tasks by equipping the LLM with tools to interact
with the environment. In the field of software engineering, this means that the LLM can operate on
the codebase autonomously with the ability to read files, make edits, execute commands, commit
changes, etc.

</div>

<div id="S2.SS1.p3" class="ltx_para">

Fig. <a href="#S2.F1" class="ltx_ref"
title="Figure 1 ‣ 2.1. Preliminaries ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">1</span></a> shows the typical workflow of an LLM agent. The core of an
agent is its *trajectory*, which records all the necessary context that will be given to the LLM. An
agent starts with an initial trajectory that contains the instruction to the LLM (in a system
message) and the current task (in a user message). The LLM then analyzes the current situation and
predicts the next action to take in a standard tool call format (in an assistant message). The agent
system parses the generated tool call, executes the action, and returns the output to the LLM (in a
tool message). In this loop, assistant and tool messages are continuously concatenated into the
trajectory, which will be the input to subsequent LLM predictions. The loop continues until the LLM
decides to finish the task with a special indicator, or when the agent system reaches the step
limit.

</div>

<div id="S2.SS1.p4" class="ltx_para">

From this workflow, we can identify an obvious efficiency issue in such agent systems: Once the LLM
calls a tool, the corresponding assistant and tool messages will be concatenated into the trajectory
and will be kept forever until the task finishes. A long message is included in each subsequent LLM
prediction, even if its content is irrelevant (or no longer relevant) to the task, leading to
inefficient use of computational resources. As a quantitative result, the average trajectory for
solving a single GitHub issue that we collected from the SWE-bench
Verified (<a href="#bib.bib14" class="ltx_ref">Jimenez et al. 2024</a>) benchmark contains 48.4K
tokens in 40 steps. Breaking down these tokens, tool messages (containing the results of tool calls)
use 30.4K tokens, assistant messages use 13.7K tokens (of which 11.9K are the arguments of tool
calls), and system/user messages (containing the initial instructions) use 4.4K tokens. Since each
token concatenated into the trajectory is included in every subsequent input to the LLM, the
accumulated token usage per issue reaches 1.0M, which requires excessive computational and memory
resources.

</div>

<div id="S2.SS1.p5" class="ltx_para">

Recent LLMs are equipped with the KV Cache mechanism, which mitigates the issue of high
computational cost by caching repeated calculations of the Key and Value matrices in the
Transformer (<a href="#bib.bib34" class="ltx_ref">Vaswani et al. 2017</a>) architecture. However,
this does not eliminate the need for trajectory reduction because: (1) KV Cache only caches part of
the computations, and the remaining calculations are still costly as the trajectory grows rapidly;
(2) KV Cache consumes hardware resources like VRAM and I/O bandwidth, so reducing the trajectory
length conserves these valuable resources. In fact, the existence of KV Cache makes designing
trajectory reduction approaches more challenging, since modifying a token in the trajectory
invalidates the cache for all subsequent tokens.

</div>

<div id="S2.SS1.p6" class="ltx_para">

Long messages in the context window not only harm the efficiency but also cause the performance of
LLMs to degrade (<a href="#bib.bib22" class="ltx_ref">Liu et al. 2023</a>;
<a href="#bib.bib17" class="ltx_ref">Li et al. 2025</a>). Therefore, removing content from
trajectories does not necessarily lead to a drop in the agent’s performance. Instead, it has the
potential to maintain or even slightly improve the performance of agents by removing waste.

</div>

</div>

<div id="S2.SS2" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">2.2. </span>Waste in Trajectories

<div id="S2.SS2.p1" class="ltx_para">

This subsection presents a pilot study where we analyze the feasibility of trajectory reduction by
first identifying typical waste in trajectories. For this purpose, we use SWE-bench
Verified (<a href="#bib.bib14" class="ltx_ref">Jimenez et al. 2024</a>), a popular benchmark
requiring agent systems to solve GitHub issues in well-known Python repositories. The benchmark
makes the logs and trajectories of all participants available for download. We downloaded and
manually inspected 100 trajectories from Trae
Agent (<a href="#bib.bib12" class="ltx_ref">Gao et al. 2025</a>), which is based on Claude 4 Sonnet
and ranked top on SWE-bench Verified.

</div>

<div id="S2.SS2.p2" class="ltx_para">

By qualitatively inspecting the contents of the trajectories, we found that waste is widespread in
almost all trajectories. We categorized the waste into three typical scenarios in which tokens could
be removed or compressed from a human perspective:

</div>

<div id="S2.SS2.SSS1" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">2.2.1. </span>Useless Information

<div id="S2.SS2.SSS1.p1" class="ltx_para">

Some information is irrelevant to the task and can be safely removed with minimal information loss.
For example, nearly all trajectories begin with a tool call to enumerate all files in the
repository, and the tool response includes cache and resource files (e.g., files under the
<span id="S2.SS2.SSS1.p1.1.1" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">\_\_pycache\_\_</span> and <span id="S2.SS2.SSS1.p1.1.2"
class="ltx_text ltx_font_typewriter" style="font-size:90%;">.egg-info</span> directories). In all
trajectories, the agent also executed commands to build and test the project, which may generate
verbose output (e.g., GNU <span id="S2.SS2.SSS1.p1.1.3" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">make</span> prints the message “<span id="S2.SS2.SSS1.p1.1.4"
class="ltx_text ltx_font_typewriter" style="font-size:90%;">make\[2\]: Entering/Leaving directory
'...'</span>” for each visited location by default). Although Trae Agent has a mechanism to truncate
output to the first 16KB, a fixed threshold only avoids extreme cases, and we still frequently
observed useless information within this threshold.

</div>

</div>

<div id="S2.SS2.SSS2" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">2.2.2. </span>Redundant Information

<div id="S2.SS2.SSS2.p1" class="ltx_para">

When a piece of information appears multiple times in the trajectory, redundant copies can be
removed without losing information. The most typical case of redundant information involves the
<span id="S2.SS2.SSS2.p1.1.1" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">str_replace_editor</span> tool, a standard file editing tool designed by
Anthropic that is frequently used in all trajectories. The tool call arguments for
<span id="S2.SS2.SSS2.p1.1.2" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">str_replace_editor</span> are passed as JSON, such as
<span id="S2.SS2.SSS2.p1.1.3" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">{"command": "str_replace", "path": "F", "old_str": "P", "new_str":
"Q"}</span>, where P is a unique fragment of file F that typically contains multiple lines, and will
be replaced by Q. The tool will perform the string replacement and then respond with the replaced
result. There are multiple redundancies in such a tool call: (1) Q in the argument is repeated in
the replaced result in the tool response; (2) Q may contain the same components (e.g., shared
statements) as P; (3) the agent must have retrieved the context to edit prior to this tool call, so
P repeats code from previous steps in the trajectory.

</div>

</div>

<div id="S2.SS2.SSS3" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">2.2.3. </span>Expired Information

<div id="S2.SS2.SSS3.p1" class="ltx_para">

Information relevant to a local step may no longer be necessary after the step is completed. A
typical case is where the agent loops through many items to find the relevant one. For example, in
the process of diagnosing the root cause of the issue, the agent often searches for a symbol with
the <span id="S2.SS2.SSS3.p1.1.1" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">grep</span> shell command, and then opens each file to read as it appears in
the search results. This process takes a few steps in the trajectory, and once the agent identifies
the faulty file, most content in other files becomes unnecessary.

</div>

</div>

</div>

<div id="S2.SS3" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">2.3. </span>A Prototype Approach to Trajectory Reduction

<div id="S2.SS3.SSS1" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">2.3.1. </span>Reducing the Waste

<div id="S2.SS3.SSS1.p1" class="ltx_para">

In this subsection, we discuss how to automatically identify and reduce waste in trajectories. A
straightforward approach would be to maintain a set of rules (such as regular expressions) for each
typical kind of waste, but such rules are unlikely to cover the variety of scenarios. For example,
it is difficult to write a rule to identify all verbose output in test logs, since every project has
its own output format.

</div>

<div id="S2.SS3.SSS1.p2" class="ltx_para">

Given the heuristic nature of this task, we chose to identify and reduce waste with the help of an
LLM. We designed a prompt for trajectory reduction consisting of four parts:

</div>

##### <span class="ltx_tag ltx_tag_subsubsection">2.3.2. </span>Agent Integration

<div id="S2.SS3.SSS2.p1" class="ltx_para">

After showing that trajectory reduction is possible with an LLM, the next natural topic is how to
integrate this into an agent system.

</div>

<div id="S2.SS3.SSS2.p2" class="ltx_para">

Ideally, if the agent system is powerful enough, it could reduce its own trajectory given a tool for
that purpose. We tested this hypothesis by implementing a tool called <span id="S2.SS3.SSS2.p2.1.1"
class="ltx_text ltx_font_typewriter" style="font-size:90%;">erase</span>, which allows the agent to
override existing steps in the trajectory. We assigned a numeric ID to each segment in the
trajectory, and the LLM could call the <span id="S2.SS3.SSS2.p2.1.2"
class="ltx_text ltx_font_typewriter" style="font-size:90%;">erase</span> tool with arguments such as
<span id="S2.SS3.SSS2.p2.1.3" class="ltx_text ltx_font_typewriter" style="font-size:90%;">{"id": 17,
"takeaway": "unrelated content"}</span> to replace the segment with a short takeaway. However, based
on our preliminary experiments, even with powerful LLMs such as Claude 4 Sonnet and Gemini 2.5 Pro,
the agent often persisted with the original task without calling <span id="S2.SS3.SSS2.p2.1.4"
class="ltx_text ltx_font_typewriter" style="font-size:90%;">erase</span>, despite explicit prompts.

<div id="S2.SS3.SSS2.p4" class="ltx_para">

A possible reason is that the LLM has memorized the standard procedure of program repair during
training, leading to an uncontrollable tendency to follow that procedure given the context.
Therefore, enabling the agent to reduce its own trajectory would require careful fine-tuning, which
is resource-intensive, error-prone, and often impossible for proprietary LLMs.

</div>

<div id="S2.SS3.SSS2.p5" class="ltx_para">

To overcome this problem, we took a step back and moved the trajectory reduction step to a separate
module called the *reflection module*. This LLM-based module is explicitly called by the outer
system to reduce the trajectory when there is an estimated benefit. In this way, the timing of
trajectory reduction is controlled by an external system, and the the LLM that runs the agent
remains unaware of the reduction process, minimizing disturbance to its original workflow.

</div>

</div>

<div id="S2.SS3.SSS3" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">2.3.3. </span>Controlling the Overhead

<div id="S2.SS3.SSS3.p1" class="ltx_para">

In terms of efficiency, the current design with a separate reflection module is not ideal due to the
additional cost overhead. Passing the full agent trajectory to the reflection module at each step
would double the token usage, defeating the whole purpose of cost reduction. Making the situation
worse, the KV Cache cannot be shared between the target agent and the reflection module due to
differences in the system prompts and tools. Furthermore, modifying a step in the trajectory
invalidates all subsequent caches. Therefore, controlling the overhead becomes an essential topic.

</div>

<div id="S2.SS3.SSS3.p2" class="ltx_para">

The first approach to consider is the choice of LLM in the reflection module. Since trajectory
reduction is arguably easier than the agent’s primary task, we can significantly reduce overhead by
choosing a more cost-efficient LLM for the reflection module. In the case study illustrated in
Fig. <a href="#S2.F2" class="ltx_ref"
title="Figure 2 ‣ 2.3.1. Reducing the Waste ‣ 2.3. A Prototype Approach to Trajectory Reduction ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">2</span></a>, the trajectory was generated by the agent using Claude 4
Sonnet, while the reduction was performed by GPT-5 mini, which is 12 times cheaper than Claude 4
Sonnet, minimizing the overhead concern. We will discuss more about the choice of LLM in Section
 <a href="#S4.SS2" class="ltx_ref"
title="4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.2</span></a>.

</div>

<figure id="S2.F3" class="ltx_figure">

<figcaption><span class="ltx_tag ltx_tag_figure">Figure 3. </span>Design of the reflection module in
AgentDiet.</figcaption>
</figure>

<div id="S2.SS3.SSS3.p3" class="ltx_para">

To further reduce overhead, we reduce the amount of context provided to the LLM used in the
reflection module. We propose a sliding-window approach, as shown in
Fig. <a href="#S2.F3" class="ltx_ref"
title="Figure 3 ‣ 2.3.3. Controlling the Overhead ‣ 2.3. A Prototype Approach to Trajectory Reduction ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">3</span></a>. The orange box in the figure refers to the reflection
module. When the agent reaches step $`s`$, the reflection module is allowed to reduce only the
content in step $`s-a`$, and given only a fixed amount of context, from step $`s-a-b`$ to step
$`s`$. The module prompts a cost-efficient LLM to reduce the content in step $`s-a`$ by removing
useless, redundant, and expired information with the given context. $`a`$ and $`b`$ are
hyperparameters that can be adjusted to balance the cost overhead and agent performance caused by
trajectory reduction. Furthermore, we skip the trajectory reflection process if the length of step
$`s-a`$ is within a token threshold $`\theta`$, where the benefit would be small.
Fig. <a href="#S2.F3" class="ltx_ref"
title="Figure 3 ‣ 2.3.3. Controlling the Overhead ‣ 2.3. A Prototype Approach to Trajectory Reduction ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">3</span></a> illustrates the approach where $`a=2`$, $`b=1`$ and
$`\theta=0`$. The choice of these hyperparameters will be discussed in Section
 <a href="#S4.SS2" class="ltx_ref"
title="4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.2</span></a>.

</div>

<div id="S2.SS3.SSS3.p4" class="ltx_para">

From the perspective of efficiency, the token usage of each trajectory reduction step is capped at
the length of $`a+1+b`$ steps. Additionally, since it only modifies a fixed recent step (step
$`s-a`$), KV Cache entries corresponding to previous steps are preserved, minimizing overhead from
cache invalidation. From the perspective of agent performance, this design ensures that the
reflection module cannot destructively erase the most recent step or all steps at once, preventing
disastrous outcomes from occasional LLM failures.

</div>

</div>

</div>

</div>

title="Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">1</span></a> takes two inputs: the problem instruction $`I`$, which

interact with through tool calls. The output is the result $`r`$, which indicates whether the task
is completed. The environment $`E`$ is modified by the agent in place. The algorithm also contains
several constants that are adjustable hyperparameters.

</div>

<div id="S3.p5" class="ltx_para">

The first part (lines <a href="#alg1.l5" class="ltx_ref"
title="In Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">5</span></a>-<a href="#alg1.l13" class="ltx_ref"
title="In Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">13</span></a>) of this algorithm is directly based on the workflow of
existing LLM agents. It first initializes the trajectory $`T`$ with only the initial system and user
prompts constructed with $`I`$. Then, it iteratively calls the $`\text{LLM}_{\text{agent}}`$
function to generate an assistant message ($`m_{\text{assis}}`$) that contains the next action to
take based on $`T`$. If the action is to finish the task, the agent stops; otherwise, the
<span id="S3.p5.1.1" class="ltx_text ltx_font_smallcaps">ExecTool</span> function interacts with the
environment $`E`$ based on the tool call and retrieves the result as $`m_{\text{tool}}`$. The
messages generated in this step ($`m_{\text{assis}}`$ and $`m_{\text{tool}}`$) are then concatenated
into $`T`$.

</div>

<div id="S3.p6" class="ltx_para">

Lines <a href="#alg1.l15" class="ltx_ref"
title="In Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">15</span></a>-<a href="#alg1.l26" class="ltx_ref"
title="In Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">26</span></a> highlighted by the orange box represent the reflection
module introduced in AgentDiet. As illustrated in Fig. <a href="#S2.F3" class="ltx_ref"
title="Figure 3 ‣ 2.3.3. Controlling the Overhead ‣ 2.3. A Prototype Approach to Trajectory Reduction ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">3</span></a>, the reflection module employs a sliding window and aims
to reduce the length of step $`s-a`$ when the agent reaches step $`s`$. It uses another language
model, $`\text{LLM}_{\text{reflect}}`$, which can be more cost-efficient than
$`\text{LLM}_{\text{agent}}`$ to reduce the overhead of trajectory reduction. The module is
controlled by the hyperparameter $`\theta`$, which is the minimum number of tokens required for a
beneficial reduction, and by $`a`$ and $`b`$, which define the number of steps included in the
context given to $`\text{LLM}_{\text{reflect}}`$. It first serializes the target step into a string
(<span id="S3.p6.1.1" class="ltx_text ltx_font_smallcaps">Serialize</span>) and calculates its
tokenized length (<span id="S3.p6.1.2" class="ltx_text ltx_font_smallcaps">Length</span>) as
$`l_{\text{orig}}`$ at line <a href="#alg1.l16" class="ltx_ref"
title="In Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">16</span></a>. If the length is below the threshold
($`l_{\text{orig}}\leq\theta`$), reflection is skipped because the benefit may not exceed the
overhead. Otherwise, it constructs the context ($`ctx`$) and asks $`\text{LLM}_{\text{reflect}}`$ to
generate a reduced version of the target step based on $`ctx`$. If the length reduction exceeds the
token threshold $`\theta`$, the target step in the trajectory $`T`$ is replaced by the reduced
version at line <a href="#alg1.l23" class="ltx_ref"
title="In Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">23</span></a>.

</div>

<div id="S4" class="section ltx_section">

### <span class="ltx_tag ltx_tag_section">4. </span>Implementation

<div id="S4.SS1" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">4.1. </span>Integration in Agents

<div id="S4.SS1.p1" class="ltx_para">

AgentDiet is a general approach that can be readily applied to any LLM agent fitting the definition
“agents are models using tools in a loop”. For a typical agent system similar to the example in
Algorithm <a href="#alg1" class="ltx_ref"
title="Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">1</span></a>, we can add a call to the reflection module (highlighted
by the orange box) after each step in the agentic loop.

</div>

<div id="S4.SS1.p2" class="ltx_para">

Following this procedure, we integrated AgentDiet into Trae Agent, which is open-source and ranked
first on SWE-bench Verified at the time of our research (July 2025). We did not further integrate or
experiment with AgentDiet in other LLM agents, based on the observation that current agent systems
are generally homogeneous and employ a similar set of prompts and tools. For example, Trae Agent is
equipped with four tools: <span id="S4.SS1.p2.1.1" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">bash</span> to execute Bash commands, <span id="S4.SS1.p2.1.2"
class="ltx_text ltx_font_typewriter" style="font-size:90%;">str_replace_editor</span> to view or
edit files, <span id="S4.SS1.p2.1.3" class="ltx_text ltx_font_typewriter"
style="font-size:90%;">think</span> to analyze the issue, and <span id="S4.SS1.p2.1.4"
class="ltx_text ltx_font_typewriter" style="font-size:90%;">task_done</span> to finish the task.
This set of tools is semantically similar to those in other systems, such as
mini-SWE-agent (<a href="#bib.bib44" class="ltx_ref">Yang et al. 2024a</a>) and
OpenHands (<a href="#bib.bib36" class="ltx_ref">Wang et al. 2024c</a>). Therefore, the results with
Trae Agent are likely to generalize to a variety of similar agent systems.

</div>

<div id="S4.SS1.p3" class="ltx_para">

Note that there are variants of agent systems, such as *ensembled* systems that call the LLM agent
multiple times and decide the final answer by majority voting or an LLM, and *multi-agent* systems
that simultaneously spawn multiple LLM agents with a communication mechanism. AgentDiet can be
integrated into such systems by adding the reflection module to the LLM agent in an ensembled
system, or to all LLM agents in a multi-agent system. To maintain the generality of the approach,
this paper does not focus on optimizations specific to these systems. We leave the evaluation of
such applications for future work.

</div>

</div>

<div id="S4.SS2" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">4.2. </span>Hyperparameter Settings

<div id="S4.SS2.p1" class="ltx_para">

In this subsection, we discuss the effect of different hyperparameter settings
($`\text{LLM}_{\text{reflect}}`$, $`\theta`$, $`a`$, and $`b`$, as shown in
Algorithm <a href="#alg1" class="ltx_ref"
title="Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">1</span></a>) based on the Trae Agent integration. Note that the other
two hyperparameters ($`\text{LLM}_{\text{agent}}`$ and $`s_{\text{max}}`$) already exist in the
original Trae Agent, so we exclude them from the discussion and set them to standard default values:
$`\text{LLM}_{\text{agent}}=`$ Claude 4 Sonnet, and $`s_{\text{max}}=`$ 50.

</div>

<div id="S4.SS2.SSS1" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">4.2.1. </span>The Process

<div id="S4.SS2.SSS1.p1" class="ltx_para">

Since the search space of hyperparameters is multidimensional, we used the standard hill climbing
algorithm to find an ideal setting, which is arguably more rigorous than determining each parameter
independently.

</div>

<div id="S4.SS2.SSS1.p2" class="ltx_para">

The process began by setting each hyperparameter to an initial default value. Then, we
quantitatively compared efficiency and agent performance via a small experiment involving variants.
Each variant adjusted one hyperparameter to a different value in the search space while keeping
other hyperparameters at their default values. If a variant demonstrated a better overall result, it
was selected as the new default value for that hyperparameter in the next iteration. The process
repeated until the hyperparameters converged to a local optimum.

</div>

</div>

<div id="S4.SS2.SSS2" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">4.2.2. </span>Benchmark

<div id="S4.SS2.SSS2.p1" class="ltx_para">

In this process, we used a random subset of 100 instances from SWE-bench
Verified (<a href="#bib.bib14" class="ltx_ref">Jimenez et al. 2024</a>) as the benchmark for
deciding hyperparameters. This was the same set used in the manual analysis in Section
 <a href="#S2.SS2" class="ltx_ref"
title="2.2. Waste in Trajectories ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">2.2</span></a>. We did not use the full benchmark because the remaining
instances will be used exclusively for evaluation in Section  <a href="#S5" class="ltx_ref"
title="5. Evaluation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">5</span></a>.

</div>

</div>

  </div>

short or recent step.

  </div>

  <div id="S4.I2.i2.p1" class="ltx_para">

  </div>
- <span id="S4.I2.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S4.I2.i3.p1" class="ltx_para">

  </div>

</div>

<div id="S4.SS2.SSS3.p7" class="ltx_para">

higher values would strictly increase cost overhead and potentially improve agent performance. Since
the variants of $`a=2`$ and $`b=1`$ already exhibit satisfactory performance, as will be shown in
the results, we estimated that there would be minimal benefit in further increasing $`a`$ or $`b`$.

<div id="S4.SS2.SSS4.p2" class="ltx_para">

- <span id="S4.I3.i1"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S4.I3.i1.p1" class="ltx_para">

  <span id="S4.I3.i1.p1.1.1" class="ltx_text ltx_font_bold">Keep%</span>: The average percentage of
  trajectory tokens retained by the LLM in the reflection module, formally
  $`\sum l_{\text{reduced}}\>/\>\sum l_{\text{orig}}*100`$ in
  Algorithm <a href="#alg1" class="ltx_ref"
  title="Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span

  Original baseline has Keep% = 100.

  </div>
- <span id="S4.I3.i2"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S4.I3.i2.p1" class="ltx_para">

  <span id="S4.I3.i2.p1.1.1" class="ltx_text ltx_font_bold">I</span> and <span id="S4.I3.i2.p1.1.2"
  class="ltx_text ltx_font_bold">O</span>: Accumulated usage of input (“prompt”) or output
  (“completion”) tokens. For easier comparison, we normalized all numbers in these two rows so that
  the Original baseline has $`I=1`$.

  </div>
- <span id="S4.I3.i3"><span class="ltx_tag ltx_tag_item">•</span></span>
  <div id="S4.I3.i3.p1" class="ltx_para">

  <span id="S4.I3.i3.p1.1.1" class="ltx_text ltx_font_bold">\$</span> and <span id="S4.I3.i3.p1.1.2"
  class="ltx_text ltx_font_bold">\$+</span>: LLM cost for agent steps (\$) and reflection steps
  (\$+). This value is calculated based on the pricing for the LLMs involved. The cost covers both
  input tokens (considering the discount for tokens in KV Cache) and output tokens. We normalized
  all numbers in these two rows so that the Original baseline has $`\$=1`$. We separately reported
  the cost for agent steps and reflection steps to help readers better understand the overhead
  caused by the reflection module.

  </div>

</div>

<span id="S4.SS2.SSS4.p3.1.1" class="ltx_text ltx_font_bold">agent’s performance</span>:

<div id="S4.SS2.SSS4.p4" class="ltx_para">

  <div id="S4.I4.i1.p1" class="ltx_para">

  <span id="S4.I4.i1.p1.1.1" class="ltx_text ltx_font_bold">Pass%</span>: The percentage of

  <span id="S4.I4.i2.p1.1.1" class="ltx_text ltx_font_bold">Step</span> and
  <span id="S4.I4.i2.p1.1.2" class="ltx_text ltx_font_bold">PStep</span>: The average number of
  total agent steps for all instances (Step) and for only successfully resolved instances (PStep).
  Lower is better because an increase in steps indicates that some information is inappropriately
  reduced, disturbing the agent and requiring it to recover the information with additional steps.

  </div>

<div id="S4.SS2.SSS5.p2" class="ltx_para">

Table <a href="#S4.T2" class="ltx_ref"
title="Table 2 ‣ 4.2.5. Results ‣ 4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">2</span></a> shows the results for the $`\text{LLM}_{\text{reflect}}`$
hyperparameter. The first row (Keep%) shows that all five LLMs can remove most of the content in the
trajectory steps where the length is at least $`\theta=500`$ tokens. However, different LLMs have
different characteristics, keeping 14.4%–29.0% of tokens in the processed steps. As a result, the
accumulated input tokens (I) drop to 47.3%–72.2%, while the output tokens (O) remain close to the
Original baseline. The agent cost (\$) drops to 65.2%–81.8% of Original. The “\$+” row indicates
that $`\text{LLM}_{\text{reflect}}`$ introduces an overhead cost of 5.2%–14.8%, depending on the
model used.

</div>

<div id="S4.SS2.SSS5.p3" class="ltx_para">

The last three rows measure the performance impact of trajectory reduction on the SWE-bench Verified
instances. While the numbers in Pass% vary between LLMs and baselines, all variants reach a Pass% of
at least 58% (for the Delete baseline), which is close to the 65% achieved by the Original agent. It
may be surprising that even trivial baselines such as Delete and Random have reasonably well agent
performance. The reason is that the choice of other hyperparameters ($`a=2`$ and $`\theta=500`$ in
this experiment) ensures that $`\text{LLM}_{\text{reflect}}`$ can only manipulate steps of excessive
length after a delay of 2 steps. Therefore, the disruption to $`\text{LLM}_{\text{agent}}`$ is
limited, and the LLM can recover the disrupted information autonomously through additional tool
calls. This leads to an increase in “Step” and “PStep” of more than 13%, but not a large drop in
“Pass%”. In other words, AgentDiet protects against a malfunctioning $`\text{LLM}_{\text{reflect}}`$
and prevents catastrophic failures. We can see that the increase is most severe for the Delete
baseline, which maximizes the disruption to the trajectory. Such baselines are generally impractical
in production due to longer task completion times and the increased risk of instability.

</div>

<div id="S4.SS2.SSS5.p4" class="ltx_para">

Based on the results, GPT-5 mini maintains the same Pass% as Original, and is also the only model
with a decrease in Step and PStep, demonstrating that it does not compromise the agent’s performance
while saving significant token costs. Therefore, GPT-5 mini was chosen as the final
$`\text{LLM}_{\text{reflect}}`$ in AgentDiet.

</div>

<div id="S5.SS1" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">5.1. </span>Experimental Setup

<div id="S5.SS1.SSS1" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">5.1.1. </span>Experiment Subjects

<div id="S5.SS1.SSS1.p1" class="ltx_para">

We use the AgentDiet integrated into Trae
Agent (<a href="#bib.bib12" class="ltx_ref">Gao et al. 2025</a>) as discussed in Section
 <a href="#S4" class="ltx_ref"
title="4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4</span></a>. To assess the generalization of our approach (RQ3), we
evaluate the Trae Agent integration with two recent LLMs (i.e., $`\text{LLM}_{\text{agent}}`$) that
are common for coding agents: Claude 4 Sonnet and Gemini 2.5 Pro. For each LLM, we compare the
results of AgentDiet against the Original baseline, where the reflection step is skipped.

</div>

</div>

<div id="S5.SS1.SSS2" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">5.1.2. </span>Metrics

<div id="S5.SS1.SSS2.p1" class="ltx_para">

We use the same set of metrics as previously described in Section
 <a href="#S4.SS2.SSS4" class="ltx_ref"
title="4.2.4. Metrics ‣ 4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.2.4</span></a>, which contains five metrics for efficiency (Keep%, I,
O, \$, and \$+), and three metrics for performance impact (Pass%, Step, and PStep). For RQ1, we can
infer that AgentDiet improves efficiency if Keep% is low and I/O/\$ decrease over Original. For RQ2,
we can infer that AgentDiet does not harm the agent’s performance if Pass% does not decrease and
Step/PStep does not increase over Original.

</div>

</div>

<div id="S5.SS1.SSS3" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">5.1.3. </span>Benchmarks

<div id="S5.SS1.SSS3.p1" class="ltx_para">

We use two benchmarks for the evaluation. <span id="S5.SS1.SSS3.p1.1.1"
class="ltx_text ltx_font_bold">(1) SWE-bench
Verified</span> (<a href="#bib.bib14" class="ltx_ref">Jimenez et al. 2024</a>) contains 500
human-verified software engineering tasks in Python based on real-world GitHub issues. Since 100
instances in this benchmark are used for manual analysis (in Section
 <a href="#S2.SS2" class="ltx_ref"
title="2.2. Waste in Trajectories ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">2.2</span></a>) and hyperparameter selection (in Section
 <a href="#S4.SS2" class="ltx_ref"
title="4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.2</span></a>), we exclude them from the experiment in this section
and randomly select 200 instances from the remaining 400 instances. Similar to the validation/test
split in standard machine learning practice, this experimental setup mitigates the risk of
hyperparameter overfitting. The list of selected instances is available in the artifact.
<span id="S5.SS1.SSS3.p1.1.2" class="ltx_text ltx_font_bold">(2) Multi-SWE-bench
Flash</span> (<a href="#bib.bib46" class="ltx_ref">Zan et al. 2025</a>) contains 300 instances based
on GitHub issues, similar to SWE-bench Verified. However, this benchmark covers tasks in seven other
programming languages, comprising 45 Rust instances, 45 TypeScript instances, 45 JavaScript
instances, 40 Java instances, 45 Go instances, 40 C instances, and 40 C++ instances. These tasks are
generally harder than SWE-bench Verified, and often require the agent to figure out how to build the
project, whereas SWE-bench Verified provides the agent with a fully working environment from the
start.

</div>

</div>

<div id="S5.SS1.SSS4" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">5.1.4. </span>Hyperparameters

<div id="S5.SS1.SSS4.p1" class="ltx_para">

For the hyperparameters related to AgentDiet, we follow the experiment results in Section
 <a href="#S4.SS2" class="ltx_ref"
title="4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.2</span></a>, setting $`a=2`$, $`b=1`$, $`\theta=500`$ and
$`\text{LLM}_{\text{reflect}}=\text{GPT-5 mini}`$. For the step limit ($`s_{\text{max}}`$), we set
it to 50 for the SWE-bench Verified benchmark as the default value in Trae Agent. $`s_{\text{max}}`$
is increased to 100 for Multi-SWE-bench Flash because this benchmark requires more steps to
complete, as will be shown from the Step/PStep metrics in the experiment results.

</div>

</div>

title="Table 4 ‣ 5.2. Results ‣ 5. Evaluation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4</span></a>. First, the reflection module removes 69.2%–77.4% of the
content it processes (calculated by 1 - $`\frac{\text{Keep\%}}{100}`$). This results in a reduction
in the accumulated input tokens (1 - I) of 39.9%–59.7%. This reduction is lower than the percentage
of deleted tokens among the processed tokens because the reflection module only processes steps
longer than the token threshold ($`\theta=500`$) and only applies the reduction after $`a=2`$ steps.
The reduced input tokens then lead to a reduction in the computational cost of the agent (\$) of
28.6%–44.1%. This reduction is smaller due to costs related to output tokens and invalidated KV
Caches, but is still significant. After we further consider the computational overhead of the
reflection module itself (\$+), the final cost reduction becomes 21.1%–35.9%.

##### <span class="ltx_tag ltx_tag_subsubsection">5.2.2. </span>RQ2. Performance Impact

<div id="S5.SS2.SSS2.p1" class="ltx_para">

From the “Pass%” row in Table <a href="#S5.T4" class="ltx_ref"
title="Table 4 ‣ 5.2. Results ‣ 5. Evaluation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4</span></a>, we can compare the numbers between Original and AgentDiet
to assess its impact on the agent’s performance. On two benchmarks and two LLMs, the performance of
AgentDiet is comparable (-1.0%–+2.0%) to that of Original. These results show that AgentDiet does
not harm the agent’s performance while improving efficiency, which contradicts the common belief of
“test-time compute” (<a href="#bib.bib5" class="ltx_ref">Beeching et al. 2025</a>) that there is a
trade-off between token efficiency and model performance. As discussed in Section
 <a href="#S2.SS1" class="ltx_ref"
title="2.1. Preliminaries ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">2.1</span></a>, a possible explanation is that the performance of LLMs
degrades as the length of the context
increases (<a href="#bib.bib17" class="ltx_ref">Li et al. 2025</a>) or when the context is of low
quality (<a href="#bib.bib16" class="ltx_ref">Laban et al. 2025</a>). Therefore, the removal of
waste information from the agent trajectory may cause less degradation to the model’s performance.

</div>

Multi-SWE-bench Flash + Gemini 2.5 Pro between Original (left) and AgentDiet (right).</figcaption>
</figure>

<div id="S5.SS2.SSS2.p2" class="ltx_para">

Additionally, from the “Step” and “PStep” rows, we observe that AgentDiet does not cause the steps
required to resolve a task to increase. This is an additional indicator confirming that AgentDiet
does not disturb the agent.

</div>

<div id="S5.SS2.SSS2.p3" class="ltx_para">

We see an unexpected case in the last column in Table <a href="#S5.T4" class="ltx_ref"
title="Table 4 ‣ 5.2. Results ‣ 5. Evaluation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4</span></a>, where AgentDiet significantly reduces the average steps
from 57.20 to 43.90 when Gemini 2.5 Pro works on the Multi-SWE-bench Flash benchmark. We identify
the reason by inspecting the trajectories: Gemini 2.5 Pro shows increasingly abnormal behavior when
the context is too long, often resulting in repeated invalid tool calls until the step limit is
reached. Therefore, AgentDiet reduces this probability by reducing the length of the trajectory by
half. Fig. <a href="#S5.F5" class="ltx_ref"
title="Figure 5 ‣ 5.2.2. RQ2. Performance Impact ‣ 5.2. Results ‣ 5. Evaluation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">5</span></a> presents the histogram of the step distribution in the
experiment with Gemini 2.5 Pro + Multi-SWE-bench Flash, where AgentDiet reduces the number of
instances that reach the step limit (100 steps) from 66 to 26. As a result, the average steps are
significantly reduced. This interesting observation highlights a side effect of AgentDiet: improving
the robustness of LLM agents in corner cases.

</div>

class="ltx_text ltx_ref_tag">1</span></a>, AgentDiet adds an additional reflection step to the agent
loop, which introduces an increase in latency. This increase is expected to be minimal, as we use a
cost-efficient model for $`\text{LLM}_{\text{reflect}}`$, and the latency is reduced for
$`\text{LLM}_{\text{agent}}`$ due to the reduction in trajectory length. We do not quantitatively
compare latency between AgentDiet and the Original agent because the experiment relies on commercial
LLM APIs, where latency is highly unstable due to server load. In latency-critical scenarios,
Algorithm <a href="#alg1" class="ltx_ref"
title="Algorithm 1 ‣ 3. Algorithm ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">1</span></a> can be modified to perform the reflection and agent steps
in parallel. This modification would eliminate the latency increase, at the cost of reducing the
context available to the reflection module (hyperparameter $`a`$) by one step.

</div>

</div>

<div id="S6.SS1.SSS2" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">6.1.2. </span>Exploring Different Designs for Trajectory Reduction

<div id="S6.SS1.SSS2.p1" class="ltx_para">

This paper presents a preliminary study on the efficiency of LLM agents and proposes AgentDiet as a
simple yet effective approach for trajectory reduction. Moreover, we only consider off-the-shelf
LLMs as $`\text{LLM}_{\text{reflect}}`$, incurring a cost overhead of 5%–10%. Future work could
replace off-the-shelf LLMs with more efficient customized models to reduce this overhead.

</div>

<div id="S6.SS1.SSS2.p2" class="ltx_para">

For agent systems that route tasks of varying difficulty to different LLMs, it is also possible to
automatically adjust the hyperparameters of AgentDiet to balance efficiency and performance across
tasks.

</div>

</div>

</div>

<div id="S6.SS2" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">6.2. </span>Threats to Validity

<div id="S6.SS2.SSS1" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">6.2.1. </span>Generalization Across Agents

<div id="S6.SS2.SSS1.p1" class="ltx_para">

The main threat to external validity comes from the generalization of our findings. We employ two
benchmarks and two LLMs to mitigate this threat. However, due to effort and cost constraints,
AgentDiet is implemented only for the Trae Agent. In fact, the existing experiments have already
incurred an LLM cost of approximately US\$ 2000, making experimentation with additional agent
systems financially prohibitive. As discussed in Section  <a href="#S4.SS1" class="ltx_ref"
title="4.1. Integration in Agents ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.1</span></a>, current agent systems are generally homogeneous,
employing a similar set of prompts and tools. Therefore, we believe this threat has a limited impact
on our findings.

</div>

</div>

<div id="S6.SS2.SSS2" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">6.2.2. </span>Data Leakage in LLMs

<div id="S6.SS2.SSS2.p1" class="ltx_para">

Another potential threat to internal validity is data leakage in LLMs. Since the experiment utilizes
proprietary LLMs, benchmark instances may have been included in their training data. We have no
control over their training process. There are existing studies on this threat that readers can
refer to. For example, the authors of SWE-bench empirically compared the performance of multiple
LLMs before and after their knowledge cutoff date and concluded that “for most models there’s little
difference in performance before or after this
date” (<a href="#bib.bib14" class="ltx_ref">Jimenez et al. 2024</a>). Thus, we believe this threat
does not significantly affect the validity of our findings.

</div>

<div id="S6.SS2.SSS2.p2" class="ltx_para">

To further mitigate this threat, we included Multi-SWE-bench
Flash (<a href="#bib.bib46" class="ltx_ref">Zan et al. 2025</a>), a recently published benchmark
collected by a third party and not mentioned in the technical report of any evaluated LLM.

</div>

</div>

<div id="S6.SS2.SSS3" class="section ltx_subsubsection">

##### <span class="ltx_tag ltx_tag_subsubsection">6.2.3. </span>Correctness of Patches

<div id="S6.SS2.SSS3.p1" class="ltx_para">

Both SWE-bench Verified and Multi-SWE-bench Flash validate the correctness of agent-generated
patches using developer-written test cases. An instance is deemed successfully resolved if it passes
all test cases. However, a patch that passes all test cases (“plausible”) may not be semantically
equivalent to the ground truth patch written by the developer (“correct”). Consequently, overfitting
to test cases poses a potential threat to validity for all test-based approaches, including ours.
However, prior work (<a href="#bib.bib29" class="ltx_ref">Petke et al. 2024</a>) suggests that
overfitting is not a severe threat in program repair. Additionally, since each instance in SWE-bench
Verified and Multi-SWE-bench Flash includes at least one held-out test case, the threat of
overfitting is mitigated. Furthermore, our experiment compares AgentDiet with the Original agent,
both of which are exposed to the same degree of overfitting threat. Therefore, we believe this
threat does not affect the validity of our findings.

</div>

</div>

</div>

</div>

<div id="S7" class="section ltx_section">

### <span class="ltx_tag ltx_tag_section">7. </span>Related Work

<div id="S7.SS1" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">7.1. </span>Prompt Reduction

<div id="S7.SS1.p1" class="ltx_para">

Previous approaches to prompt reduction improve the efficiency of LLMs by reducing the number of
tokens in the prompt. The majority of prompt reduction work aims at Retrieval-Augmented Generation
(RAG), where the system retrieves documents related to the user query from a database used as a
reference by the LLM. FilCo (<a href="#bib.bib38" class="ltx_ref">Wang et al. 2023</a>) filters the
retrieved documents to retain only useful parts based on information-theoretic approaches. Selective
Context (<a href="#bib.bib18" class="ltx_ref">Li et al. 2023</a>) calculates the self-information of
each token from the output probability and removes tokens with lower self-information.
RECOMP (<a href="#bib.bib42" class="ltx_ref">Xu et al. 2024</a>) introduces an abstractive
compressor that paraphrases the compressed document into a concise abstract.
Provence (<a href="#bib.bib7" class="ltx_ref">Chirkova et al. 2025</a>) and
LLMLingua-2 (<a href="#bib.bib28" class="ltx_ref">Pan et al. 2024</a>) train a classifier model to
judge the relevance of each token in the document with ground truth generated by a teacher LLM.
CPC (<a href="#bib.bib20" class="ltx_ref">Liskavets et al. 2025</a>) trains a context-aware sentence
encoder to judge similarity based on the user query. These approaches target prompts in natural
language, so they do not preserve the important structure in code and command outputs. For example,
LLMLingua-2 does not preserve the full method names of the test cases in the example shown in
Fig. <a href="#S2.F2" class="ltx_ref"
title="Figure 2 ‣ 2.3.1. Reducing the Waste ‣ 2.3. A Prototype Approach to Trajectory Reduction ‣ 2. Problem Analysis ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">2</span></a>, leading to unrecognizable reduced content compared to the
reflection module in AgentDiet. The following text shows the compression result of LLMLingua-2 with
the <span id="S7.SS1.p1.1.1" class="ltx_text ltx_font_typewriter" style="font-size:90%;">rate</span>
parameter set to 0.25, which controls its compression ratio to the same degree of the Keep% of
AgentDiet.

</div>

</div>

<div id="S7.SS1.p3" class="ltx_para">

There are also approaches to prompt reduction specifically designed for code input.
<a href="#bib.bib33" class="ltx_ref">Suneja et al. 2021</a> and
<a href="#bib.bib31" class="ltx_ref">Rabin et al. 2022</a> minimize the input code while preserving
the output based on program simplification approaches.
<a href="#bib.bib48" class="ltx_ref">Zhang et al. 2022</a> and
<a href="#bib.bib37" class="ltx_ref">Wang et al. 2024b</a> prune tokens in the code based on
heuristic rules. <a href="#bib.bib43" class="ltx_ref">Yang et al. 2024b</a> compresses the docstring
in the source code. <a href="#bib.bib27" class="ltx_ref">Pan et al. 2025</a> reformats the code to
remove tokens related to whitespace and indentation.

</div>

<div id="S7.SS1.p4" class="ltx_para">

However, all approaches mentioned above aim to reduce prompts in the *initial* input to the LLM, and
do not consider the iterative nature of agent systems. Since trajectories are generated iteratively
in agent systems, the timing of reduction becomes an important factor that can affect the efficiency
and performance of the agent (as we show in Section  <a href="#S4.SS2" class="ltx_ref"
title="4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.2</span></a>). Therefore, these approaches cannot be directly applied
to agent trajectories without discussing the timing of prompt reduction.

</div>

<div id="S7.SS1.p5" class="ltx_para">

<a href="#bib.bib19" class="ltx_ref">Lindenbauer et al. 2025</a> propose an approach to trajectory
reduction in parallel with our work. Their approach can be considered a variant of the Delete
baseline (in Section  <a href="#S4.SS2.SSS3" class="ltx_ref"
title="4.2.3. The Search Space ‣ 4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">4.2.3</span></a>) that deletes only the tool message but not the
assistant message after a delay of 10 steps. Our results in Table <a href="#S4.T2" class="ltx_ref"
title="Table 2 ‣ 4.2.5. Results ‣ 4.2. Hyperparameter Settings ‣ 4. Implementation ‣ Reducing Cost of LLM Agents with Trajectory Reduction"><span
class="ltx_text ltx_ref_tag">2</span></a> show that the Delete baseline is inferior to all LLM
variants, with a severe decrease in Pass% by 7% and an increase in Step and PStep by 14%.
Furthermore, the choice of $`a=10`$ would cause significant overhead due to KV Cache invalidation.

</div>

</div>

<div id="S7.SS2" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">7.2. </span>Context Management in Agent Systems

<div id="S7.SS2.p1" class="ltx_para">

Various agent systems employ some form of context management mechanism. For example,
Cursor (<a href="#bib.bib8" class="ltx_ref">Cursor 2025</a>) and Claude
Code (<a href="#bib.bib3" class="ltx_ref">Anthropic 2025a</a>) compress the context with an LLM when
the context window is full. Trae Agent (<a href="#bib.bib12" class="ltx_ref">Gao et al. 2025</a>)
truncates each tool response to the first 16 KB.
SWE-agent (<a href="#bib.bib44" class="ltx_ref">Yang et al. 2024a</a>) has multiple configurable
mechanisms such as removing text identified by a regular expression. These mechanisms are often
ad-hoc and applied sparingly, aiming to improve the robustness of the agent in corner cases. In
comparison, AgentDiet aims to improve the overall efficiency of the agent by applying trajectory
reduction aggressively. Such context management mechanisms are also not reported or evaluated as a
first-class research question in existing
papers (<a href="#bib.bib19" class="ltx_ref">Lindenbauer et al. 2025</a>). In contrast, this paper
provides an in-depth discussion and a large-scale evaluation of AgentDiet.

</div>

</div>

<div id="S7.SS3" class="section ltx_subsection">

#### <span class="ltx_tag ltx_tag_subsection">7.3. </span>Efficiency Improvement for White-Box LLM Systems

<div id="S7.SS3.p1" class="ltx_para">

Some approaches improve the efficiency of LLMs by fine-tuning the model structure or optimizing the
inference process. DMC (<a href="#bib.bib24" class="ltx_ref">Nawrot et al. 2024</a>) combines
adjacent KV Cache entries, which has the effect of merging multiple tokens into one token, thus
saving computational cost. PISCO (<a href="#bib.bib23" class="ltx_ref">Louis et al. 2025</a>)
distills RAG documents into embedding vectors with minimal cross-entropy to save tokens.
Prune-on-Logic (<a href="#bib.bib49" class="ltx_ref">Zhao et al. 2025</a>) prunes the
Chain-of-Thought tokens during model training to improve the reasoning efficiency of the trained
model. MEM1 (<a href="#bib.bib50" class="ltx_ref">Zhou et al. 2025</a>) trains an LLM that can
modify the content in fixed-length memory.
Alpine (<a href="#bib.bib32" class="ltx_ref">Saad et al. 2025</a>) adds a pruning layer in each
Transformer block to reduce computational cost.

</div>

<div id="S7.SS3.p2" class="ltx_para">

Since these approaches modify the LLM’s training or inference process, they require white-box access
to the model. However, many state-of-the-art LLMs for agent systems are proprietary and do not
permit such modifications. In comparison, AgentDiet does not depend on the internal mechanisms of
the LLM and can be applied to a wider range of agent systems.

</div>

</div>

</div>

<div id="S8" class="section ltx_section">

### <span class="ltx_tag ltx_tag_section">8. </span>Conclusion

<div id="S8.p1" class="ltx_para">

This paper addresses the efficiency concerns of coding LLM agents, an aspect often overlooked in
existing studies. Through an analysis of trajectories in SWE-bench Verified, we identify typical
sources of waste in these trajectories. We then propose AgentDiet, an inference-time trajectory
reduction approach designed to reduce the token cost of agent systems with a reflection module. We
integrate AgentDiet into a top-performing coding agent and investigate hyperparameter settings for
the reflection module through quantitative experiments. Finally, we evaluate AgentDiet on both
SWE-bench Verified and Multi-SWE-bench Flash using Claude 4 Sonnet and Gemini 2.5 Pro. The results
show that AgentDiet consistently reduces input token usage by 39.9%–59.7%, resulting in significant
computational cost savings of 21.1%–35.9%. Moreover, AgentDiet maintains performance parity with the
Original agent (ranging between -1.0% and +2.0%). This work demonstrates that the cost of LLM agents
can be reduced without compromising performance using a simple approach. This approach benefits the
practical application of agent systems and serves as a foundation for future research.

</div>

</div>
