## 6. Run defects seen in this window

1. **A backgrounded command is not a yield (192 P3, 12:02–13:02, plugin 0.9.12).** The
   reviewer's mutation run (`tsc` + the node suite) passed the Bash tool's 120 s timeout and the
   harness moved it to the background ("You will be notified when it completes"). The reviewer
   applied the new delegate-then-yield rule to it — "I'll stop here and pick up when it
   completes" — and ended its turn. A headless session that ends its turn with only a background
   *command* in flight is never re-invoked (a sub-agent does re-invoke it: 190–193's doc-writers
   resumed on their survey reports); the driver waited out its 3600 s cap, bailed `timeout`, the
   operator resumed 47 s later and the re-run signed off ($3.55). The dead session (32 turns,
   $2.35) is absent from `state.json` and from `slice_cost.py`'s table — the vanished-round trap.
   The yield rule ([agent-dispatch.md](../../plugins/dev/docs/agent-dispatch.md) § Nested
   delegation) needs the boundary stated: sub-agents only; a long command gets a longer
   `timeout` or is polled.
   **Correction (2026-09-01, #783): the diagnosis is wrong.** Headless sessions *are* re-invoked
   when a backgrounded command completes — 71 such completions across the corpus's headless
   sessions, every one after the model had ended its turn, every one resumed (KubeCoder's
   headless engine keeps stdin open for exactly this). 192 P3's run never completed: M1 dropped
   `read()`'s trailing `schedule()`, so the suite's paced-read tests waited for a tick that never
   came and `npm test` hung, its output file still empty three minutes in. Backgrounding had
   removed the tool's deadline, so nothing ended it before the driver's cap. The fix is in
   KubeCoder's preamble (§ Waiting on work now asks for an outer `timeout(1)` on anything that
   can hang), not in the plugin; the registers say nothing about it.
2. **A spec-repo-targeted phase cannot land (189 P10).** The phase's target was
   `../KubeCoderSpecs`; the reviewer's signoff appended to `close-out.md` in that same worktree,
   on the phase branch; the driver's `git checkout main` refused the dirty file. Bail
   `protocol_failure`, resumed 71 s later. Every agent writes the close-out report; when the
   target repo *is* the spec repo the landing step has to commit or stash it first.
3. **`session not found` (181 P1, 20:51).** The reviewer's response stream vanished at 2m35s —
   kc-side; resumed in 17 s, the re-run reviewed from scratch.
4. **The gate's red summary is a brace (193 P6).** The one gate-red of the window (a real-clock
   timer test, green on the fix round) is recorded with `summary: "  }"` — the extractor took the
   last line of a JSON tail. Same phase, one writer-side loss: P5's mutation witnesses reverted
   with `git checkout` and took the writer's uncommitted edits with them ("Lesson learned", one
   re-apply turn).
5. **The shipped diff carries the parallel lanes' work.** Both the digest's `touched` list
   (`slice_base..merge-base` for the target repo, `slice_base..<base branch>` for the others,
   `run_loop.py` ≈ l. 2409) and the doc phase's diff files (`slice_base..<base branch>` for every
   repo, l. 3461) are "everything on the base branch since the slice began", which in parallel
   lanes includes the other lanes' merges: 192's `KubeCoder.diff` (237 KB, 57 files) carries
   190's controller tests; 190's `KubeCoderSpecs.diff` (315 KB, 80 files) is mostly the slice's
   own run artifacts (`sweeps/*.log`, `test_phase_result_r1.json`) plus 191's
   `verification.json`. 192's doc-writer documented only its own scope (its commit touches the
   desktop docs, the manual page and change-discipline.md), so nothing wrong was written that I
   can see — but the writer reads and pays for the file, and the digest tells a writer that
   earlier phases changed files they did not. The slice's own phase commits are in `state.json`
   (`gate_green_commit`, `reviewed_head`); the spec repo's diff should exclude `slices/`.
