# The round-1 blocking rate after 0.9.6–0.9.8: phase size, not the plugin (read, 2026-09-01)

Trello #782, out of the [#720 rework read](readout-2026-09-01.md): the share of phases carrying a
blocking finding at review round 1 went from 11 % to 23 % across the 2026-08-23 plugin step
(0.9.6 prefix trim · 0.9.7 writer digest · 0.9.8 flag trim), and the blocking findings' anchor
flipped from `repro-trace` to `coverage-gap`. The card asked whether that is a regression, and named
three reads: the reviewer's mutation practice, writer transcripts each side of the step, and the
rate on more slices. All three are done here, over KubeCoder 144–195 — 149–153 excluded (their
reviewer rows predate the anchored-findings fields of 0.4.3), 194 added, 195 counted as far as it
has run. `pre` = no `plugin_version` in state.json (run before 0.9.6 landed), `post` = 0.9.7+.
Every figure regenerates from `tools/r1_blocking_readout.py`; the tool counts sub-phases and
appended phases the card's table left out, so its per-slice rows run one or two above the card's.

**Verdict: not a regression the plugin caused.** The rise is a phase-size effect — the post-era
phases are three to four times the size of the pre-era ones, and blocked phases are the large ones
in both eras; standardized on size the two eras' rates are the same. The reviewer runs mutations
exactly as often as before. What did move independently of size is the *impact tag* the reviewer
puts on a coverage-gap anchor — the same finding shape was advisory Minor in the pre era and is
blocking Major now — and nothing in the reviewer's text, dispatch, model or effort changed to
explain it. Of the 20 blocking coverage-gap findings, 19 were fixed by adding tests and none by
changing product code: the cost is a ≈ $3.80 round per finding, ≈ $4 a slice, and no shipped defect
sits behind any of them.

## 2. Phase size explains the rise

Phase size is the added lines of the round-1 diff, `git diff --numstat <merge-base> <r1 commit>`
with both SHAs read from the reviewer's dispatch; the r1 commit survives the slice-end rebase on
53 of 87 pre and 66 of 108 post code phases (root/worker/extensions). Docs excluded.

| added lines | pre blocked / phases | post blocked / phases |
|---|---:|---:|
| < 100 | 1 / 27 | 1 / 12 |
| 100–300 | 4 / 20 | 4 / 21 |
| 300–600 | 2 / 4 | 2 / 11 |
| 600–1200 | 0 / 2 | 8 / 14 |
| ≥ 1200 | 0 / 0 | 4 / 8 |
| median lines (blocked · unblocked) | 81 (264 · 71) | 297 (839 · 242) |

Direct standardization — the pooled per-bin rate applied to each era's size mix — gives 14 %
expected against 13 % observed for pre, 28 % expected against 29 % observed for post. Size mix
reproduces both eras; there is nothing left for the plugin step to explain. Within the bins both
eras populate (< 600 lines) the rates match; the post-era excess is entirely phases of 600+ lines,
of which the pre era has two.

The size proxy every phase has, the writer's output tokens, agrees: median 22.8 k → 36.5 k, and
blocking by tercile 5 → 8 % (small), 3 → 18 % (mid), 33 → 38 % (large) — the mid-band rise is
partly the proxy (0.9.7-era turns carry ≈ 200 more thinking tokens each, so a post mid-band phase
is smaller in lines than a pre one).

Where the size comes from: the slices. 181 (the desktop extension stood up from nothing) is 14
phases of 1,250–1,920 lines each, 8 blocked; 182, 184, 186 and 187 carry root phases of 580–1,020
lines against a pre-era root maximum of 332 in the sample; the extension phases' test files alone
run 300–490 lines each. The plan sections asking for those phases grew 21 % (2.1 k → 2.6 k chars
median) while the phases delivered 3.7× the lines — the plan-writer's "PR-sized" rule is being
read the same way, on bigger asks.

## 3. The reviewer runs mutations as before; its impact tag moved

Reviewer round-1 sessions, from the transcripts (`turn_profile.py`'s shell-op classes; a
"mutation session" edited a non-record file *and* ran a test — a floor, since most shell edits
resolve to no target):

| | pre (107) | post (122) |
|---|---:|---:|
| mutation sessions | 43 (40 %) | 49 (40 %) |
| … in blocked phases | 6/13 | 16/28 |
| … in coverage-gap-blocked phases | 1/1 | 13/18 |
| test runs per session | 0.68 | 0.95 |
| turns median · duration median | 22 · 405 s | 27 · 486 s |
| reviews mentioning a mutation | 57/127 (45 %)† | 77/122 (63 %) |
| model · effort | opus-5 · xhigh | opus-5 · xhigh |
| dispatch text | gate paragraph incl. "a mutation that proves a test actually catches" — unchanged since 2026-08-11 | same |

† review files, 149–153 included. The turns and test runs track the larger diffs; the practice
did not change. A read of the 20 blocking coverage-gap reviews (168 P2 and the 19 post) finds a
mutation actually run in all 20 ("adding `env.name` to the tuple leaves the suite green"), a named
criterion in 19, in-phase in 18; and three signed-off pre-era reviews (149 P1, 160 P4, 164 P4)
ran two to three mutations each, caught by the tests.

**What did move is the impact tag on the coverage-gap anchor.** Pre: 1 blocking, 7 advisory
Minor. Post: 19 blocking Major, 14 advisory (8 Minor, 6 Major). The pre-era advisory ones are the
same shape as the post-era blocking ones — a named criterion whose test survives a mutation:
162 P6 "V20's verbatim-307 guarantee is witnessed by no test", 163 P1 "op=create … squarely
inside V01/V02", 170 P6 "deleting `await self.tick_once()` leaves all 29 tests green, so V04's
renewal …" — all advisory Minor. Rule 6 of `code-reviewer.md` makes missing coverage of new
behaviour a Major and a mutation-surviving criterion a blocking anchor, so the post era is the
literal reading and the pre era the lenient one. No cause found: the reviewer's text, dispatch,
model and effort are identical across the step; the prefix trim (0.9.6 auto-memory and skills,
0.9.8 MCP and slash commands) is the only reviewer-side change in the window, and the narration
shows no memory use on either side (the operator's "close test gaps" close-out memory dates from
2026-08-30, after the pre era). At equal size the tag shift costs nothing extra — the 100–300-line
bin blocks 4 of 20 pre and 4 of 21 post — it changes which anchor the block carries.

## 4. The writer: reads less, tests the same

| writer round-1 sessions | pre (106) | post (122) |
|---|---:|---:|
| opened verification.json | 70 (66 %) | 0 |
| read the plan whole | 104 (98 %) | 3 (2 %) |
| test-line share of the r1 diff, median | 0.7 | 0.6 |
| test-file edits per root phase, median | 2 | 3.5 |
| root phases with no test-file edit | 14/53 | 11/54 |
| extension phases with no test-file edit | 1/7 | 25/42 |
| turns median · duration median | 39.5 · 355 s | 39 · 527 s |

The reads are the digest by design (0.9.7): the acceptance criteria arrive in the prompt under
"Acceptance criteria (verification.json — the test phase checks them off, not you)". Test volume
did not fall. The extension zero-test phases are 180's surface work (11 of its 14) — one of them
blocked, none for coverage — not the coverage-gap population.

Six transcripts read (pre 164 P2, 169 P3, 170 P1; post 173 P2, 187 P2, 190 P1): all three pre
writers opened verification.json, one (170 P1) filtered it by phase and wrote the ids into its
test file, two never referred to it again; both eras narrate test choice by scenario ("pinning the
outcome", "the re-delivered survivor"), never by criterion; the one revert-and-confirm-fail check
is in the post group (190 P1). In both post blocking gaps the writer believed an existing test
covered the case — 173 P2's recorder tests proved the callable fired, not the envelope emitted;
190 P1's reproduction pinned the interleaving but not that the lifespan closes the window — which
is what a mutation finds on a large diff. The within-pre contrast is direction only: writers that
opened verification.json blocked 4/60, those that did not 4/26.

## 5. What the blocking bought

19 of the 20 coverage-gap fix rounds changed tests only (184 P1 also extracted a guard); none was
refuted. The traced-defect anchor, `repro-trace`, fell 9 → 5 on more phases. So the rounds bought
pinned criteria, not corrected code: ≈ $3.80 each (#720's writer-fix + re-review medians), ≈ $4 a
slice at the post-era rate.

## 6. What follows

- **No plugin change is indicated.** Neither 0.9.6 nor 0.9.7 nor 0.9.8 shows in the record: the
  reviewer's practice is flat, the writer's test volume is flat, and size standardization closes
  the gap. Re-adding the whole-plan read or a verification.json read for the writer is not
  supported — two of three pre writers read the criteria and did not use them.
- **The lever, if the operator wants fewer rounds, is phase size at plan time.** Phases of 600+
  lines block at 12/24 (50 %) against 4/48 under 300; the plan-reviewer's phase-sizing check is
  where that is decided, and it is a plan-shape question (181's 14 greenfield phases), not a run
  question.
- **The digest's criteria banner** ("the test phase checks them off, not you") is not shown to
  steer anyone — no writer cites it — so rewording it to "pin the ones your phase delivers" is a
  cheap hygiene edit, not a fix; one session in three (170 P1) is the whole evidence that a writer
  who reads the criteria writes to them.
- **The impact-tag shift** is worth one line in the reviewer's record if it recurs on small
  phases: it is the literal reading of rule 6, and the operator's disposition of test-only fix
  rounds decides whether blocking is the right tag for a mutation-surviving criterion.
- **Re-read** when 195 closes and after the next slices without a greenfield component:
  `python3 docs/research/tools/r1_blocking_readout.py` (`--per-slice` for the card's table).
