## Core results

1. **Success rate, WebArena (gpt-4-0613, temp 0).** AWM 35.5 total SR vs BrowserGym 23.5 (+12.0
   absolute, +51.1 % relative) and vs BrowserGym_ax-tree 15.0 (+20.5 absolute); per site +11.8–30.7
   over ax-tree. AWM also beats SteP (33.0), which uses **14 human-expert-written** workflows, by
   7.6 % relative (§3.1, Table 1; the intro says 7.9 % — an internal inconsistency).

2. **Steps taken — the efficiency result.** Same table: BrowserGym_ax-tree needs **7.9 steps** per
   task, AWM **5.9** (−2.0, ≈ −25 %) while scoring 20.5 points higher. Against AutoEval (46.7 steps,
   spent on evaluate-and-refine loops) AWM is **40.8 steps** fewer. The gain is not bought with a
   longer trajectory; the trajectory gets *shorter*. This is the paper's only step measurement —
   Mind2Web tasks have a fixed step count, so no step reduction is reported there.

3. **Learning curve: tens of examples suffice.** Cumulative SR over the online stream rises steeply
   between 0 and ~40 examples ("acquiring the most essential workflows") then plateaus near its
   final level (§3.1). The gap over a non-adapting agent reaches **22.5 points** after "only tens of
   examples" (§1).

4. **Mind2Web, offline induction (gpt-3.5-turbo, gpt-4).** Prose reports +4.0–8.9 % relative and
   +0.4–2.8 absolute over Synapse and MindAct, the gain coming mainly from **element accuracy
   (+5.0–9.0)** (§3.2). The main results table did not survive the LaTeX→Markdown conversion; the
   ablation table gives cross-task numbers: MindAct 41.6 elem-acc / 60.6 action-F1 / 36.2 step-SR /
   2.0 task-SR → AWM 50.6 / 57.3 / 45.1 / 4.8 (§4.2). 36.2 → 45.1 is the abstract's "24.6 % relative".

5. **Abstraction beats retrieved concrete examples.** Against Synapse, which retrieves whole
   relevant training trajectories, AWM gains **+5.0 element accuracy, +4.0 step SR** (§3.2). The
   authors attribute this to abstracting example-specific values into slots ("dry cat food" →
   "{product-name}"), which biases element selection less than full examples do.

6. **Generalisation widens with the distribution gap.** Mind2Web step SR over MindAct: cross-task
   +7.4–8.9, cross-website +3.6–3.8, cross-domain **+14.0–16.9** absolute (§3.2); AWM_online pulls
   further ahead of AWM_offline as the gap widens. On a WebArena **cross-template subset** (one
   example per task template, so no two tests share a canonical trajectory) AWM is still best
   overall and on every split — 33.2 vs ax-tree 20.5, SteP 32.1 (§3.1, Table 2). The gains are not
   template memorisation.

7. **The memory is small and heavily used.** Quality analysis (§8.3, Table 3): **7.4 workflows**
   (WebArena) / 7.3 (Mind2Web) per website group; **utility rate 0.94 / 0.91** (share of test
   examples that use a workflow); function overlap 0.08 / 0.20; step coverage 0.40 on Mind2Web.
   Workflows are grouped **per website** deliberately, "to maintain a small collection of workflows
   that are nonetheless relevant to the test tasks" (§3 preamble); "fewer workflows is better" is
   the metric's stated direction.

8. **Failure modes, all measured.**
   - *Wrong workflows.* AWM_online induces from its own predictions, which "are not always correct,
     thus can lead to incorrect workflows that degrade model performance" (§3.2). The guard is an LM
     evaluator emitting a binary success label; only trajectories labelled 1 become workflows.
   - *Stale / mismatched workflows.* Offline workflows from a train distribution unlike test (Amazon
     shopping vs Amazon careers) hurt, and mixing sets is **not additive**: AWM_off+on scores
     *between* offline and online on all three splits, offline workflows appearing to "impair the
     generative quality and utility efficacy of online workflows" (§10).
   - *Over-following.* AWM's action F1 is **below MindAct** (57.3 vs 60.6): workflows push actions
     "not always relevant to the particular environment state at hand"; agents "encounter some
     challenges in identifying places to diverge from the workflow guidelines" (§3.2).
   - *More grounding detail ≠ better.* Adding filtered HTML to each step's NL state description made
     everything worse (step SR 34.6 → 32.9, task SR 2.8 → 2.0; §4.3). Conjectured causes: longer
     context, and the filter missing all correct elements **47 %** of the time.

9. **Format and induction method barely matter.** Text vs program format: +0.6 elem acc, +0.3 step
   SR, −1.2 task SR — "no substantial performance variance" (§4.2). Rule-based induction (dedupe by
   action sequence, drop invalid actions) vs LM-based: WebArena 35.6 vs 35.5 SR but **6.3 vs 5.9
   steps** — the LM version is finer-grained and avoids "unnecessary steps"; on Mind2Web LM-based is
   +2.8 (§4.1). Wrapping workflows as callable *actions* rather than memory gives +1.3 step SR, but
   agents call them in only **18.5 %** of tasks and pre-set sequences break when an intermediate
   state must be observed (flight-booking pop-up airports; §5).

## Method and setting

- **Task type:** web navigation (click/type over accessibility trees), not code. WebArena: 812
  execution-checked tasks, 5 sites. Mind2Web: 1000+ tasks, 200+ domains, step-wise scoring against
  one annotated gold trajectory.
- **Horizon:** very short — ~6–8 steps per task for AWM/BrowserGym, 46.7 for the refine-loop
  baseline. A step is one observe→act pair, not a Claude-Code-style tool loop.
- **Models:** gpt-4-0613 (WebArena); gpt-3.5-turbo and gpt-4 (Mind2Web), temp 0. The *same* model
  does induction and action generation. **No Claude, no open-weights model.**
- **Nothing is trained.** Pure prompting: memory is "a system prompt or auxiliary information in the
  main prompt context" (fn. 1). Workflows are appended wholesale — **no retrieval step**; the
  per-website grouping is what keeps the block small.
- **A workflow item** = an NL goal description + a step list, each step being (NL state description,
  the agent's reasoning, the executable action), with example-specific values replaced by slots.
  Segmented on double newlines in the induction output. Token size is never reported — only count.
- **Two regimes:** *offline* — concatenate a site's training examples into one prompt, induce once,
  use frozen; *online* — stream test queries, LM-evaluate each finished trajectory, induce from the
  successes, grow the memory for the next query. Online needs no annotations.
- **Baselines:** BrowserGym (SOTA autonomous), SteP (14 hand-written workflows), AutoEval
  (evaluate-and-refine), MindAct, Synapse (retrieved full trajectories).

## Relevance to P1–P4

**P1 — context is the cost.** No token or money accounting anywhere; the paper bears on P1 only
through step count — 25 % fewer observe-act steps for a memory of ~7 items. Each of their steps
carries a fresh page observation, so fewer steps means less accumulated context, the same shape as
our per-turn growth. No cache, no 33k prefix, no long tool loop: no cost ratio transfers.

**P2 — sessions grow; the longest dominate.** Result 2 is the closest thing here to "same task,
fewer turns": higher success on a shorter trajectory, and against AutoEval an order of magnitude
(46.7 → 5.9) because the memory removes discover-then-refine. Direction transfers to our 14–65
orientation turns before the first edit; magnitude does not — their trajectories are ~8 steps and
their steps are environment actions, not repo reads.

**P3 — every session rebuilds the same picture.** The paper's exact target: agents "solve each task
separately... unable to adapt over time" (§1). Measured answer: a small, abstract, per-site text
memory recovers most of what a fresh agent lacks, ≈ 40 examples suffice to induce it, and 91–94 % of
tasks use it. Transfer gap: their re-learned knowledge is a click sequence on a *frozen* site; ours
is CLI argument shapes and procedures against a changing repo, and the paper says nothing about
invalidating a workflow when the environment moves.

**P4 — what curated context costs in grounding.** Three measured data points. (a) Abstraction *won*
over concrete examples (+4.0 step SR vs Synapse) — compressing into slot-filled routines gained
grounding rather than losing it. (b) Over-following is real and quantified: action F1 3.3 points
below MindAct, from applying the routine where the state does not warrant it. (c) Adding *more*
grounding detail (HTML alongside NL) made everything worse. Their step-SR/action-F1 split is the
analogue of our blocking-finding vs refuted-finding instruments: watch for "did the prescribed thing
in the wrong place", not for a fall in overall success.

## Interventions this paper supports

- **A per-project workflow-memory file every dispatch prompt points at**, injected by the dispatch
  script rather than read as one more file (results 1, 2, 7: a ≈ 7-item text memory raised SR and
  cut steps 25 %; memory is literally auxiliary prompt context). Expected: fewer orientation turns
  before the first edit. Nothing measured is lost at this size — but see over-following.
- **Keep it per-project and to single digits of items** (§3 preamble; Table 3: 7.3–7.4 items,
  overlap 0.08, utility 0.91–0.94, "fewer workflows is better"). A cross-project global memory is
  precisely the case their grouping avoids.
- **Write items as abstract sub-routines with slots, not transcripts of a past run** (result 5, §4.1:
  beats retrieved full examples by +4.0 step SR and rule-deduplicated real trajectories by 0.4
  steps). Concretely: "run the gate for component {name}" with the argument shape, not one phase's
  bash history.
- **Prose or code — pick either** (§4.2, ±0.6). Cheapest to maintain wins.
- **Induce online, from *verified* successes** (§2.3, §3.2): online avoids the train/test gap and
  generalises better as the gap widens, but only because an evaluator gates what becomes a workflow.
  Our gate is deterministic — a stronger filter than their LM judge. Hook: after a green phase,
  distil any repeated friction into a one-line item.
- **Do not merge a legacy/hand-written set with an induced one** (§10: off+on landed *between* the
  two, never above; offline degraded online). One source of truth per memory file.
- **Do not paste raw tool output into the items** (§4.3: NL state descriptions alone beat NL +
  filtered HTML on every metric). Say what state to expect, not the output that proves it.
- **Prefer memory over new callable wrappers** (§5: workflow-actions used in only 18.5 % of tasks
  and brittle when an intermediate state matters). A described routine the agent may deviate from is
  the robust end of this design; a wrapper freezing an argument sequence is the brittle end.
- **Instrument for over-following** (result 8c): if a workflow memory ships, watch refuted-finding
  rate and rework share for the specific failure of following the routine where it did not apply.

## Applicability caveats

- **No Claude, and no long-context model** (gpt-4-0613 / gpt-3.5-turbo, 2024). Their agents are
  context-starved in a way ours are not; part of AWM's gain may be supplying what a modern model
  would find by reading.
- **Web navigation, not code.** No repo, diff, test gate or compiler. The nearest split to us is
  GitLab (31.8 SR) — still click-level navigation.
- **Horizon mismatch.** 6–8 steps vs our 20–200 turns; the 2.0-step saving is 25 % of *their*
  trajectory. Nothing says whether the benefit scales, saturates or inverts at our length.
- **Static environments.** Benchmark sites do not change between induction and use, so the paper
  cannot speak to staleness — the likeliest failure mode for a repo-attached file. Its only
  staleness evidence is distributional (§3.2, §10), not "the CLI changed its flags".
- **No token accounting.** Steps are the only efficiency metric and item size is never reported, so
  "keep it small" is grounded in item *count* and overlap, not tokens.
- **Benchmark quirks.** WebArena instantiates many tasks from shared templates (the cross-template
  subset, Table 2, is the number to trust); Mind2Web scores against a single gold trajectory, so a
  valid alternative route scores zero. Baselines are 2024-era.

## Briefing check

The note — "what workflow memory buys on recurring frictions" — is supported. Carrying results:
**+12.0 absolute / +51.1 % relative SR with 7.9 → 5.9 steps** (Table 1: a higher score on a
*shorter* trajectory), and **7.4 items per site at 0.94 utility rate** (Table 3: a memory smaller
than one of our design docs, hit by 94 % of tasks). The learning curve (most of the gain inside ~40
examples) says the induction cost is small — relevant to filling such a file per project.

What the note under-specifies: the buy is measured only as steps and success, never as tokens or
money, and only on ~8-step web tasks — it supports the *direction* for our orientation reads but
gives no size estimate for a 20–200-turn coding session. And it carries no cost side, where the
paper measures two: an action-F1 drop from over-following (57.3 vs 60.6) and outright degradation
from workflows induced off unverified trajectories or merged from a mismatched source (§10).
"Correct and small" is load-bearing in the paper's own results, not a stylistic preference.
