## Core results

1. **MAST: 14 failure modes in 3 categories, with prevalence over 1642 annotated traces**
   (Figure 1 caption; per-mode numbers stated in §4 FC1/FC2/FC3; Appendix 7 has the definitions).
   The percentages are shares of *all annotated failure instances*, not per-trace rates — they sum to
   ≈ 100 %.

   | FC | Mode | % |
   |:---|:---|--:|
   | **FC1 System design issues (≈ 44.2 %)** | 1.1 Disobey task specification | 11.8 |
   | | 1.2 Disobey role specification | 1.5 |
   | | 1.3 Step repetition | 15.7 |
   | | 1.4 Loss of conversation history | 2.80 |
   | | 1.5 Unaware of termination conditions | 12.4 |
   | **FC2 Inter-agent misalignment (≈ 32.4 %)** | 2.1 Conversation reset | 2.20 |
   | | 2.2 Fail to ask for clarification | 6.80 |
   | | 2.3 Task derailment | 7.40 |
   | | 2.4 Information withholding | 0.85 |
   | | 2.5 Ignored other agent's input | 1.90 |
   | | 2.6 Reasoning–action mismatch | 13.2 |
   | **FC3 Task verification (≈ 23.5 %)** | 3.1 Premature termination | 6.20 |
   | | 3.2 No or incomplete verification | 8.20 |
   | | 3.3 Incorrect verification | 9.10 |

   Definitions that matter here (Appendix 7): **2.4** = holding data/insight that would change another
   agent's decision; **2.5** = disregarding input received; **2.3** = drift from the asked objective;
   **3.1** = ending before the necessary information has been exchanged or the objective met;
   **3.3** = failing to cross-check crucial information *during* iteration; **1.4** = unexpected
   truncation/reversion to an earlier state.

2. **Frequency is not fatality.** On the subset where actual task success is known (Appendix 16.1,
   ChatDev n = 10 success / 20 fail, MetaGPT n = 12 / 18), **1.5 Unaware of termination conditions**
   and **2.4 Information withholding** appear *almost exclusively in failed runs* (both 0.0 % in
   successful traces of both frameworks; 1.5 at 10.0 % / 11.1 % and 2.4 at 5.0 % / 5.6 % in failed
   traces), while **3.2** and **3.3** occur at similar rates in successful and failed runs (3.3:
   ChatDev 20.0 % success vs 25.0 % fail; MetaGPT 16.7 % vs 27.8 %). Authors' reading: some modes are
   critical bugs, verification failures are a *systemic weakness that a passing run still carries*.
   Sample sizes are tiny — treat as directional.

3. **The obvious fixes give single-digit gains and are not universal** (Appendix 14, Table
   `tab:ag2-chatdev-accuracies`; 6 repetitions for AG2, Wilcoxon tests).
   - AG2 MathChat on 200 GSM-Plus problems, **GPT-4**: baseline 84.75 ± 1.94 → improved prompt (added
     a structured VERIFICATION section) **89.75 ± 1.44**; → new topology (Problem-Solver / Coder /
     Verifier, only the Verifier may terminate) **85.50 ± 1.18**, *p = 0.4, not significant*.
   - Same, **GPT-4o**: 84.25 ± 1.86 → prompt 89.00 ± 1.38; → topology 88.83 ± 1.51; both p = 0.03.
     So the *same* topology change is worthless on one model and significant on another.
   - ChatDev on ProgramDev-v0 (32 tasks): baseline 25.0 → role-spec prompt fix **34.4 (+9.4 pts)** →
     cyclic-graph topology, terminating only when the CTO confirms all reviews satisfied,
     **40.6 (+15.6 pts)**. On HumanEval the same interventions move 89.6 → 90.3 → 91.5 (+1.9 max).
   - Authors' own summary (§6, Appendix 14.3): max improvement 15.6 %, "not all failure modes are
     resolved, and task completion rates still remain low"; achieving reliability "may require
     combinatorial changes ranging from agent system organization to model level improvements."

4. **Prompt vs topology: the paper's two claims disagree.** Appendix 14.3 concludes "topology-based
   changes are more effective than prompt-based changes for both systems" — that claim is about
   *MAST failure-mode counts* from the LLM annotator (Figures 10–11), not accuracy; on accuracy the
   AG2/GPT-4 column shows prompt > topology. The +15.6 pt ChatDev result is also described two ways:
   "adding a high-level task objective verification step" (§1) and a DAG→cyclic topology change with
   CTO-gated termination (Appendix 14.2). One intervention, two descriptions.

5. **Failure is the norm:** 41 % – 86.7 % failure rates across the 7 open-source MAS studied
   (§1, Figure 5).

6. **Model and architecture each reshape the failure profile, and neither fixes FC3** (§5.1, §12).
   In MetaGPT on ProgramDev-v2, GPT-4o shows **39 % fewer FC1 failures** than Claude-3.7-Sonnet and
   fewer FC2; both stay high on FC3. With GPT-4o fixed, MetaGPT has **60–68 % fewer FC1 and FC2** than
   ChatDev but **1.56× more FC3** — attributed to ChatDev's explicit review/test phases. Signatures
   differ per framework: AppWorld (star, no predefined workflow) is dominated by 3.1; OpenManus by
   1.3; HyperAgent by 1.3 and 3.3.

7. **Verifiers under-perform their instructions.** From the grounded-theory pass (§4 FC3): "many
   existing verifiers perform only superficial checks, **despite being prompted to perform thorough
   verification**" — e.g. checking that code compiles or that no `TODO`s remain. The ChatDev chess
   program passes compilation checks and still violates the game rules. Insight 3: sole reliance on
   final-stage low-level checks is inadequate; multi-level verification (low-level correctness *and*
   high-level objective) is needed.

8. **Insight 2 (a warning about the intuitive fix):** communication-protocol and context solutions are
   "often insufficient" for FC2, because the observed errors occur *between agents in the same
   framework already sharing a natural-language channel*. The authors frame this as a collapse of
   theory-of-mind — agents fail to model what the other needs to know — and conjecture it needs
   message-content structure plus model-level training, not a wire format (MCP and A2A are named as
   not addressing it). Conjecture, not measured.

## Method and setting (what was actually built/tested)

Observational failure study, not a systems benchmark. 1642 execution traces from **7 open-source MAS
frameworks** (MetaGPT, ChatDev, HyperAgent, AppWorld, AG2/AutoGen, Magentic-One, OpenManus) on
**coding (ProgramDev / ProgramDev-v2 / SWE-Bench Lite / HumanEval), math (GSM-Plus, OlympiadBench),
general agent (GAIA, AppWorld Test-C, MMLU)**. Models: **GPT-4, GPT-4o, GPT-4o-mini, Claude-3.7-Sonnet,
Qwen2.5-Coder-32B, CodeLlama-7b** (Table 1). Traces average **>15,000 lines** each.

Taxonomy built by Grounded Theory over 150 traces / 6 experts (>20 h each), refined over 3
inter-annotator rounds to **κ = 0.88**; generalisation checked on 2 unseen MAS + 2 unseen benchmarks at
**κ = 0.79**. Scaled annotation is **LLM-as-a-judge (OpenAI o1, few-shot)**: accuracy 0.94, recall 0.77,
precision 0.833, F1 0.80, **κ = 0.77** (Table 2) — ~23 % of failures missed by the annotator that
produced most of the corpus. Category correlations 0.17–0.32; mode-level up to 0.63, which the authors
admit may conflate root causes. Nothing trained or fine-tuned; interventions are prompt edits and
workflow rewiring. Shipped as `pip install agentdash`. Annotation cost $1.8/trace average (Appendix 17).

**No token, latency or dollar cost of the MAS runs themselves is reported anywhere.** No single-agent
baseline is run; the "MAS gains are minimal" premise is cited from others (Agentless, *AI Agents
That Matter*), not measured here.

## Relevance to P1–P4

**P1 — Context is the cost.** The paper bears on this only indirectly and reports no token economics.
The one quantitative hook: **1.3 step repetition is the single largest failure mode at 15.7 %** —
unnecessary reiteration of completed steps is the failure-shaped version of our re-reading problem,
and it is the dominant mode in OpenManus and HyperAgent. But the paper counts it as a correctness
failure, never prices it. Do not cite this paper for cost.

**P3 — Every session rebuilds the same picture.** Strongest bearing, with a caution. Four modes
describe what goes wrong at a hand-off: 2.4 information withholding (0.85 %, near-exclusively in
failed runs), 2.5 ignored other agent's input (1.90 %), 1.4 loss of conversation history (2.80 %),
2.1 conversation reset (2.20 %). The canonical example (Figure 3) is a service agent that knows the
API's username-format requirement, never states it, and a supervisor that never asks — repeated failed
logins, task lost. The HyperAgent example (Appendix 20) is closer to our shape: the **Navigator works
out a candidate fix and returns only the code snippets to the Planner**, dropping its own conclusion.
Caution: Insight 2 says protocol and context fixes are "often insufficient" for exactly this category,
so a richer hand-off format is predicted to dent FC2, not eliminate it.

**P4 — We do not know what smaller reads cost in grounding.** The paper never varies what an agent
reads, so it cannot answer this. What it gives P4 is a warning about our instruments: FC3 is 23.5 % of
failures, and **3.2/3.3 appear at roughly equal rates in successful and failed traces** — a completed
task is not evidence that verification worked. With "verifiers perform only superficial checks despite
being prompted to perform thorough verification", a green gate plus a reviewer saying "looks fine" is
a weak instrument for detecting grounding loss. A curated-context experiment needs an outcome measure
that is not the reviewer's own verdict.

**P2** — no bearing (no length, growth or truncation economics; 1.4 is about unexpected truncation as
a correctness event, in frameworks that manage their own history).

## Interventions this paper supports

- **Give every sub-agent return a "constraints discovered" field, separate from the conclusion.**
  Rests on FM-2.4 and its two examples (withheld username format, Figure 3; the Navigator that returned
  snippets but not its candidate fix). Direction: removes a mode that is rare (0.85 %) but appears
  almost only in failed runs. Loses: longer returns, and the returning agent must judge what the parent
  depends on — the theory-of-mind the paper says models are weak at (Insight 2), so expect partial
  compliance.
- **Make "underspecified — I could not answer X" a first-class return value.** Rests on FM-2.2
  (6.80 %): agents proceed on assumptions instead of asking. Our sub-agents cannot ask mid-flight, so
  the return is the only channel; without a slot for it, they will guess. Loses: round-trips, and a
  parent that must handle the case.
- **Require the return to mark each claim verified vs asserted.** Rests on FM-3.1's example (the
  HyperAgent Editor reported "the modification has been successfully applied" when it had not; the
  Executor found out later) and FM-2.6 reasoning–action mismatch (13.2 %, second-largest mode).
  Catches the confident-but-unexecuted return; costs a few lines of contract.
- **Make the parent's acceptance explicit (accepted / contradicted / superseded).** Rests on FM-2.5
  (1.90 %) and its example: an agent acknowledges a peer's correct solution, misses that it contradicts
  its own, and proceeds with its own answer. Turns a silent discard into a visible one. Loses: little.
- **Re-state the asked question in the return and check the answer against it.** Rests on FM-2.3
  (7.40 %) and FM-1.1 (11.8 %). Cheap, and it is the failure a fresh-context sub-agent is most exposed
  to, since it cannot see the parent's objective drift.
- **Verify at the objective level, not only the gate level, and during iteration rather than at the
  end.** Rests on Insight 3, the ChatDev chess example, and the +15.6 pt result, whose mechanism was a
  termination condition owned by a role that checks *all reviews are satisfied*. Largest single gain in
  the paper. Loses: rounds — it added a cycle to a DAG with an iteration cutoff, which is spend.
- **Prefer fixing role/termination specifications over rewiring topology if only one can be tried.**
  The AG2 prompt fix was significant on both GPT-4 and GPT-4o; the topology change on GPT-4o only
  (p = 0.03 vs p = 0.4). Both are single-digit-to-15-point, never transformative.
- **Do not expect a hand-off format alone to fix coordination.** Insight 2 names MCP/A2A-style
  standardisation as not addressing the observed FC2 errors, which occur over natural language inside
  one framework. Budget the return contract as partial mitigation.

## Applicability caveats

- **No Claude Opus, and Claude comes off worse where it appears.** Claude-3.7-Sonnet is the only Claude
  tested (MetaGPT, AG2) and shows 39 % *more* FC1 failures than GPT-4o. Nothing characterises a frontier
  Claude model at high effort, and the AG2 result (same topology change, opposite verdict on GPT-4 vs
  GPT-4o) is direct evidence that these interventions do not transfer across models.
- **Task type is half-matched.** Coding tasks are ProgramDev / HumanEval greenfield toys ("a two-player
  chess game", "a BMI calculator") plus SWE-Bench Lite bug fixes — not multi-phase changes to an
  existing repo with a plan file, a deterministic gate and a review loop. Much of the corpus is math/QA.
- **The frameworks are not our shape.** Chat-topology MAS with a shared conversation (assembly line,
  hierarchical, star). Several modes (2.1 reset, 1.4 truncation, 1.5 termination) are artefacts of a
  shared growing transcript our fresh-session/files-are-memory design does not have. Conversely we are
  *more* exposed to 2.4/2.3/3.1 because there is no shared transcript to fall back on — untested here.
- **Prevalence numbers are annotator output, not ground truth.** ~1400 of 1642 traces labelled by o1
  few-shot at κ = 0.77 / recall 0.77 — one in four failures missed — with mode correlations up to 0.63
  the authors say may conflate root causes. The rarest modes (2.4 at 0.85 %, 1.2 at 1.5 %) are least
  safe to read as rates.
- **The fatality finding rests on ~60 traces** (10/20 and 12/18 per framework). Directional only.
- **No cost, latency or token counts** for the MAS runs. Nothing here prices an intervention.
- **Nothing is trained**, so all of it is implementable in our surface — but all of it sits in the
  "tactical approaches" bucket the authors themselves report as inconsistent.

## Briefing check

The S4 note asks for three things: *the task properties under which coordination pays or costs*, *the
failure classes that matter*, and *the token economics practitioners report*. The paper delivers one
of the three.

- **Failure classes — fully supported; this is why to keep the paper.** MAST is a catalogue of failure
  classes with prevalences, validated at κ = 0.88 (human) / κ = 0.77 (annotator), generalising to unseen
  systems at κ = 0.79, and it separates fatal modes from systemic ones ("1.5 Unaware of Termination
  Conditions and 2.4 Information Withholding appear almost exclusively in failed runs", Appendix 16.1).
- **Task properties under which coordination pays or costs — not supported.** No single-agent baseline,
  no controlled comparison of decomposing against continuing; §1's "MAS gains are minimal" premise is a
  citation to Agentless and *AI Agents That Matter*, not a result here. The one architecture comparison
  (MetaGPT vs ChatDev, §12) varies two whole frameworks at once and reports failure-mode shares, not
  whether decomposing paid. Q3's core question must come from Kim et al. 2512.08296.
- **Token economics — not supported at all.** The only dollar figure is $1.8 average to *annotate* a
  trace with o1 (Appendix 17). If the note implied this paper carries S4's economics half, that is an
  overstatement.
- Correct if leaned on: the headline "+9.4 %" and "+15.6 %" are **percentage-point gains on a 32-task
  custom benchmark (ProgramDev-v0)** off a 25.0 % baseline — 8 → 11 and 8 → 13 tasks. On HumanEval the
  same two interventions gain 0.7 and 1.9 points. Small, benchmark-dependent, model-dependent — the
  authors' own conclusion.
