## Core results

1. **A constant-size, prompt-resident "context map" beats every context-management baseline on
   repeated queries over the same external context.** Abstract: +6.3–34.0 % over strong baselines,
   with 93–145 fewer iterations and 1.7–5.8× lower cost than ACE (the SOTA prompt-learning
   framework). §Main Results, on OOLONG: PEEK beats ACE by **+7.8–15.0 %**; on CL-bench by **+6.0 %
   solving rate and +9.9 % rubric accuracy**. Base LM for the main table is GPT-5-mini.

2. **The map is small and its exact size barely matters.** §Ablations: hard budget **B = 1024
   tokens**, fixed across every context and every experiment, chosen "without tuning". Varying
   B ∈ {512, 1024, 2048} — a 4× range — gives average **+15.5 % at 512** and **+20.3 % at 2048** over
   base RLM. Authors' conclusion: "the presence of a context map matters more than its exact size."

3. **Even a frozen map works; maintenance adds ~10 %.** §Ablations (1): disabling eviction and
   freezing the map once it hits B still "yields large gains over the base RLM"; the full policy adds
   **+10.2 % on average** on top. §Ablations (2): collapsing the Distiller and Cartographer into one
   LLM call costs **−7.7 % on average** — separating diagnosis from edit planning is load-bearing.
   Map updates ran for only **m ≤ 4** queries in all reported variants (evolution can be frozen after
   as few as m = 1), while ACE ran fully online on every query and still lost.

4. **Iterations do not go up, and maintenance is cheap.** §Fine-Grained Cost Analysis: PEEK's total
   iteration count is at or below base RLM on 3 of 4 benchmarks (**378 vs 394; 398 vs 496; 269 vs
   277**). Maintenance cost is **$0.31 / $0.22 / $0.43 / $0.31** across the four benchmarks =
   **6.2–17.9 %** of PEEK's totals ($5.10 / $2.30 / $2.39 / $1.88), with the **Distiller ≈ two-thirds**
   of it (trajectory analysis costs more than edit planning). On AGNews execution cost alone falls
   **6.8 %** ($2.09 vs $2.24) while accuracy gains **+22.9 points**.

5. **Carrying the trajectory instead is the expensive failure.** §Fine-Grained Cost Analysis, Shared
   Chat: input tokens inflate **10.1× (2.85M → 28.76M)** on TREC-Q-coarse for **+1.75 %** accuracy;
   on CL-bench **9.0× (2.72M → 24.39M)** while solve rate **drops 14.0 % → 12.0 %**. Iterations rise
   to **748** (OOLONG) and **301** (CL-bench). ACE's playbook induces verbosity: **12.45M output
   tokens** and **$29.42** on TREC-Q-coarse = 5.9× base RLM, 5.8× PEEK.

6. **Cheap alternatives buy less orientation.** RAG and Compaction Agent (MemAgent) use 490–539
   iterations for modest gains and trail PEEK by **6.3–28.0 %** (OOLONG) and **6.0–12.0 %** solving
   rate (CL-bench), even where they cost slightly less ($1.43 and $1.38 vs base RLM's $1.57 on
   CL-bench). The authors' reading: "the bottleneck is not access cost but how productively the agent
   uses its iterations."

7. **Generalizes across LMs and to a production coding agent.** §Generalization: unchanged algorithm
   and prompts under **GPT-5.5** (run costs $148.84 base RLM / $923.44 +ACE / $487.39 +PEEK),
   **Qwen3-Coder-Next-FP8**, and with **OpenAI Codex CLI** as the backbone agent, where "the gains do
   not disappear either and are in fact even larger". No per-condition numbers survive the table loss.

8. **Negative results — what must *not* go in the map** (§Things We Tried, average improvement over
   base RLM on an OOLONG subset): raw **first 1,024 tokens** of the context **+0.73 %**; **retrieval
   on the agent's latest sub-goal** **+4.92 %** (and "severely hurts" on some contexts by cluttering
   working memory); **retrieval over an ACE-style playbook** **+0.73 %**; **runtime feedback** that
   rewrites the whole map after every root-LM iteration **−14.86 %**; **behavioral instructions**
   ("do not take shortcuts") **+5.65 %** at noticeably higher cost.

## Method and setting (what was actually built/tested)

**The artefact.** Five sections, all starting as bare headers (the map may even start blank; authors
deliberately refuse to hand-craft or pre-populate entries):

- `Context Roadmap` (default) — abbreviated index of what the external context contains and where.
  Example entry, verbatim: `[cr-00001] Single text block (~38k chars) containing 388 records of the
  form…`
- `Context Understanding` (default) — higher-level description: key entities, concepts, relationships.
- `Domain Constants` (optional) — exact values or enumerated sets.
- `Reusable Results` (optional) — derived computations.
- `Parsing Schema` (optional) — format and delimiter structure.

Every item carries a **stable unique ID**, which is what makes updates local and traceable.
Deliberately excluded: the conversation trajectory, task-specific rules/strategies, raw context
excerpts, behavioural instructions.

**How it is built and refreshed.** By models, from execution signals, *after* a run completes — never
by hand, never mid-run. Three modules: a **Distiller** reads the finished trajectory plus the current
map and emits (a) a diagnosis of how the agent spent its iterations — orientation vs task-specific
work, where it stalled or succeeded, (b) per-item tags `helpful | harmful | neutral | stale`, and
(c) cache candidates, keeping only transferable contextual knowledge and discarding task-specific
rules. It runs **without ground truth or a final answer**. A **Cartographer** turns that into
Add/Delete/Replace edits against item IDs, deduplicating against existing entries. An **Evictor**
enforces B after each update, evicting in ascending Distiller-accumulated score, ties broken
oldest-first, and in the inverse of the section hierarchy: `Parsing Schema` first, then
`Reusable Results`, then `Domain Constants`; **`Context Roadmap` and `Context Understanding` are
protected until last**.

**Setting.** Two benchmark families, both *question answering over a shared long text*, not code
editing. **OOLONG** (three hardest splits: trec_coarse, agnews, yahoo), scored 0.75^|y−ŷ| for
numerics / exact match otherwise. **CL-bench** (contexts paired with up to 12 related tasks;
all-or-nothing scoring, GPT-5.1 as judge; solving rate + rubric accuracy). Baselines: base RLM, RLM
w/ Shared Chat, RAG (text-embedding-3-small), Compaction Agent (MemAgent, GPT-5.4-nano), ACE.
All methods built on **RLM** — contexts offloaded as REPL variables, `max_iterations=30`,
`max_depth=1`, REPL output truncated to 20,000 chars. **Nothing is trained** — PEEK is entirely
prompted, and its own prompts (Distiller, Cartographer) are in the appendix. Models: GPT-5-mini
primary ($0.25/$2.00 per 1M), GPT-5.5, Qwen3-Coder-Next-FP8, GPT-5.4-nano (compaction only), GPT-5.1
(judge only). **No Claude model is used anywhere**; Claude Opus 4.6 (High) appears only as an
out-of-the-box entry on the reproduced CL-bench leaderboard.

**Codex condition (the "production coding agent").** Codex CLI, `sandbox="workspace-write"`, approval
policy `"never"`, no tool-call limit, unmodified default system prompt. **The context is written to a
`context.txt` file and Codex is told to work with that file.** It is a coding agent operating on a
text blob — *not* a repository.

## Relevance to P1–P4

**P3 (every session rebuilds the same picture)** — this is the paper's thesis, and it is the strongest
transfer. §Context Map: "When an agent repeatedly interacts with a long external context, it often
spends its first several iterations building a working understanding of that context… This
orientation work is transferable." The measured payoff is that a ≈1k-token artefact recovers 6–34 %
quality *while holding iteration count at or below baseline*. The `Domain Constants` and
`Parsing Schema` sections are the direct analogue of our re-learned frictions (a CLI's argument shape,
line-citation format). Gap: their recurring context is one static blob per benchmark instance; ours is
a mutating repo plus a per-slice plan, and the paper never tests a context that changes between runs.

**P1 (context is the cost)** — supported directionally but not in our units. The paper's cost figures
are raw API pricing with **no prompt caching anywhere** in the analysis, so it says nothing about the
cache-read/cache-write split that dominates our spend. What it does establish: the alternative to a
curated artefact — carrying the trajectory — inflates input tokens 9–10× for no or negative quality
(Shared Chat), and a curated playbook inflates *output* tokens (ACE, 12.45M). A constant-size map in
the system prompt would sit in our cacheable prefix, which the paper neither exploits nor measures.

**P2 (sessions grow; the longest dominate)** — weak transfer. Their horizon is `max_iterations=30` per
run and the reported iteration counts (269–748) are benchmark totals across many tasks, not per
session. They never report per-session context growth, and no run in this paper approaches our 145k
median / 438k peak. The one on-point claim is the negative one: persisting the full history "actually
hurts performance", so growth is not simply a cost problem.

**P4 (what smaller reads cost in grounding)** — the paper is unusually good evidence here because it
scores quality and cost together, and *the smaller curated context won on both*. It also names the
failure boundary: in the retrofitted benchmarks where each task needed a near-disjoint slice of the
corpus (BrowseComp-Plus: ~7.3 required docs out of ~800; FanOutQA: only **1.1 %** of ~48K dev question
pairs share any evidence page, overlapping pairs sharing ~2.4 pages), the map is "at best useless…
at worst it misleads the agent". That is the grounding-loss condition stated by measurement, and our
slices touching different parts of a repo look closer to that regime than to OOLONG's uniform corpus.

## Interventions this paper supports

- **A per-repository orientation artefact in every dispatch prompt, at a hard ~1k-token budget.**
  Rests on B = 1024 and the 512/2048 sweep (+15.5 %/+20.3 %): budget the artefact rather than letting
  the doc phase's output volume set it. Loses nothing the paper measured — the frozen-map ablation
  shows even an unmaintained map beats no map.
- **Fix its shape to Roadmap + Understanding, with optional Constants / Reusable Results / Parsing
  Schema.** Rests on the eviction order protecting the first two: what the repo contains and where,
  then the entity/concept model; frictions and exact values are second-class and evicted first.
- **Write it from finished-session trajectories, not by hand and not from the diff.** Rests on the
  Distiller design and the explicit refusal to pre-populate. Nearest surface: a post-run pass over a
  session's transcript or done-record. Cost shape: Distiller ≈2/3 of maintenance, maintenance
  6.2–17.9 % of total.
- **Split the update into diagnose-then-edit, two dispatches, not one** (monolithic ablation −7.7 %).
  A single "update the docs from this run" agent is the losing variant.
- **Give every item a stable ID and apply Add/Delete/Replace edits** (§Cartographer). Our doc phase
  rewrites prose; item IDs are what make tagging and eviction possible at all.
- **Refresh a few times, then freeze — not per session.** Rests on m ≤ 4 sufficing while fully-online
  ACE lost on both quality and cost. Per-slice refresh, not per-dispatch.
- **Do not put the trajectory, plan history, or prior-turn narration into it** — Shared Chat, 10.1×
  input for +1.75 %, −2 points on CL-bench; "persisting the full history actually hurts performance".
- **Do not build it by retrieval or by dumping a prefix, and do not regenerate it mid-session**
  (+0.73 % / +4.92 % / +0.73 %; runtime feedback −14.86 %, which "destroy[s] any stable orientation").
  That is an argument for stability across a session and against a wrapper that re-summarizes as it goes.
- **Do not spend the budget on behavioural instructions** ("be goal-oriented"): +5.65 % at higher cost.

## Applicability caveats

- **No Claude, and no repository.** Every backbone is GPT-5-mini / GPT-5.5 / Qwen3-Coder; Claude
  appears only as a leaderboard row. The Codex condition writes the context to `context.txt` — the
  external context is never a codebase, a file tree, or a symbol graph in any experiment.
- **Task type is QA, not code editing.** No gate, no diff, no acceptance criteria, no reviewer. The
  quality metrics (exact match, rubric accuracy) have no analogue to blocking-finding rate or gate-red.
- **No staleness experiment.** The premise is stated as "the external context stays largely the same
  while the tasks change." Staleness is handled only as a Distiller per-item tag inferred from a
  run's own trajectory — there is **no test of a context that mutates between runs**, which is exactly
  our case (every slice changes the repo). The paper gives no staleness *rule*, only a staleness
  *tag*.
- **Horizon mismatch.** `max_iterations=30`, depth-1 recursion, REPL output truncated at 20k chars,
  versus our 20–200 turns with no compaction.
- **Tables lost in conversion.** All per-condition cells (including every Codex and GPT-5.5 number)
  are unavailable; the ranges above are the authors' prose summaries of them.
- **Prompt caching absent.** Cost claims are raw token pricing; the 1.25×/0.1× economics that decide
  whether a resident prefix is cheap for us are not modelled.
- Nothing needs training; PEEK is prompts plus a budget, which is squarely inside our surface.

## Briefing check

The note reads: *"constant-size context map of a recurring repository; validated on a production
coding agent."*

- **"Constant-size context map" — fully supported.** "a hard token budget B, fixed across all queries
  on a context and across all experiments", default **B = 1024 tokens**, with the 4× sweep showing
  presence matters more than size.
- **"validated on a production coding agent" — supported, but thinner than it sounds.** §Generalization:
  "When we change the backbone agent to Codex, the gains do not disappear either and are in fact even
  larger, demonstrating that a context map can deliver substantial improvements on top of a
  production-grade coding agent." No numbers survive the table loss, and it is Codex, not Claude Code.
- **"of a recurring repository" — this is the part the note gets wrong.** No experiment maps a
  repository. The recurring external contexts are OOLONG's uniform tabular text blobs and CL-bench's
  knowledge/rule/procedure documents; in the Codex condition the corpus is handed over as a single
  `context.txt`. "Code repositories" appears only in the abstract's and introduction's motivating
  list. The paper also never compares against a repo-map baseline (Aider-style) or against reading
  the full repo — its baselines are Shared Chat, RAG, MemAgent compaction, and ACE.

**Transfer answer for the doc phase** (paper-grounded where marked; the rest is flagged inference):
*What it must contain* — an index of what the repo contains and where (`Context Roadmap`) plus the
entity/concept model (`Context Understanding`), and only then the frictions: exact values and
enumerated sets (`Domain Constants`) and format/delimiter conventions (`Parsing Schema`). Explicitly
not: narration, prior trajectories, task strategies, or behavioural advice — all four measured at or
below +5.65 %, one at −14.86 %. *How big* — a hard budget around 1k tokens, enforced by eviction that
protects the roadmap and understanding sections last (paper-grounded; 512 already delivers +15.5 %).
*What staleness rule* — **the paper supplies none for a mutating context.** What it does supply is
per-item tagging (`helpful | harmful | neutral | stale`) derived from a completed run's trajectory,
with Replace/Delete edits against stable IDs and refresh frozen after m ≤ 4 updates. Our repo changes
under the map every slice, a regime the paper never tested; its own failure analysis (near-disjoint
per-task evidence ⇒ "at worst it misleads the agent") is the warning that an artefact pinned to
structure that a slice has just moved is a grounding risk, not a saving. Any staleness rule we adopt
is unevidenced by this paper and needs its own measurement.
