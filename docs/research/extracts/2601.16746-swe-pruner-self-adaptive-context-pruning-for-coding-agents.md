## Core results

1. **Read operations are where an agent's tokens go.** Mini SWE Agent + Claude Sonnet 4.5 on
   SWE-Bench Verified: *read* ops (`cat`, `grep`, `head`, directory inspection) = **76.1 %** of all
   tokens; *execute* 12.1 %; *edit* 11.8 % (§Motivation, Fig. 2). Same agent with GLM-4.6: read
   **67.5 %** (2.89 M), edit 18.5 % (0.79 M), execute 14.0 % (0.60 M) (App. A). Measured, from
   trajectory action-type accounting.

2. **SWE-Bench Verified, full 500 (recovered table).** Mini SWE Agent, temperature 0, ≤250 rounds:

   | Agent | Rounds | Solved | Success % | Tokens (M) | Cost ($) |
   |---|---|---|---|---|---|
   | Claude Sonnet 4.5 | 51.0 | 353/500 | 70.6 | 0.911 | 0.504 |
   | + SWE-Pruner | 41.7 (−18.2 %) | 360/500 | **72.0 (+1.4 pt)** | 0.701 (**−23.1 %**) | 0.369 (−26.8 %) |
   | GLM-4.6 | 49.3 | 277/500 | 55.4 | 0.791 | 0.055 |
   | + SWE-Pruner | 36.6 (−25.7 %) | 283/500 | **56.6 (+1.2 pt)** | 0.488 (**−38.3 %**) | 0.035 (−36.4 %) |

   **Internal inconsistency to flag:** Fig. 1 / Fig. 7 captions claim, for Claude, −38.7 % prompt,
   −40.8 % completion, **−39.2 % total** tokens and −18.3 % rounds (GLM: −44.2/−44.0/−43.6/−34.6 %),
   and the Introduction repeats "39 % reduction … with Claude Sonnet 4.5". The table says −23.1 %
   (Claude) / −38.3 % (GLM), and the abstract says "23–38 %". Rounds agree for Claude (18.2 ≈ 18.3)
   but not GLM (25.7 vs 34.6). **Use the table's 23.1 %, not the figure's 39 %.**

3. **The decision-relevant number for us: every *untrained* compressor lost resolve rate.** Random
   50-instance subset of SWE-Bench Verified, Claude Sonnet 4.5 (Tab. `baseline_comparison`):

   | Method | Rounds | Success % | Tokens (M) |
   |---|---|---|---|
   | Mini SWE Agent (no compression) | 52.3 | 62.0 | 0.972 |
   | + LLMLingua2 (token-level, trained classifier) | 42.1 | **54.0** | 0.856 |
   | + RAG (function chunks, UniXCoder top-k) | 40.2 | **50.0** | 0.771 |
   | + LLM Summarize (backbone model summarises files) | 41.3 | **56.0** | 0.794 |
   | + LongCodeZip (AST chunks + entropy) | 44.3 | **54.0** | 0.889 |
   | + SWE-Pruner (goal-hinted trained skimmer) | 41.1 | **64.0** | 0.670 (−31 %) |

   Task-agnostic compression cost **6–12 resolve points** for 9–21 % token savings; the
   goal-conditioned trained skimmer gained 2 points for 31 %.

4. **Line-level granularity is what preserves code, and most of that is free.** AST correctness after
   compression, tree-sitter on Long Code Completion (Tab. `ast_correctness`): Full 98.5 %;
   LLMLingua2 **0.29 %**; Selective-Context 12.4 %; **Random Token Pruner 49.6 %**; Function RAG
   92.3 %; Function RAG + **Random Line Pruner 78.2 %**; Function RAG + SWE-Pruner 87.3 %;
   LongCodeZip 89.3 %; LongCodeZip + SWE-Pruner **76.8 %** (stacking two pruners *hurts* structure).
   Untrained random *line* pruning (78.2) is close to the trained skimmer (87.3); the token/line axis,
   not the model, buys the syntactic validity.

5. **SWE-QA (OpenHands, repo-level QA, LLM-judge 0–10).** Claude Sonnet 4.5 gains are small on tokens,
   GLM's are large: Streamlink 8.36→8.59, 611.2K→557.1K (−8.9 %); Reflex 8.68→8.85,
   1081.6K→866.8K (−19.9 %); Conan 8.70→8.84, 654.7K→520.7K (−20.5 %). GLM-4.6: Streamlink
   8.56→8.56 (−54.4 % tokens), Reflex 8.37→**8.23** (−28.9 %), Conan 8.58→**8.45** (−33.7 %), with
   rounds **up 29–41 %** (more files explored per answer). The headline "29–54 %" is GLM-driven; for
   **Claude the SWE-QA token reduction is 8.9–20.5 %.**

6. **Single-turn (Qwen2.5-Coder-7B, Tab. `main-results`).** Long Code Completion, 8× constraint:
   Full 64.65 ES / 40.5 EM; SWE-Pruner 10.92× / 57.58 / 31.0; LongCodeZip 7.85× / 56.08 / 27.5; RAG
   6.60× / 55.82 / 29.0; Selective-Context 7.49× / 48.67 / 17.0; LLMLingua2 7.89× / 44.74 / 13.0;
   No Context 44.90 / 13.5. **No compressor recovers Full on completion** (−7 ES, −9.5 EM at best).
   Long Code QA: Full 54.05 % acc; SWE-Pruner 13.95× / **59.46 %** (4×) and 14.84× / 58.71 % (8×) —
   *above* full context; RAG 5.87× / 55.86 %. Seed-Coder-8B replicates the pattern (App. F).

7. **Skimmer latency is negligible.** TTFT (Tab. `ttft_results`) 44.7 / 43.9 / 42.1 / 49.1 / **102.0 ms**
   at 64 / 128 / 512 / 2048 / 8192 input tokens, vs Qwen3-32B 1188.67 ms at 8192. Authors argue
   40–50 ms is <10 % of a typical Claude API roundtrip (500 ms–seconds).

8. **Case studies (App. I), two instances only.** `django__django-10554`: baseline exhausts limits at
   164 steps / 7,001,934 tokens / peak prompt 87,790 → pruner succeeds in 56 steps / 1,170,160 tokens
   / peak 38,226 (−83.3 % tokens; failure→success). `django__django-11740`: both succeed; pruner takes
   **more** steps (48 vs 42) for −6.0 % tokens and **−30.2 % peak prompt length**.

## Method and setting (what was actually built/tested)

Middleware at the agent–environment boundary. File-reading tools get an optional
`context_focus_question` parameter; when the agent supplies a goal hint the raw tool output is scored
and pruned before entering context, when it omits it the **skimmer is bypassed and full output is
returned** (§3.2, code listing). Pruning happens **at read time**, so the reduced form is what
accumulates across rounds. The agent regenerates a hint each round from its evolving reasoning trace
("complete, self-contained questions", e.g. *"How is authentication handled?"*, *"Focus on MRO
resolution logic"*); exact prompt text is in an appendix figure that did not convert.

Scope: **only file-read observations** — `cat`, `grep`, file/dir inspection. Test/execute output and
edit results are **not** pruned. Prior interaction history is explicitly out of scope: the authors
decline comparison with history compressors (AgentFold, ACON) as "a different problem", calling
SWE-Pruner orthogonal to and combinable with them (§Related Work).

The skimmer is **trained**, not prompted: Qwen3-Reranker-0.6B backbone (last two layers fine-tuned,
hidden states from layers 7/14/28 fused), a CRF pruning head (Viterbi, retain/prune) plus the original
reranking head; token scores averaged per line, line kept if mean > τ = 0.5. Training data: 200,000
snippets from 195,370 files / 5,945 repos (GitHub-Code-2025), queries + line masks synthesised by
Qwen3-Coder-30B-A3B-Instruct across a **9-task taxonomy** (code-debug, feature-addition,
find-relevant-part, code-locate, code-explain, code-summarize, code-refactor, code-optimize,
code-completion), judge-filtered by Qwen3-Next-80B-A3B-Thinking keeping ≈1/6 → **61,184 samples**;
3 epochs, lr 3e-5, batch 128, λ=0.05.

Agents/models: Mini SWE Agent (cat/grep read, sed edit, bash exec; ≤250 rounds) on SWE-Bench Verified
(500 issues, 12 **Python** repos); OpenHands on SWE-QA (streamlink, reflex, conan). Backbones **Claude
Sonnet 4.5** and GLM-4.6, temperature 0, "averaged over three random seeds where applicable".
Single-turn with Qwen2.5-Coder-7B and Seed-Coder-8B.

**No ablation exists** on the goal hint (hint vs no hint), on trained-vs-prompted skimmer, on τ, or on
CRF vs BCE — confirmed against the HTML. **No truncation, head/tail, fixed-window or observation-mask
baseline was run.** No systematic failure analysis: no count or rate of "pruning removed a line the
agent needed".

## Relevance to P1–P4

**P1 (context is the cost).** Direct support for the diagnosis, from the same model family: 76.1 % of
Claude Sonnet 4.5's agent tokens are file-read observations. But their cost accounting is **uncached**
(−23.1 % tokens → −26.8 % $). With our profile (63 % cache read at 0.1×) a retained-but-cached bulk is
already ~10× cheaper per token, so a 23 % cut in read volume converts to a much smaller dollar cut for
us — and read-time shaping that varies the *stable* early part of a transcript would break cache
prefixes. The mechanism (shrink what enters, once) is the right shape for us; the dollar multiplier is
not.

**P2 (sessions grow; the longest dominate).** The strongest transfer. Peak prompt length fell 30.2 %
in a case where total tokens only fell 6 %, and the 7 M-token / 164-step runaway became a 56-step
success — that is our long-tail doc-writer / big code-writer session. Rounds fell 18.2 % for Claude,
i.e. the shaped read also cut *turns*, not just bytes per turn. Caveat: their agent has a 250-round
cap and no compaction, like ours; but their sessions are one continuous SWE-Bench episode, not our
30-session relay.

**P3 (every session rebuilds the same picture).** **Not addressed.** SWE-Pruner is strictly
within-session and explicitly refuses the cross-turn/history problem. Nothing here about hand-offs,
carry-over artefacts, or re-reading the same plan across fresh sessions.

**P4 (what smaller reads cost in grounding).** The most useful paper we have on this, because it
prices the loss on outcome instruments. Task-agnostic compression at ~4–8× cost **6–12 resolve points**
on SWE-Bench (62 % → 50–56 %); goal-conditioned line pruning at 31 % token savings *gained* 2 points.
On single-turn completion, **every** method including theirs stayed 7 ES / 9.5 EM below full context —
so a shaped read is not free when the task is "produce exactly the right code at a point". On QA the
sign flips: pruned context beat full context (59.46 vs 54.05), i.e. noise removal helps comprehension
questions more than it helps generation.

## Interventions this paper supports

- **Cut at line boundaries, never at token/character level, in any read wrapper we write.** Rests on
  #4 (AST 0.29–12.4 % token-level vs 78.2 % *random* line-level) and #3 (LLMLingua2 −8 resolve points).
  Free to implement; the syntactic-validity part of the benefit does not need a model. *Loses:* random
  line pruning still drops 92.3 → 78.2 % AST correctness, so line-alignment alone is not safety.
- **Default to full output; prune only when the caller states an information need.** Their
  bypass-by-default wrapper (§3.2) is the exact shape of a `Read`/`Grep` wrapper we could add, and it
  preserves the "no hint → nothing changes" escape hatch. *Loses:* nothing measured — but the paper
  never ablates the hint, so we cannot claim a size for the hint alone.
- **Require dispatch prompts and sub-agent contracts to carry an explicit, self-contained goal
  question** (their hint format: complete questions, median 24 words / 169 chars). This is the one
  component that transfers with zero training cost. *Evidence is indirect*: the goal-conditioning is
  what distinguishes their winner from the task-agnostic losers in #3, but no ablation isolates it.
- **Do not replace reads with retrieval.** RAG scored worst (50.0 % vs 62.0 %) despite good token
  savings — relevant to any proposal that an Explore sub-agent return retrieved chunks rather than the
  writer reading. *Loses:* "fine-grained implementation details" (their stated diagnosis).
- **Do not put an LLM summariser in front of file reads.** LLM Summarize: 56.0 % vs 62.0 %, plus added
  latency (#3). This is the prompted-model substitute we would reach for and it measured worse than
  doing nothing.
- **Instrument read-vs-execute-vs-edit token share per session** (their 76.1 / 12.1 / 11.8 split gives
  a comparison point) and **track peak per-turn context as its own metric**, not just totals — #8
  shows peak moving 5× more than the total.
- **Do not spend effort compacting gate/test output on this paper's authority**: execute ops were only
  12.1 % of tokens and were never pruned in any experiment.
- **Do not stack two compressors.** LongCodeZip + SWE-Pruner dropped AST correctness to 76.8 %, below
  either alone (#4).

## Applicability caveats

- **The winning method requires training** a 0.6B reranker on 61k synthesised line-mask samples — out
  of scope for us. Everything the paper measured that we *can* build (retrieval, entropy/perplexity
  pruning, AST chunking, LLM summarisation) lost resolve rate.
- **No head/tail, fixed-window, or grep-window baseline was tested at all.** The cheapest mechanical
  wrappers are simply unmeasured here — the paper neither supports nor refutes them.
- **Claude-specific effects are the weaker half.** Claude gained least everywhere (−23.1 % tokens vs
  GLM −38.3 %; SWE-QA −8.9 to −20.5 % vs GLM −28.9 to −54.4 %), and the authors attribute this to
  Claude's "extensive context capabilities maintain[ing] reasonable focus even unpruned". Our stack is
  Opus, further along that axis.
- **Sonnet 4.5, not Opus; SWE-Bench single-episode, not a 30-session relay; Python-only** (stated
  limitation); the head-to-head baseline table is **n = 50**, and 62 %→64 % on 50 samples is one
  instance flipping.
- **No error analysis of pruning damage**, no reported rate of "needed line removed". The only visible
  cost signals are GLM's +29–41 % rounds and −0.13/−0.14 SWE-QA scores, and the single-turn ES gap.
- **The paper contradicts itself on the headline number** (23.1 % table vs 39 % figure/intro); prefer
  the table.

## Briefing check

The note — *"goal-hinted line-level pruning with Claude Sonnet 4.5 on SWE-bench Verified; the skimmer
is a trained model — the shaped-read result is what we need"* — is accurate on all four counts.
Supporting quote: "SWE-Pruner reduces token consumption by 23–38 % on SWE-Bench while improving
success rates by 1.2–1.4 percentage points" (Conclusion), against a skimmer that is explicitly "a
lightweight 0.6B pruning model [trained] on 61K synthetic data" (Introduction).

Two corrections to how the note might be read. (1) **"The shaped-read result" is not separable from the
training.** The paper's own baseline table is the counter-evidence: every shaped read we could build
without training (RAG 50.0 %, LLM Summarize 56.0 %, LongCodeZip 54.0 %, LLMLingua2 54.0 %) came in
*below* the unshaped baseline of 62.0 %. The transferable-without-training finding is narrower: **cut
whole lines, not tokens** (AST 78.2 % random-line vs 49.6 % random-token). (2) The Claude-specific
numbers are the *low* end of every range the abstract quotes — 23.1 % tokens on SWE-Bench and 8.9–20.5 %
on SWE-QA; the 39 %, 54 % and 14.84× figures come from a mislabelled figure, GLM-4.6, and single-turn
Qwen respectively.
