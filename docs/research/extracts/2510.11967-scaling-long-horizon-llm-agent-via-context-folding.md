## Core results

All rows below share one base model, **Seed-OSS-36B-Instruct**, one tool set, one training corpus.
"32K × 10" = a 32,768-token *active* context with up to 10 branches/summaries, i.e. 327,680 tokens
of total possible interaction. Numbers are pass@1 / mean tool calls, from **Table 1**
(BrowseComp-Plus N=150, a 680/150 author re-split; SWE-Bench Verified N=500).

1. **Folding at 32K active context beats ReAct at 327K — but only after RL.** Folding + FoldGRPO:
   **0.620 / 19.2** (BC) and **0.580 / 96.5** (SWE), vs the 327K ReAct reference 0.478 / 10.8 and
   0.552 / 49.5. The abstract's "10× smaller active context" is this row.
2. **Prompted-only folding does *not* reach long context.** With no RL: **0.420** (BC), **0.492**
   (SWE) — 5.8 and 6.0 points below 327K ReAct, 13.4 and 5.6 above 32K ReAct (0.286 / 0.436). §4.1:
   "without performing RL, the context folding agent already surpasses the 32K-context ReAct and
   context summarization baselines, though it does not yet match the … long-context ReAct agent."
3. **Folding vs summarisation is a real but small margin, and RL-dependent.** Summary agent
   (compaction when the context fills, 32K × 10): **0.386 / 0.488** prompted, **0.527 / 0.550** with
   GRPO. Folding: **0.420 / 0.492**, **0.567 / 0.564**, **0.620 / 0.580** (FoldGRPO). Boundary-aligned
   folding beats threshold summarisation by **+3.4 / +0.4** prompted, **+4.0 / +1.4** under the same
   RL, **+9.3 / +3.0** with the folding-specific reward.
4. **RL is the largest single term.** Absolute RL gain on the folding agent: **+20.0 points BC,
   +8.8 SWE** (0.420→0.620, 0.492→0.580; §1). The *architecture* gain at fixed prompting is
   5.8/6.0 points **negative** against long context (finding 2).
5. **Compression measured.** With FoldGRPO the main trajectory is cut to **~8K tokens while >100K
   are processed in total — "over 90% context compression"** (§4.3; Table 2 Main Len 7,752 BC /
   8,885 SWE). Case study: 4 branches compress a 107K context to 6K (§4.5.1). Caveat: the prompted
   SWE agent's Main Len is 47,475 against a 32,768 limit, so "Main Len" is presumably cumulative
   main-thread tokens, not peak context.
6. **Delegation loses scope, measurably.** Table 2's "Scope" = fraction of sub-trajectories a
   GPT-5-nano judge rules on-topic given the branch prompt and the returned message. Prompted
   folding: **0.774 BC / 0.473 SWE**. Plain GRPO worsens it (0.762 / 0.419) and inflates main length
   (22,285 / 48,908). FoldGRPO's out-of-scope penalty lifts it to **0.895 / 0.754**, and the
   in-budget completion rate ("Finish") from 0.806 / 0.781 to **0.935 / 0.962**.
7. **More context management buys more tool calls, not fewer.** The winning agent makes **96.5** SWE
   tool calls vs 49.5 for 327K ReAct and 77.0 for the summary agent; §4.1 reads this as more thorough
   exploration. The paper reports **no token-spend, dollar or wall-clock cost for any eval agent**.
8. **Parallel branching bought nothing.** A parallel-branch variant scored **0.6133** vs 0.620
   single-branch on BC, with ~2.3 parallel branches and 110 pages read vs 80 (§4.5.3). The authors
   *conjecture* the benchmark is depth-first and breadth-first tasks might differ.
9. **Scaling behaviour.** Pass@1 vs branch count (0→16) rises then **plateaus beyond ~320K total
   tokens** "because most task instances are already completed" (§4.4.1). On compound queries (1–50
   easy questions merged, ReAct given 1M context), folding's margin grows with complexity, and an
   agent trained on ≤10 branches adaptively uses **32.6 branches** at 50 questions (§4.4.2).
10. **Frontier reference points** (327K ReAct, BC / SWE pass@1, Table 1): GPT-5 0.793 / 0.718;
    GPT-4.1 0.640 / 0.486; DeepSeek-V3.1 0.613 / 0.610; GLM-4.5-Air 0.566 / 0.576; Qwen3-235B
    0.560 / 0.344. **No frontier model was run with folding.**

*Discrepancy to flag:* §4.1 claims FoldGRPO beats GRPO by "+7.7% on BrowseComp"; Table 1 gives
0.620 − 0.567 = **+5.3**. The SWE figure (+1.6) does match.

## Method and setting (what was actually built/tested)

**Mechanism.** Two tools (appendix §9.3). `branch(description, prompt)` opens a sub-trajectory —
`description` a 3–5 word id, `prompt` must "state objectives and critical info to preserve in the
response". `return(message)` ends it, `message` being "a comprehensive message describing sub task
outcome". On return the context **rolls back the KV-cache to the pre-branch position** and appends
only the return message: the prefix stays cached, every action/observation inside the branch
disappears (§2.2). Instantiated as plan–execution — token-heavy tools discouraged in the main
thread, **nested branching disabled inside a branch**.

**Trained, not prompted.** FoldGRPO adds three token-level process rewards on top of outcome reward
(§2.3.2): an *unfolded token penalty* (−1 on all main-thread tokens once the main thread passes 50%
of the limit, except branch-creating turns), an *out-of-scope penalty* (−0.2 on a whole branch a
GPT-5-nano judge rules off-brief), and a *failed tool call penalty* (−1). Training: VeRL, 50 steps
(~2 epochs), no KL; inference greedy.

**Tasks.** (a) BrowseComp-Plus deep research — `search(query, topk)`, `open_page(url)`,
Qwen3-Embed-8B retriever, LLM-judge reward. (b) SWE-Bench Verified — `execute_bash`,
`str_replace_editor`, `think` (OpenHands scaffold), reward = unit tests in a per-instance sandbox;
740 training instances filtered from SWE-Gym/SWE-Rebench by 0 < success@8 ≤ 87.5%. The SWE system
prompt is a fixed 8-phase procedure (read → run tests → explore → write repro test → analyse fix →
implement → verify → final review; appendix §8.2).

**Horizon.** One session per instance, 26–97 tool calls, 3–6 branches, ≤327K total tokens.
Baselines: ReAct at 32K / 65K / 131K / 327K (only 32K and 327K appear in Table 1), and a Summary
Agent compacting when the context fills (32K, 10 summary sessions) — same base model, data and RL
hyperparameters throughout. Reported metrics: pass@1, tool calls, peak length, Finish, Main Len,
Scope, #Branch.

## Relevance to P1–P4

**P1 (context is the cost).** Partial, and easy to over-read. Folding shrinks *peak active context*
per generation step, and KV-rollback means the pre-branch prefix survives the branch — the same
economics as our cache reads. But the folding agent issues **~2× the tool calls of long-context
ReAct** (96.5 vs 49.5), so *total* tokens processed plausibly went **up**, and the paper never
measures spend. Nothing here says folding is cheaper in dollars; it says a small active window need
not cost accuracy. Our 33k fixed per-session prefix has no analogue — folding keeps one session and
one prefix, where we pay a new prefix per fresh session.

**P2 (sessions grow; the longest dominate).** Directly on point, and the closest structural analogue
to our doc-writer (one session, whole diff, 145k median / 438k peak). Table 2 is the existence proof
that a main thread can be held at ~8K while >100K flows through it, and §4.4.2 shows the advantage
*growing* with task complexity — with 32.6 branches emerging for tasks trained at ≤10. Transfer gap:
their agent was trained to do this; ours would be prompted (see P4).

**P3 (every session rebuilds the same picture).** The sharpest contrast with our design. §2.4 lists
three deliberate differences from multi-agent systems: sub-agents created on the fly rather than
predefined, interleaved rather than parallel, and "all the agents share the same context prefix,
making it KV-cache friendly". Our Explore sub-agents are the opposite on all three: fresh context,
fixed roles, no shared prefix. The paper never isolates how much of the win comes from prefix
sharing versus folding, so this is a design argument, not a measured one.

**P4 (what smaller reads cost in grounding).** The best-instrumented answer here. At fixed model and
task, dropping 327K → 32K active context costs **19.2 points BC / 11.6 SWE** by plain truncation,
**9.2 / 6.4** by threshold summarisation, **5.8 / 6.0** by sub-task-boundary folding — all prompted.
A ranking of context-management strategies by grounding loss: the loss is real (5–6 points even for
the best prompted method), but *how* you cut matters more than *that* you cut. Table 2's Scope adds
an instrument we lack — a cheap judge scoring whether a sub-agent stayed inside its brief.

## Interventions this paper supports

- **Two-tier context inside a long role (doc-writer first).** Keep a durable main thread (plan,
  decisions, diff inventory) and push each token-heavy chunk into a branch whose only residue is a
  written outcome. Rests on Table 2 (main 8K / total >100K) and §4.5.1 (107K → 6K over 4 branches).
  *Loses:* prompted-only, expect finding 2's 5.8/6.0-point grounding gap and 0.473–0.774 Scope —
  a quarter of BC branches and half of SWE branches wandered off brief before training.
- **Cut at sub-task boundaries, never at a token threshold.** §2.4 ("summarization … discards
  details at arbitrary points"; folding "compacts once its utility is realized") plus the
  +3.4 / +0.4 prompted and +4.0 / +1.4 same-RL margins. Applies to where we end a session and what
  the hand-off carries. *Loses:* the prompted SWE margin is 0.4 points — inside noise.
- **Make the dispatch prompt name what the return must preserve** — their branch parameter reads
  "state objectives and critical info to preserve in the response". Cheap edit to our sub-agent
  contract. *Loses:* nothing measured; the paper never ablates the wording.
- **Add a scope check to sub-agent returns.** A cheap-model judge over (dispatch prompt, returned
  conclusion) → in/out of scope, as a new P4 instrument alongside blocking-finding rate. Rests on
  §2.3.2 and Table 2's Scope column. *Loses:* the paper used it as a training signal, not a runtime
  filter; as a runtime gate it is unvalidated.
- **Ban token-heavy reads in the planning thread; force them into a sub-agent.** The unfolded-token
  penalty's intent, expressible as a dispatch-prompt rule; targets the 14–65 orientation reads before
  first edit. *Loses:* the paper enforced this by RL penalty, and prompting alone was one of the two
  failure modes it observed — sparse outcome reward left "token-intensive operations unfolded in the
  main context" (§2.3.2).
- **Forbid nesting.** Their execution state disables further branching, to avoid nested complexity
  (§2.2). Our Explore agents should not spawn Explore agents.
- **Do not add parallel sub-agents expecting accuracy.** 0.6133 vs 0.620 (§4.5.3) — parallelism is
  a latency argument here, not a quality one.

## Applicability caveats

- **No Claude, no frontier model, ever ran folding.** Every folding number is Seed-OSS-36B-Instruct.
  GPT-5 etc. appear only as 327K ReAct baselines. A model already strong at long context (GPT-5:
  0.718 SWE, above every folding row) may have far less headroom.
- **The headline needs training we cannot do.** The only configuration beating long context is
  RL-trained with folding-specific rewards; our surface is prompts, files and scripts. The honest
  prompted-only reading of Table 1: folding ≈ summarisation ≈ still ~6 points below long context.
- **Task shape.** SWE-Bench Verified is one issue, one session, a fixed 8-phase prompt, no plan
  loop, no reviewer, no cross-session hand-off, unit tests as ground truth. Our slice is ~30
  sessions with judgment steps whose "reward" is unobservable.
- **No cost measurement of any kind** for the eval agents — no token spend, no cache accounting, no
  wall clock (only training-step time, §4.5.2). Any read-across to our $221 slice is extrapolation.
- **Benchmark quirks.** BrowseComp-Plus was re-split by the authors (680 train / 150 eval), so BC
  numbers are not comparable to published BrowseComp-Plus results; its difficulty tiers are defined
  by a ReAct agent's own acc@8, coupling the tiering to the baseline.
- **Internal inconsistency** in the +7.7% claim, and an ambiguous "Main Len" definition (both noted
  in Core results) — treat the "90% compression" figure as approximate.

## Briefing check

The briefing filed this as "read only the folding-versus-summarisation comparison". That comparison
exists and is clean — same base model, data and RL setup (Table 1: summary 0.386 / 0.488 prompted,
0.527 / 0.550 with GRPO; folding 0.420 / 0.492 and 0.567 / 0.564). But the note under-scopes the
read in a way that would mislead. Two corrections:

1. **The folding-vs-summarisation delta is the smallest of the deltas in the table** (+3.4 / +0.4
   prompted). The decision-relevant comparisons are the other two: folding vs *plain 32K ReAct*
   (+13.4 / +5.6, i.e. any structured management beats truncation) and folding vs *327K ReAct*
   (−5.8 / −6.0 prompted, +14.2 / +2.8 only after FoldGRPO). Reading only the folding-vs-summary row
   would credit the mechanism with a win it earns from RL.
2. **The paper's own summary of that row is the quote to carry:** "without performing RL, the
   context folding agent already surpasses the 32K-context ReAct and context summarization
   baselines, though it does not yet match the performance of the long-context ReAct agent" (§4.1).
   So the answer to "does the gain need training" is **yes for the headline, no for the ordering** —
   the ranking truncation < summarisation < boundary folding < long context holds prompted; only
   training flips the last inequality.
