## Core results

1. **Failure-pair guideline optimization beats every compression baseline, at roughly-preserved
   average accuracy.** AppWorld test-normal (168 tasks), gpt-4.1 agent + gpt-4.1 compressor,
   history compression (Table 1), as acc / peak-input-tokens(×10³): no-compression 56.0/9.93;
   FIFO-5 45.8/6.73; retrieval 27.4/8.39; LLMLingua 39.3/7.50; naive prompting 43.5/6.93;
   **ACON ᵁᵀ 51.2/7.17; ACON ᵁᵀᶜᴼ 56.5/7.33** — +13.0 acc over the best prior baseline at
   −26.2 % peak. Observation compression, same table: ACON ᵁᵀᶜᴼ 53.6/7.43 vs prompting 42.3/6.58.
2. **The average hides a large loss on hard tasks.** AppWorld by difficulty (Table 1):
   Easy 80.7 → 86.0, Medium 47.9 → 56.2, but **Hard 39.7 → 30.2** for ACON ᵁᵀᶜᴼ history
   (ACON ᵁᵀ Hard 28.6). Every other history baseline collapses further on Hard (FIFO 15.9,
   LLMLingua 15.9, prompting 23.8, retrieval 7.9). Compression also *lengthens* trajectories:
   16.14 → 22.82 steps (+41 %).
3. **Per-benchmark accuracy retained vs tokens saved** (peak input tokens, ×10³, excl. system
   prompt; best ACON variant, gpt-4.1 both roles):

   | Benchmark | metric | no-compress | ACON ᵁᵀ | ACON ᵁᵀᶜᴼ | peak saved |
   |---|---|---|---|---|---|
   | AppWorld (T1) | acc | 56.0 / 9.93 | 51.2 / 7.17 | 56.5 / 7.33 | −26 % |
   | OfficeBench (T2a, 95 tasks) | acc | 76.84 / 7.27 | 74.74 / 4.93 | 72.63 / 4.54 | −32…−38 % |
   | 8-objective QA (T2b, 100 tasks) | EM/F1 | .366/.488 / 10.35 | .373/.494 / 4.71 | .335/.458 / 4.65 | −54.5 % |
   | WebVoyager (T6, 70 tasks) | acc | 35.7 / 13.28 | 48.6 / 8.04 | — | −39 % |

   OfficeBench by level (Table 8): ACON ᵁᵀ history *gains* on the hardest, Level-3 54.84 → 61.29.
   WebVoyager is the one setting where compression clearly beats full context (+12.9 acc), which the
   authors attribute to verbose AXTree observations distracting the agent.
4. **Model transfer is weaker than the headline.** **gpt-5-chat** as agent and compressor, reusing
   the gpt-4.1-derived guidelines (Table 12): no-compression 66.7/9.67; best history ACON ᵁᵀᶜᴼ
   62.5/7.26; best observation ACON ᵁᵀ 65.5/7.58. On the stronger model ACON **loses** accuracy
   versus full context (Hard 47.6 → 33.3) rather than matching it. No Claude, Gemini or DeepSeek
   results at all (Appendix A lists this as a limitation).
5. **The contrastive pairing is a small part of the gain.** Optimizer ablation (Table 3, AppWorld):
   o3 + contrastive feedback 51.2; **o3 on failed trajectories only (no pairing) 50.6 (−0.6)**;
   gpt-4.1 as optimizer 47.6 (−3.6); gpt-5 optimizer 50.6 (−0.6). Failure-driven optimization *at
   all* is worth ≈ +7.7 over naive prompting; the full-vs-compressed *pairing* ≈ 0.6; the optimizer
   model up to 3.6.
6. **One optimization round only; stacking compressions is destructive.** An extra ᵁᵀ round after
   ᵁᵀᶜᴼ drops AppWorld accuracy 56.5 → 47.0 (Table 14). Applying history *and* observation
   compression together: 45.8 acc at 5.85k peak vs 56.5 at 7.33k — ~11 accuracy points bought for
   ~20 % further peak reduction (Table 14).
7. **Distillation of the compressor works; the compressor need not be large.** Qwen3-14B, Qwen3-8B
   and Phi-4 LoRA-distilled from the gpt-4.1 compressor retain **>95 %** of teacher performance
   (Fig. 4, Fig. 7); gpt-4.1-mini works as a compressor with the optimized guideline and *no*
   distillation on OfficeBench and QA. Compression cost per example: gpt-4.1 $0.045 →
   gpt-4.1-mini $0.014 (−69.2 %) → distilled Qwen3-14B $0.0004 (−99.1 %) (§4.5).
8. **End-to-end money saved is far smaller than peak tokens saved, and latency rises.** AppWorld,
   per task, gpt-4.1 agent + Qwen3-14B compressor, **explicitly excluding input caching**
   (Table 4): no compression $0.331 / 73.24 s; ACON history $0.285 / 87.68 s; ACON observation
   $0.272 / 101.92 s. That is a 14–18 % cost reduction and a 20–39 % latency increase, against a
   26–54 % *peak-token* reduction. Appendix A adds that history compression **invalidates the
   KV cache and forces recomputation of the compressed sequence**.
9. **Optimization is cheap.** Guideline optimization < **$2 per domain** (o3, one round, 5 candidate
   prompts); the rollout data collection (90 AppWorld train tasks × 2 trajectories) ≈ **$20**, and
   the authors note it can be substituted with existing offline logs (§4.5, §C.2).

## Method and setting

**Task type:** ReAct tool-use agents in simulated environments — AppWorld (9 apps, 457 APIs,
avg 42.5 API calls/task; 90 train / 168 test), OfficeBench (92/95), 8-objective QA (BM25 over 2018
Wikipedia, 100/100), WebVoyager (50/70). Horizon 10–40+ steps. No coding benchmark, no repository,
no file:line citation task anywhere.

**What is compressed, and when.** Two independent, threshold-gated hooks: history compressed when
|h| > T_hist (4096 tokens; 2048 for QA), observation when |o| > T_obs (1024/512/400). The last
(action, observation) pair is always kept raw, for ACON and every baseline. Fig. 6: smaller
thresholds mean more compressor calls and *worse* accuracy. Compressed history is injected into a
**fresh session** — the optimizer prompt describes the compressed run as "split into multiple
sessions where each new session starts with a fresh system + user prompt and an injected
`<HISTORY_SUMMARY>`."

**How the failure pairs are formed and the guideline derived** (§3.3, Algorithm 1, Appendix B.3):

- Run the fixed agent over the training set **twice**: no compression (context **H**, success
  r_base) and with the current guideline (**H′**, success r).
- `I⁺` = tasks the *uncompressed* run solved. `D_cont` = `{(H, H′) : i ∈ I⁺ and r_i = 0}` —
  **full succeeds, compressed fails**. (The shipped analysis prompt also admits pairs where the
  compressed run *succeeded but inflated step count past a threshold factor* — a
  `performance_regression` flag — so efficiency regressions feed the pairs too, which Algorithm 1's
  set definition does not capture.)
- For each pair an **optimizer LLM (o3)** gets both trajectories plus metadata (both success flags,
  both env step counts, step_ratio) and must return **strict JSON**: first divergence point,
  `root_cause_categories` from a fixed taxonomy — *Missing Critical Fact, Incorrect Summary, Lost
  Variable/State, Unnecessary Re-discovery, Instruction Drift, API Misuse, Premature Completion,
  Token Truncation, Inefficient Looping, Redundant API Calls, Over-Exploration* — plus
  `missing_or_distorted_facts` (quoted baseline line vs the altered/absent compressed line),
  `summary_inaccuracies`, `lost_state_variables`, `inefficiency_patterns` with excess step counts,
  `remediation_recommendations`, and a `reliability_score` 0–1.
- Feedbacks are **concatenated across tasks** (batch "textual gradient"), an LLM rewrites the
  guideline, **K = 5** candidates are sampled, best selected by success rate on a held-out subset of
  `I⁺`. That is the **ᵁᵀ (utility maximization)** step.
- A second **ᶜᴼ (compression maximization)** step looks *only* at `D_succ` (compressed runs that
  succeeded), asks which information was actually used, and rewrites the guideline to prune the
  rest; candidates selected by `success − λ·NormCost`. One ᵁᵀ→ᶜᴼ round is all that is run —
  more rounds hurt (result 6).

**Trained vs prompted — can we use it untrained? Yes.** The guideline optimization is *entirely*
prompt-level: no weight updates, no gradients, agent frozen, works on proprietary API models. That
is the paper's central claim against MEM1/RL-coupled methods (Table 7, §C.3). Only the *optional*
compressor distillation is trained (LoRA r=16, α=32, lr 1e-4, 3 epochs, 100 examples/domain,
1×A100), and it exists purely to make the compressor cheap, not to make it work.

**What the learned guideline actually says** (Appendix D — the copyable deliverable). The optimized
AppWorld *history* guideline fixes five sections: `REASONING`, `VARS` (a name | value | purpose
table of *every runtime value the next session must re-declare* — tokens, ids, lists, pagination
indices), `TODO` (detailed enough to execute directly), `COMPLETED`, `GUARDRAILS` (repeat-error
reminders: "memory resets, re-create VARS before use", "paginate until empty page", "validate API
parameters against spec", "avoid redundant logins or doc look-ups"). The ᶜᴼ pass adds pruning rules
— collapse narrative, drop expired credentials/pagination/verbose API dumps, keep only variables
referenced in upcoming steps, target < 1500 chars — under a *Critical Essentials* clause: "always
keep evidence-driven items required next session (tokens, ids, emails, amounts, lists, paths,
description strings, brief task status)". The optimized *observation* guideline is explicitly
evidence-preserving: "always preserve every endpoint that may be called plus its full parameter list
and defaults; response-schema fields referenced or likely needed later; raw data rows required for
future comparisons or loops; if summarising, keep at least all positive-match examples" and
"never … declare parameters 'not critical' without proof … never replace machine-readable data with
vague prose."

## Relevance to P1–P4

**P1 (context is the cost).** The transferable warning is result 8: a 26–54 % *peak-token* reduction
bought only a 14–18 % end-to-end cost reduction **with caching switched off**, plus 20–39 % more
wall-clock; Appendix A states history compression invalidates the KV cache. Our 63 %-of-spend
cache-read line is billed at 0.1× precisely because those tokens are cached, and rewriting a
session's history is the operation that destroys that discount. The paper measures nothing about
prompt caching, so this is directional only: compress *before* content enters a cached prefix (their
observation compression, which "can mitigate this by reducing the context before caching"), never
mid-session.

**P2 (sessions grow; the longest dominate).** ACON's regime matches ours in shape — threshold-gated
at 4096 tokens of history, hand-off into a *fresh session* carrying a `<HISTORY_SUMMARY>` block.
Measured trade: the long tail shrinks and average accuracy holds, but hard tasks lose (result 2) and
step counts rise 41 %. Transfer gap: our doc-writer at 145k median / 438k peak is an order of
magnitude past their 7–10k peaks, and they never compress a *code* artefact.

**P3 (every session rebuilds the same picture).** The paper's strongest support. Its root-cause
taxonomy names **"Unnecessary Re-discovery"** and **"Redundant API Calls"** as failure classes to be
*designed out* by the guideline, and the learned `GUARDRAILS` section is a per-environment list of
known frictions mined from failure analysis. The case study (§C.2): gpt-4.1-mini fails 10 auth
attempts uncompressed and succeeds compressed, because the summary retained three load-bearing facts
(login needs username *and* password; the returned `access_token` must be passed into each call; the
supervisor app has no proxy APIs) — "compression does not merely shorten history but clarifies
critical dependencies."

**P4 (we don't know what smaller reads cost in grounding).** The paper offers a *method* for exactly
this measurement: run the same task with full and reduced context, keep the pairs where full
succeeds and reduced fails, have a judge produce a structured, quoted diagnosis. Transfer gap: it
needs a binary task reward and ~90–100 paired rollouts per domain. Our nearest rewards (gate-red,
blocking-finding rate, rework share) are noisier and a slice costs far more than an AppWorld task,
so pair collection (≈ $20 there) is the part that does not transfer cheaply.

## Interventions this paper supports

- **Adopt the five-section hand-off shape for any session-cut summary** (`REASONING / VARS / TODO /
  COMPLETED / GUARDRAILS`, VARS being a name|value|purpose table of everything the next session must
  re-declare). Rests on result 1 and Appendix D: that shape is what took AppWorld 43.5 → 51.2 over
  the naive "summarize the history" prompt. Loses: nothing measured at the ᵁᵀ level — ᵁᵀ improved
  accuracy *and* cost on all three benchmarks.
- **Write the observation-compression "never" rules into any tool-output wrapper we build** —
  preserve full parameter lists and defaults, keep raw rows needed for later comparison, keep all
  positive matches, never replace machine-readable data with prose. Closest thing in the paper to
  protecting file:line evidence: the Appendix D example shows naive prompting destroying JSON
  structure and dropping the one API (`play_music`) the task needed, while the optimized guideline
  kept both. Direction: 42.3 → 53.6 accuracy on AppWorld observation compression.
- **Mine our own guardrails from failure transcripts rather than writing them by hand.** Rests on
  results 1 and 5 plus the JSON taxonomy. Cheap version per result 5: pairing is worth only 0.6
  points, so *failed runs alone* recover most of the benefit — we can start from existing red-gate
  and blocking-finding transcripts without paying for matched uncompressed rollouts.
- **Gate any reduction on a size threshold and never touch the most recent turn.** Fig. 6: below the
  sweet-spot threshold accuracy degrades and compressor calls multiply; the last
  (action, observation) pair is kept raw in every configuration.
- **Do one round, and reduce along one axis only.** Result 6: a second optimization round cost 9.5
  accuracy points; combining history + observation compression cost ~11. Bears directly on any
  temptation to shrink dispatch prompts *and* wrap tool output in the same change.
- **A compressor/summarizer role, if we add one, can be a cheap model.** Result 7: >95 % of teacher
  quality from a 14B student, and gpt-4.1-mini worked untrained with a good guideline. This concerns
  the *compressor*, not the writer or reviewer — it does not reopen the settled no-weaker-model rule.

## Applicability caveats

- **Models:** gpt-4.1, gpt-4.1-mini, gpt-5-chat, Qwen3-8B/14B, Phi-4. **No Claude anywhere**;
  Appendix A concedes generalization to Claude/Gemini is unverified. On the strongest model tested
  (gpt-5-chat) ACON no longer matched full context (result 4) — the accuracy-preserving claim is
  weakest exactly where our setting sits.
- **Task type:** tool-call and QA benchmarks with a binary automatic reward. No code editing, no
  diff review, no citation-bearing artefact; nothing measures whether a compressed history preserves
  a `file:line` reference, and the only bearing evidence is qualitative (the JSON/endpoint example).
- **Horizon and scale:** peak contexts of 4–13k tokens over 10–40 steps versus our 80–438k over
  20–200 turns. Their thresholds (4096/1024) are not transferable numbers.
- **Metric mismatch:** "peak tokens" is max single-sequence length excluding system prompts. Our
  cost is dominated by *cumulative cached input*, which peak tokens does not measure — and their
  dollar figure (result 8) explicitly excludes caching.
- **Hard-task regression is under-discussed:** the abstract's "improving task success" is an average;
  AppWorld Hard fell 39.7 → 30.2 (Table 1), gpt-5-chat Hard 47.6 → 33.3 (Table 12).
- **Fact mutation is visible but unmeasured:** in the 8-objective-QA example the same question's
  cached answer reads 1981 (prompting), 1955 (ᵁᵀ) and 1956 (ᵁᵀᶜᴼ). The paper does not comment; it
  cautions that a compressed fact cache can carry altered values forward — exactly the failure mode
  a line citation would suffer.
- **No convergence guarantee** for the natural-language optimization (Appendix A), and the guideline
  is optimized *per environment* — ours would need re-deriving per project, cutting against the
  plugin's portability constraint.

## Briefing check

The note — *"guideline learned from full-succeeds/compressed-fails pairs"* — is **accurate as a
description of the mechanism**: §3.3 defines `D_cont` as tasks "where the agent succeeds with **H**
but fails with **H′**", and Algorithm 1 line 18 makes it exact: `D_cont ← {(H_i, H_i′) | i ∈ I⁺,
r_i = 0}`.

Two corrections. **(1) It overstates the pairing's measured value** — result 5: dropping the
contrastive half and optimizing from failed trajectories alone costs 0.6 accuracy points, less than
swapping the optimizer model (−3.6). The pairs make the diagnosis easier to write; they are not
where the gain lives. **(2) It omits half the method.** The guideline behind the headline AppWorld
number (56.5, matching full context) comes from a *second* step optimized on the opposite
population — `D_succ`, runs where the **compressed** context succeeded — asking which information
was actually used; that step is worth +5.3 points (51.2 → 56.5) plus the length reduction. A summary
naming only the failure pairs would lead us to build the weaker half of the loop.
