## Core results

1. **The problem they measure in the baselines.** Across existing systems that decompose a repo and
   document each component independently: **50 % average overlap in repeated source-file retrieval**
   and **13 % average cross-document inconsistency rate** (Introduction, Fig. 1). MemDocAgent
   "eliminates repeated retrieval" (structurally — a memory hit is O(1) by key) and **reduces
   inconsistency by 75.5 %** (Fig. 1 caption). 20 Python repos. The inconsistency metric is not
   defined in the prose; the related in-loop score is the NLI conflict rate (§8.3).

2. **Documentation quality vs. six baselines.** Qwen3-Coder-30B-A3B: completeness **0.979**,
   truthfulness **0.916**, helpfulness **0.690** — beating the strongest baseline by
   **15.9 % / 9.7 % / 9.9 %**. GPT-5-mini: truthfulness **0.952**, helpfulness **0.800**,
   completeness **0.958** (§6.1). Baselines: Prompting, RepoAgent, DocAgent, CodeWiki, DeepWiki, and
   **Claude Code** (its `/init` `README.md` treated as the repository-level document). Per-level
   results are asserted best-in-class on both backbones; that table is not readable here.

3. **Efficiency — measured in seconds and dollars, never in tokens.** Read time per unit: DocAgent
   **23.44 s** → MemDocAgent **13.76 s**, a **41 % reduction** (§6.4), consistent across all 20
   repos. Generation time per document: **53.16 s vs 60.86 s** (Qwen), **56.72 s vs 69.89 s**
   (GPT-5-mini). **API cost per document on GPT-5-mini: $0.0215 vs DocAgent's $0.0219** — 1.8 %
   lower (§10.4). Documents produced: **3,323** (Qwen), **3,497** (GPT-5-mini) across all three
   levels. *Derived, not stated:* 3,497 × $0.0215 ≈ **$75 for 20 repos ≈ $3.8 and ≈ 175 documents
   per repo**. No token counts, no context-length curve, no cache accounting anywhere.

4. **The verification loop's cost profile.** **63.8 %** of components pass Verify on the first
   attempt at an average score **≈ 0.97**; **24.4 %** need two attempts, **11.3 %** three (§6.5).
   Caps: 10 steps per sub-task, 2 revisions, threshold 0.9. Only **0.08 %** of components terminate
   without meeting the threshold (Limitation). The expensive re-work lands on roughly a third of
   units, targeted by a score, not on everything.

5. **Hierarchical context helps downstream code generation, monotonically.** Information
   sufficiency = regenerate a stripped function body from documentation + signature alone;
   **564 DevEval test cases over 312 functions**. Supplying (C) component doc, (C+M) + parent module
   doc, (C+M+R) + repository doc raises Pass@1/Pass@3/CodeBLEU **monotonically**, C+M+R best in
   *every* setting (§6.2, Fig. 3 — numbers only in the figure). Generated docs can beat the *human*
   ground-truth docstring, which the authors attribute to human docstrings being deliberately terse.
   Generators: Claude Haiku 4.5 and GPT-4o-mini.

6. **Ablation.** Removing *think*, removing the memory system (replaced by "a stateless cache that
   is cleared after each documentation unit"), or removing cross-document conflict verification each
   causes "substantial drops across all metrics" (§6.3). **Effect sizes are table-only — not
   recoverable here.** The stateless-cache arm is the closest analogue to our fresh-session design,
   which makes those missing numbers the most costly gap in this read.

7. **Scalability.** Sorting the 20 repos by file count into halves: all open-source baselines degrade
   on all four metrics (Prompting worst, **−0.086** on "Effectiveness"); MemDocAgent has the smallest
   |Δ| on every metric and slightly *improves* (Completeness **+0.001**, Truthfulness **+0.010**,
   Helpfulness **+0.006**) (§10.2).

## Method and setting (what was actually built/tested)

**Task.** Generate a *whole* hierarchical documentation set for a repository from scratch:
one document per component (function/method/class), per module (directory), and one for the repo —
`|D| = N_c + N_m + 1`, ~175 documents per repo here. **Not** diff-driven updating of existing
human-written docs.

**Horizon.** The authors state a single trajectory "typically spans over a thousand turns."
**Crucially, this is not one context window.** The FINISH action reads: the agent "commits `d_i` to
the corresponding granularity store, and **refreshes its local context for the next sub-task**"
(§4.3, and Fig. 2 caption: "The local context is refreshed before moving to the next sub-task").
Each unit is an independent multi-turn sub-task of **≤ 10 steps** (typical sequence: Read → Write →
Verify → optional Read/Write → Finish). Continuity between sub-tasks is carried **entirely by
RepoMemory, an external store**, not by conversation history. Backbone input caps confirm this:
**32k max input tokens for Qwen, 100k for GPT-5-mini**.

**What RepoMemory carries.** Two stores. *Documentation store*, per record: identifier, path, the
document text, its decomposed atomic claims, verification score, source code, type (function/method/
class) for components, and child units for modules/repo. *External store*: web-search results cached
by query string. Lookup is by key (component id / query) at O(1); a miss falls through to the
dependency graph or the Perplexity API and is then cached. For module and repo sub-tasks the
retrieval tool returns **the already-written child documents instead of the child source code** —
this is the mechanism that removes the redundant reads. **No size figure is given** for RepoMemory
in tokens or bytes, and no statement of how much of it enters any one prompt.

**Ordering.** Dependency-Aware Traversal Guiding precomputes a static order π satisfying two
constraints jointly: components precede their dependents, and a module is processed only after all
its components and sub-modules, with the repo last (Alg. 8.1, SCC-condensed topological DFS). This
is a *deterministic script*, not a model decision — it is what makes "the child doc already exists"
a guarantee rather than a hope.

**Consistency mechanism (the part that does the work).** Verify combines (a) LLM self-evaluation on
consistency/completeness/helpfulness, mean of three, under a harsh rubric (start at 0.50, −0.05 per
minor flaw, −0.10 per major, "never round up"); and (b) **NLI-based cross-document conflict
detection**: the draft is decomposed into atomic claims by an LLM, filtered to those naming a
component/module covered by the reference set, and each is checked by a **local pre-trained NLI
model** (`DeBERTa-v3-large-mnli-fever-anli-ling-wanli`) against dependency-related documents already
committed **and already scoring > 0.9**. Conflict score = fraction of unsupported claims; final =
½(self-eval + (1 − conflict)); pass at ≥ 0.9. Failures return a **named conflict report** ("YOUR
claim: … / DEP states: … / Fix the above conflicts") into the next turn's observation (§4.3, §8.3,
trajectories in §8.5).

**Models / training.** Two prompted backbones — **Qwen3-Coder-30B-A3B** (vLLM, temp 0.1) and
**GPT-5-mini** (temp 1.0), both max 4,096 output tokens, identical scaffolding and prompts.
**Nothing is trained.** Evaluators are deliberately different models: Claude Haiku 4.5 (judge, and
one of two code generators), GPT-4o-mini (claim extraction, code generator). Code at
github.com/bsy99615/MemDocAgent; data = 20 stratified DevEval Python repos.

## Relevance to P1–P4

**P2 (sessions grow; the doc-writer dominates).** The paper's home ground, and it lands on the
*opposite* side of where the note files it. Their answer to a 1000-turn documentation horizon is to
**cut the context at every unit boundary** and make the durable artefact carry the state, with a
precomputed order guaranteeing that artefact exists when needed. They cite the failure mode we would
be betting against (working memory exceeding the window, agents losing prior objectives, propagating
errors — Related Work; Liu et al., "Lost in the Middle") as the *reason* for the design. Gap: they
never ran the alternative on a large-context model, so this is justified by citation and by the
ablation's stateless-cache arm, not by a head-to-head of one-long-context vs. refreshed-context on
the same backbone.

**P3 (every session rebuilds the same picture).** Directly measured, real, but modest in cost terms:
**50 % retrieval overlap** in stateless per-component systems; keying reads through a memory store
cuts **read time 41 %** and per-document generation time ~13 %, but only **1.8 % of API cost per
document**. That asymmetry matters: *the re-reads they eliminated were cheap; writing and verifying
dominate their bill.* Our P1 profile is the reverse (82 % of spend is cache read + write), so their
cost result does not transfer — but their mechanism (a keyed store consulted before the codebase;
the parent reads the child's finished document, never the child's source) does.

**P1 (context is the cost).** No token, cache or context-length accounting exists here at all. The
only cost instruments are $/document and seconds/document — read every efficiency claim as
wall-clock, not context economics.

**P4 (what smaller reads cost in grounding).** The closest thing to an answer: substituting a
*child's finished document* for the child's source did **not** cost grounding —
completeness/truthfulness/helpfulness all rose, and information sufficiency rose monotonically as
more *summary* levels were added (§6.2). But that is measured on documentation-quality metrics, not
code-edit correctness, and the summary was a verified artefact, not a lossy compaction.

## Interventions this paper supports

- **Split the doc phase per surface, in a computed order, with the artefact as the hand-off.** Rests
  on the whole architecture plus the scalability result (§10.2: quality *improves* on larger repos
  where every stateless baseline degrades). Direction: removes the 145k-median / 438k-peak single
  session; cost bounded by the surface, not the diff. Loses, per the paper: *nothing measured* —
  provided the guards below are in place, since removing the memory system alone caused
  "substantial drops."
- **Make the order deterministic and script-computed, deepest first.** Rests on §4.2: the traversal
  is what turns "the dependent doc is already written and verified" into an invariant. For us: a
  Python-computed order over doc surfaces (reference/leaf docs → overview docs → README/architecture),
  not a model decision.
- **Give the parent surface the child's *finished document*, not the child's source.** Rests on §4.3
  READ and §6.2 (monotonic C → C+M → C+M+R). This is the specific read their 41 % read-time reduction
  and 50 %-overlap elimination comes from. Grounding risk per the paper: only if the child doc is
  unverified — hence the > 0.9 filter on the reference set.
- **Add a cheap, non-LLM cross-document consistency gate between doc sessions.** Rests on §8.3: an
  off-the-shelf NLI model over LLM-extracted atomic claims, checked only against *dependency-related,
  already-passing* documents, with claims filtered to those naming a covered entity (explicitly "to
  reduce verification cost"). Expected size: 13 % → ~3 % cross-document inconsistency (75.5 %
  reduction). This is the consistency pass the lead asked about, and their version runs *outside* the
  model. Costs one extra Write+Verify round on ~36 % of units.
- **Return a named conflict report, not a score.** Rests on §8.5, where the fixing revision is driven
  by "YOUR claim: X / DEP states: Y". It is what makes a 2-revision cap sufficient (0.08 %
  non-terminating).
- **Cap the per-unit loop and the revision count.** 10 steps / 2 revisions / threshold 0.9 sufficed
  for 99.92 % of units — supports a hard turn cap on a split doc session rather than an open horizon.
- **Cache external lookups by query string across the whole phase.** Rests on the External store
  (§4.3) plus the prompt's "External Retrieval is extremely expensive" instruction. Maps onto our
  per-session re-learned frictions (a CLI's argument shape).

## Applicability caveats

- **No Claude backbone for the agent**, and no frontier long-context model at all: 32k input cap
  (Qwen), 100k (GPT-5-mini). A paper whose backbones *cannot* hold a repository in context is weak
  evidence about whether Opus-with-no-compaction *should*. Claude appears only as Haiku 4.5
  judge/generator and as a *baseline* (`/init` README) — an unflattering framing of one command's
  output as a whole system.
- **Task mismatch.** Generating a complete doc set from scratch, bottom-up over a static dependency
  graph, is not our task (updating up to 55 existing hand-written docs against a shipped diff). Their
  unit boundaries fall out of the AST; ours fall out of what the diff touched, and a diff can cut
  across many surfaces at once. Their traversal invariant has no obvious analogue for "which doc must
  be written before which" when the driver is a changeset.
- **Not a tool-loop agent.** READ is a structured XML request against a precomputed graph, one action
  per turn, with "only first-level calls are accessible." That is a far narrower and cheaper
  orientation phase than Read/Grep/Bash over a repo — so their read-cost numbers understate what
  orientation costs us, and their hit rate overstates how reliably a keyed store would serve our reads.
- **The decisive tables are missing from this conversion.** The ablation (stateless cache vs.
  RepoMemory) and the main-results table bodies could not be read; per-level and per-repo breakdowns
  are assertions only. For the ablation deltas the lead needs the source PDF or the GitHub repo.
- **Benchmark quirks.** DevEval repos are small-to-medium Python; "information sufficiency" rewards
  verbose documentation by construction (a doc that lets a model re-emit the body scores high), which
  is why generated docs beat human docstrings. Completeness is partly rule-based section matching
  against a schema the authors also wrote the prompts for. Helpfulness is a Haiku LLM-judge.
- **Nothing is trained**, so every mechanism here is portable to our surface as scripts + prompts.

## Briefing check

The note reads: *"argues for one trajectory over the whole repository; the doc-writer's two sides in
one paper."* **The first clause is the paper's rhetoric but not its mechanism, and taking it at face
value would point the lead the wrong way.**

The rhetoric supports the note: "a single agent reasons over the entire repository within one
continuous trajectory, with persistent access to its accumulated retrievals and outputs"
(Introduction). The mechanism does not. On FINISH the agent "commits `d_i` to the corresponding
granularity store, and **refreshes its local context for the next sub-task**" (§4.3); Fig. 2's
caption repeats it; the backbones cap input at 32k/100k tokens. **"One trajectory" here means one
agent identity and one shared external memory across a sequence of context-refreshed sub-tasks — not
one context window, and not evidence for a single long session.**

So on the lead's transfer question the answer inverts the note: this paper is **evidence for the
per-surface split**, conditional on (i) a script computing the order so each surface is written after
the surfaces it depends on, (ii) the hand-off being the *finished, verified* artefact rather than raw
source — exactly "files are the memory," already settled here — and (iii) a consistency pass between
units, targeted at dependency-related documents only, cheap (off-the-shelf NLI over extracted
claims), returning named conflicts. Measured payoff for that combination: 75.5 % less cross-document
inconsistency, 41 % less read time, quality that *rises* rather than falls as the repository grows.

Two qualifications. First, the note's second clause is fair: the paper genuinely holds both sides,
because what it works to preserve across the split — repository-wide accumulated knowledge — is what
a single session gives us for free, and its whole apparatus exists to buy that back. A split without
RepoMemory-and-Verify is the ablated arm the authors report dropping substantially on every metric.
Second, the head-to-head was never run: nothing here compares one long context against refreshed
contexts on the same backbone, and at a 32k/100k input cap it could not have been.
