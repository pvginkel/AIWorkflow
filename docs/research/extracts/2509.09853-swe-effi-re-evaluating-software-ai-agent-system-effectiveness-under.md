## Core results

1. **Four efficiency metrics, all defined as a normalized AUC of resolutions against spend**
   (§3.2). For each metric they plot cumulative resolved tasks against a per-issue resource axis and
   normalize the area to 0–1 (reported as %). The four differ only in axis and cap:
   **EuTB** (total tokens per issue, capped **2 M**), **EuCB** (dollars per issue, capped
   **$1.00**), **EuCTB** (scaffold-local CPU time, capped **30 min**), **EuITB** (normalized
   inference time, capped **30 min**). No closed form is given beyond "AUC, normalized"; the curves
   are Appendix Figures 8–10, unrecoverable here. Read the score as *what fraction of the resolve
   rate you get at an affordable budget*: for efficient systems EuTB ≈ resolve rate
   (Agentless+Qwen3 46.7 vs 48.0; Agentless-mini+GPT-4o-mini 19.6 vs 20.0), for inefficient ones it
   is roughly halved (SWE-agent+GPT-4o-mini **5.1 vs 10.0**; OpenHands+GPT-4o-mini **6.8 vs 11.9**)
   — Table `tab:spec-result`.
2. **A hardware-agnostic latency model** (§3.1.1), fitted on **515,041 raw API call logs**, 90/10
   split, **R² = 0.79**:
   `Normalized Inference Time (s) = 1.457 + 4.266e-5 × InputTokens + 4.999e-3 × OutputTokens`.
   Note the ratio: an output token costs **117×** an input token in latency, while input tokens
   dominate the *count* (result 5). This is why their token ranking and their time ranking disagree.
3. **Token snowball (Observation 3) — qualitative, one instance, no growth rate given.** On task
   `scikit-learn-14496` under three scaffolds, "as the number of calls increases, input token
   consumption grows steadily … this growth is roughly linear per call", caused by "a naïve memory
   accumulation strategy, where each new LLM response is appended to the next input prompt", so that
   "each API call add[s] thousands of tokens even when the agent fails to make meaningful progress"
   (Fig. 4). **No tokens-per-turn slope, no fitted curve, no cross-instance statistics** — one
   showcase figure plus prose. Aggregate per-call input
   *averages* are derivable from Table `tab:metrics` (avg T_IN ÷ avg LLM requests, my arithmetic):
   SWE-agent+GPT-4o-mini **≈ 45.0 k/call** (8,143 k over 181 calls), OpenHands+Llama **≈ 29.1 k**,
   OpenHands+GPT-4o-mini **≈ 21.6 k**, SWE-agent+Qwen3 **≈ 12.4 k**, AutoCodeRover+Qwen3 **≈ 3.8 k**,
   Agentless **≈ 0.3 k** (its calls are short, independent, non-accumulating). Under their own
   linear-accumulation model the *final* call is ≈ 2× the trajectory mean, so SWE-agent+GPT-4o-mini
   ends its trajectories near **90 k input tokens per call**.
4. **Expensive failure (Observation 4) — measured, and the headline case is scaffold-specific.**
   Table `tab:resolv-unresolv-result` splits every metric by unresolved (U) / resolved (R). Total
   tokens, U vs R, with the U/R ratio (ratios mine):
   - SWE-agent + GPT-4o-mini: **8,867 k vs 1,865 k = 4.8×** (time 658.0 s vs 167.2 s = 3.9×;
     requests 192.0 vs 81.6 = 2.4×) — this is the abstract's "over 4 times".
   - AutoCodeRover + GPT-4o-mini: **328 k vs 25 k = 13.1×** (the largest ratio in the table).
   - SWE-agent + Llama **7.9×**; OpenHands + Llama **4.5×**; AutoCodeRover + Llama **3.7×**;
     OpenHands + Qwen3 **2.0×**; AutoCodeRover + Qwen3 **1.8×**; SWE-agent + Qwen3 **1.4×**.
   - **The procedural scaffolds barely show the effect**: Agentless **1.07–1.46×**, Agentless-mini
     **0.76–1.25×** — and in two cells failure is *cheaper* than success (Agentless-mini+GPT-4o-mini
     33.5 k U vs 44 k R; Agentless+GPT-4o-mini total time 998.4 s U vs 1120.7 s R). Their pipelines
     run a fixed number of steps whether or not they are converging.
   The authors' explanation is **"the lack of futility detection"**: "when they're stuck, they enter
   expensive, repetitive loops, consuming massive amounts of compute until an external budget limit
   is reached." Making scaffolds "progress-aware" is named as **future work**, not something they
   built or evaluated.
5. **Input tokens are 90–99.8 % of all tokens in every agentic scaffold** (derived from Table
   `tab:metrics`, avg T_IN vs avg T_OUT — the paper does not compute these shares itself):
   OpenHands+GPT-4o-mini **99.8 %** (737.4 k in / 1.7 k out), SWE-agent+GPT-4o-mini **99.7 %**,
   OpenHands+Llama **99.5 %**, SWE-agent+Llama **98.4 %**, AutoCodeRover+Llama **96.6 %**,
   OpenHands+Qwen3 **95.3 %**, AutoCodeRover+GPT-4o-mini **95.1 %**, SWE-agent+Qwen3 **91.5 %**,
   AutoCodeRover+Qwen3 **73.1 %**. The procedural scaffolds invert: Agentless+Qwen3 is
   **38.6 % input** (26 k in / 41.4 k out) because it generates many candidate patches from short
   prompts. Long tool loops ⇒ input-dominated; short independent generations ⇒ output-dominated.
6. **Turn count, not per-turn intensity, drives cost (Observation 2).** Qwen3-32B (a reasoning
   model, more tokens per call) beat Llama-3.3-70B on every effectiveness score with AutoCodeRover —
   EuTB **37.1 % vs 17.3 %**, EuCB **37.0 % vs 27.4 %** — because it needed **~15 calls vs ~38** and
   **55.5 k vs 416.1 k input tokens**. The authors' stated conclusion: "the primary driver of an AI
   system's total cost is the number of interactions, not the intensity of each one."
7. **Token-efficiency and time-efficiency are a genuine trade-off, and the plane has no single
   winner** (Table `tab:spec-result`, Discussion). Agentless+Qwen3 tops EuTB **46.7 %** and EuCB
   **47.1 %** but only EuITB **29.9 %** / EuCTB **30.3 %** (727.9 s CPU running regression and
   reproduction tests). AutoCodeRover+Qwen3 tops EuITB **33.1 %** and EuCTB **37.9 %** at EuTB
   37.1 %. Scaffold effectiveness is "not an inherent property of its scaffold but emerges from its
   synergy with the base LLM" — the same SWE-agent scaffold scores EuTB 21.8 % on Qwen3 and 5.1 %
   on GPT-4o-mini.

## Method and setting (what was actually built/tested)

- **Task**: SWE-bench-Verified issue resolution — one GitHub issue per trial, patch judged by the
  benchmark's tests. **50 issues**, stratified-sampled from the 500. Not multi-phase feature work:
  no planning artefact, no review round, no docs.
- **Systems**: 5 scaffolds × 3 models = **15 permutations**. AutoCodeRover, Agentless, Agentless-Mini
  are **procedural** (fixed pipeline, LLM called at scripted checkpoints); OpenHands and SWE-agent
  are **agentic** (ReAct-style tool loop). Models: GPT-4o-mini, Llama-3.3-70B-Instruct
  (FP8-quantized), Qwen3-32B. **No Claude model, no frontier model.**
- **Nothing is trained.** Scaffolds run off-the-shelf at default iteration/generation limits with
  added profiling. One deviation: **SWE-agent's termination criterion was set to a strict $1/issue
  API budget**. Parallelism disabled, so CPU time is true sequential time.
- **Horizon**: 2 LLM calls (Agentless-mini) to 181 (SWE-agent+GPT-4o-mini) per issue, most in the
  15–85 range (Table `tab:metrics`). Every trajectory is single-session and single-agent — **no
  scaffold in the study hands off between fresh contexts.**
- **Costing**: openrouter cheapest-provider prices, 2025-07-11 (Appendix 7.1) — **no prompt-cache
  discount is modelled anywhere in the paper.** Subset, code and leaderboard promised public.

## Relevance to P1–P4

**P1 (context is the cost).** Independent confirmation of the shape from a different model family
and different scaffolds: result 5 puts input at **91–99.8 %** of tokens for every agentic tool-loop
system. Our 82 % input-side share sits *below* their agentic range, which is what prompt caching
plus a large output budget would predict. The transfer gap that matters: **their cost model has no
cache**, so their EuCB ranking penalizes a stable repeated prefix at full price while ours pays
0.1×. Their token counts transfer to us; their *dollar* conclusions do not.

**P2 (sessions grow; the longest dominate).** Their Observations 3 and 4 combined, and the paper's
weakest evidence quantitatively. The snowball is asserted from **one instance** with no slope; what
is measured across all 750 trials is the *outcome* — the longest trajectories are overwhelmingly the
failing ones (result 4). Our doc-writer's 192 turns / 438 k peak is inside their worst observed
regime (SWE-agent+GPT-4o-mini, 181 calls, ~90 k final-call input by their linear model). But their
causal story runs the other way: length correlates with failure because the agent is *lost*, not
because length was the plan. Our long sessions are long by design and terminate successfully — the
paper has no case like that, so it cannot say whether our tail is pathological or merely large.

**P3 (every session rebuilds the same picture).** No direct evidence — **every scaffold they test is
a single accumulating trajectory**, so the cost they attribute to memory accumulation is the cost
our fresh-session architecture already avoids, and the re-read cost we pay instead is not a
phenomenon in their setting. The closest transferable finding is result 6: the Qwen3 win comes from
*fewer interactions*, not cheaper ones. Agentless is the existence proof on the other side — ~83
short independent calls at ~0.3 k input each, top EuTB *and* top resolve rate — a system whose
per-call context is deliberately tiny and which still leads the benchmark. That is architecturally
closer to us than any agentic scaffold in the study.

**P4 (unknown grounding cost of smaller reads).** The paper does **not** measure this, and it is
important not to read it as if it did. Its only statement is a conjecture in Observation 3: "as the
context window becomes cluttered with stale information, the LLM **may** lose focus on relevant
cues, reducing reasoning quality and success rate" — hedged, unmeasured, no ablation. There is no
experiment anywhere in SWE-Effi that varies context size and reports resolve rate.

## Interventions this paper supports

- **Put a per-session turn/token ceiling on the tool loop, and treat hitting it as a bail rather
  than a truncation** — rests on result 4 (unresolved attempts cost 1.4–13× a resolution) and the
  authors' futility-detection framing. Expected effect: it caps the tail, it does not shift the
  median. Loss per the paper: **none demonstrated, because they never measured it** — their $1 cap
  on SWE-agent has no uncapped control run. Set the ceiling from our own distribution of *successful*
  session lengths, not from theirs.
- **Instrument the cost of failing phases separately from succeeding ones** — the U/R split is the
  paper's most reusable idea and costs nothing to compute. That the ratio varies 0.76×–13.1× *by
  scaffold* means it is a property of our loop we must measure, not a constant we can borrow. It is
  also the direct instrument for P4's missing quality axis: a rework/re-dispatch is our unresolved
  attempt.
- **Attack turn count before per-turn size** — result 6. In our surface: fewer dispatches, fewer fix
  rounds, fewer orientation reads before the first edit. Their evidence says raising per-call tokens
  to cut call count is net-positive (Qwen3 beat Llama at ~2.5× fewer calls) — consistent with the
  settled "no effort tiering" ruling, and an argument against paying for cheaper turns.
- **Prefer short, independent, non-accumulating calls where the work decomposes** — Agentless's
  ~0.3 k input per call across ~83 calls, best EuTB and resolve rate in the study. Our sub-agent
  contract is the existing version of this and the paper supports widening it. Loss: Agentless pays
  in CPU time (727.9 s, worst EuCTB tier) — decomposition moves cost from tokens to wall-clock and
  to re-verification.
- **Measure the token axis and the time axis separately** — result 7 shows the two rankings invert.
  A single per-slice efficiency score would hide the trade-off we actually face.
- **Do not cite this paper for "cluttered context degrades quality."** That claim is unmeasured here
  (P4); its defensible justification for read-trimming is call count and failure cost only.

## Applicability caveats

- **No Claude, no frontier model.** GPT-4o-mini, Llama-3.3-70B (quantized), Qwen3-32B. The largest
  effects in the paper — the snowball case, the 4.8× and 13.1× failure ratios — all involve
  **GPT-4o-mini**, the weakest model, and the authors' own explanation is capability
  ("high-quality reasoning minimizes iterations"). Extrapolating those ratios to Opus at maximum
  effort is unsupported; the paper predicts they shrink with model quality (Qwen3's are 1.4–2.0×).
- **Task shape.** One issue, one patch, benchmark-graded. No plan, review round, acceptance criteria,
  docs, or multi-agent hand-off — nothing measures a pipeline whose sessions are deliberately
  separated.
- **n = 50 issues**, 15 permutations, one run per cell — no variance, confidence intervals, or
  significance testing anywhere. The authors state the findings "are not intended to be a final,
  definitive verdict".
- **The snowball is one figure on one instance.** Do not quote a growth rate from this paper.
- **No prompt caching in the cost model** (Appendix 7.1) — their EuCB ordering is not our dollar
  ordering.
- **A confound in the headline failure number**: SWE-agent alone ran under a $1/issue budget, and
  the appendix notes its GPT-4o-mini request spike was "due to significantly lower USD-per-tokens
  costs … allowing for more attempts before the cost budget was reached". The 8,867 k-token failure
  is therefore partly an artefact of *how much a cheap model buys under a fixed dollar cap* —
  evidence that a budget cap does not prevent an expensive failure, it only denominates it.
- **Nothing here needs training** — the one clean transfer: every intervention above is
  scaffold-level and available in our surface.

## Briefing check

The note — "the 'token snowball' and 'expensive failure' patterns for SE agents" — accurately
describes what the paper contains, but the two halves are not equally evidenced and should not be
treated as one finding.

**Expensive failure is measured and is the paper's real contribution**: Table
`tab:resolv-unresolv-result` gives a U/R split for every metric in all 15 cells; "a failed attempt
consumes over 8.8 million tokens and 658 seconds, while a successful one requires just 1.8 million
tokens and 167.2 seconds. That's more than a 4x increase". The note should carry the caveat that the
effect is **scaffold-shaped, not universal** — the procedural scaffolds run 0.76–1.46×, i.e. failure
costs about what success costs, because their step count is fixed. That is the finding with the most
bearing on us, and it points the opposite way from a naive reading: a pipeline with a fixed phase
structure is the architecture that *doesn't* fail expensively; the exposure is in the unbounded
loops inside it.

**Token snowball is asserted, not quantified.** Observation 3 rests on a single showcase instance
(`scikit-learn-14496`) and contains no slope, no per-turn growth number, and no aggregate statistic;
its second clause — that a cluttered context degrades reasoning quality — is explicitly hedged
("may") and never tested. A briefing line that implies this paper *measured* how tokens per turn
grow with trajectory length would overstate it.

**On the transfer question the answer is no, with one useful negative.** SWE-Effi gives **no basis
for choosing a turn or token budget as an early stop**: it never varies a budget and measures the
resulting resolve rate. Budget management and futility detection appear only as recommended future
work ("stopping the task if the token snowball grows to an unacceptable level"), and the EuTB/EuCB
curves that would show where marginal resolutions stop arriving are Appendix figures with no numbers
in the text. **The paper says nothing about what happens to quality when trajectories are cut.** The
useful negative is the SWE-agent confound above: they *did* impose a hard $1/issue budget, and that
system still produced the study's most expensive failures — a spend cap bounds the loss but does not
detect futility, so a budget-as-early-stop in our loop should be justified as tail insurance, not as
an efficiency mechanism.
