# Qlty in the workflow — proposal (2026-10-02)

**Status: proposal, nothing built.** The operator asked for Qlty in two places — after `kc project
lint`, and as a dedicated refactoring sweep — as the resuscitation of the archived
`code_health` grader (`archive/quality/`), with the open question whether the grader is replaced
wholesale or rebuilt on qlty. § 1 answers it; § 2 holds the facts about qlty the answer rests on,
verified against the 0.651.0 source and by running it on this repo; § 3 says what of the archive
is worth keeping; § 4 and § 5 are the two builds; § 6 puts the refactoring sweep beside the
operator's other scheduled jobs; § 7 the risks; § 8 the decisions to rule and the build order.

## 1. The answer in short

1. **Qlty replaces every analyzer of `code_health` wholesale** — the Python AST rules, radon,
   the TypeScript analyzer and the `tsx` cognitive-complexity sidecar. None of them survives. It
   measures the same things (cognitive complexity per function and per file, parameters,
   nesting, size) in sixteen languages from one Rust binary, in under a second for 15k lines,
   and adds the one thing the grader never had: duplication.
2. **What survives of "my tool" is the ranking, not the measuring** — about 150 lines reading
   qlty's JSON: the excess-over-threshold score, the fixed 1–10 rating breakpoints, the top-N
   list. That is claude.ai's "use qlty as the implementation", narrowed to the part that was
   ever the tool's own. The project-level knowledge the grader carried in `config.py`,
   `.codehealthignore` and `health: ignore` comments moves into each project's `.qlty/qlty.toml`.
3. **The operator's hunch for the run loop is right in spirit and wrong in one fact.** "Limit
   the run-slice logic to qlty's built-in `--upstream`" — but qlty's own `--upstream` cannot do
   the job: `qlty check --upstream` runs *linters* (ruff, eslint), line-filtered, and never the
   maintainability smells; `qlty smells --upstream` runs the smells but is **file-level** (a
   one-line edit to a 1,500-line legacy file reports every smell in it) and **always exits 0**.
   So the loop needs a small **delta tool** — new-or-worsened smells of HEAD against a base, exit
   code per a bar — not qlty alone. It is ~150 lines, stdlib, and still no ranking logic in the
   run loop.
4. **The run loop itself changes nowhere.** The delta tool is a second statement of a project's
   `lint:` in `.kubecoder/project.yaml`, so it runs wherever lint runs today — the writer's own
   run, the loop-tail sweep, the doc gate, the wrap-up gate — and the per-phase gate stays test-only
   (settled). It starts **advisory** (always exit 0, output logged), is read after ~10 slices,
   and is then made red for *new* smells — the project's thresholds being the bar.
5. **The sweep is a skill in the `dev` plugin, `/dev:refactor-sweep`**, pointed at the project
   whose environment it runs in: `qlty metrics` + `qlty smells` over the whole tree → the ranker →
   one Opus audit agent (the archived `refactor-audit`'s procedure, kept) → an audit document in
   the spec repo and one intake card naming it. The next step already exists: `/dev:triage
   <audit>` takes a findings document. Scheduled later as a per-project `kc timer` whose prompt is
   one line.

## 2. What Qlty is — the facts that shape the design

Verified against the source at `66524db` (0.651.0, released 2026-10-01) and by running the
binary; marked where inferred. Releases are roughly daily.

**The binary.** One Rust executable. `curl https://qlty.sh | sh` installs to `~/.qlty/bin/qlty`;
`QLTY_INSTALL_BIN_PATH` redirects it (to `/usr/local/bin` in a toolchain image) and
`QLTY_VERSION=x.y.z` pins it; the installer needs `xz` and `curl`. No cloud account is needed for
anything in this proposal (`auth` and `coverage publish` are the cloud commands). Telemetry is on
by default; `QLTY_TELEMETRY=off` turns it off. **Licence:** Business Source License 1.1 — any use
except offering a code-quality or AI-coding service to third parties; GPLv3 from 2028-12-10. An
internal pipeline is inside the grant.

**Where it writes.** `~/.qlty/cache/tools/` holds the linter runtimes it downloads on first use
(its own Node from nodejs.org, its own CPython from python-build-standalone, then `pip`/`npm` for
the plugin). The smells and metrics need **none of that** — tree-sitter is in the binary — so
the design below downloads nothing. Per-repo state goes to `~/.qlty/cache/repos/<hash>/`,
symlinked from `.qlty/{logs,out,results,plugin_cachedir}`; `qlty init` writes a `.qlty/.gitignore`
that commits only `qlty.toml`, `configs/` and `hooks/`.

**Three commands, deliberately separate.**

| command | what it runs | `--upstream <ref>` | exit code |
|---|---|---|---|
| `qlty check` | the wrapped linters (`[[plugin]]`) — **not** the smells | changed files, then **only issues on added lines** (verified: an F401 on `main` was not reported, the branch's was) | 1 on issues at or above `--fail-level` (default `fmt`), 2 config error, 3 a linter crashed; `--no-fail` |
| `qlty smells` | the eight structural smells, incl. duplication | **changed files, every smell in them** — no line filter (verified: a pre-existing function in a touched file was reported) | **always 0**; no `--level`, no `--fail-level` |
| `qlty metrics` | per file (`--functions`: per function): classes, functions, fields, lines, `codeLines`, `complexity` (cognitive), `cyclomatic`, `lcom4` | file-level | always 0 |

Both `smells` and `metrics` take `--all`, paths, `--json` (hidden flag, works) and `--sarif`;
`smells` excludes tests by default (`--include-tests`), `metrics` includes them
(`--exclude-tests`). Keep stderr apart when parsing (`2>/dev/null`): progress text otherwise
breaks the JSON. Without `--upstream` the base is inferred as `refs/remotes/origin/HEAD`, else a
local `main`/`master`/`develop`, else HEAD (issue #2739: the branch's own tracking ref is
ignored). `check` needs a git repo; `init` needs the git root.

**The smells and their defaults** (`qlty-config/default.toml`; a check fires at `count >=
threshold`; every smell is `LEVEL_MEDIUM`, category `STRUCTURE`):

| smell | threshold | measures |
|---|---|---|
| `function_complexity` | 18 | cognitive complexity of a function |
| `file_complexity` | 50 | cognitive complexity summed over the file (the docs say "lines of code"; the code says complexity) |
| `function_parameters` | 6 | |
| `nested_control_flow` | 5 | |
| `return_statements` | 6 | |
| `boolean_logic` | 4 | operators in one condition (did not fire on `a and b or c and d or e` — how it counts is unverified) |
| `identical_code` / `similar_code` | 15 | duplication, syntactic / structural, with `[smells.duplication] nodes_threshold = 64` |

Per-language override: `[language.python.smells.function_parameters] threshold = 9` — **verified
here**: this repo's 29 `function-parameters` smells fell to 10. Languages: c, cpp, c-sharp,
elixir, go, java, javascript, kotlin, php, python, ruby, rust, scala, swift, typescript (`.ts`,
`.mts`, `.cts`; TSX separately), vb-dotnet — every language in the fleet's onboarded repos.

**Suppression is the weak spot.** `[[ignore]] file_patterns/rules` — **verified not to apply to
smells** in 0.651.0 (two `function-complexity` smells in an ignored file were still reported);
`// qlty-ignore` comments do not either (#2430); `[[triage]]` and `[[exclude]]` do not affect
duplication (#2902). What works: thresholds per language, and `exclude_patterns`, which removes
a file from everything. § 4.6 and § 7 say what to do about it.

**Defaults that hide code.** `qlty init` writes `exclude_patterns` that drop `**/config/**`,
`**/db/**`, `**/templates/**`, `**/generated/**`, `**/assets/**`, `**/fixtures/**`, `**/build/**`,
`**/dist/**`, `**/vendor/**` and more, plus `test_patterns` (`**/test/**`, `**/test_*.*`,
`**/*.test.*`, …). A repo with a `config/` package loses it silently; onboarding has to read the
list (§ 4.7).

**JSON shape** (`smells --json`, verified): a flat array of issues with `tool`, `driver`
(`structure`), `ruleKey`, `message`, `level`, `category`, `language`, `location{path,
range{startLine, endLine, …}}`, `value` (the measured count), `properties{actual, threshold}`,
`partialFingerprints{"function.name": …}`, `effortMinutes`, `snippet`. No stable `fingerprint`
field; `(path, ruleKey, function.name)` is the join key a delta can use. `check --json` adds
`onAddedLine`.

**On this repo** (`plugins/dev/tools`, 10 files, 14.8k lines, tests excluded by default): metrics
and smells each ran in 0.8 s. 87 smells — `function-complexity` 36, `function-parameters` 29,
`file-complexity` 8, `nested-control-flow` 6, `return-statements` 5, `boolean-logic` 3.
`run_loop.py`: 290 functions, cognitive complexity 1,479, 43 smells. The worst functions:
`turn_profile.replay` at 109 (threshold 18), `classify_turns` 54, `_wrap_up_run` 39,
`_wrap_up_clean_slate` 37, `_dispatch_rounds` 36, `slice_cost.scan_transcript` 35. The operator
will recognise the list; that it is right is the point.

## 3. The archive, and what of it is worth keeping

`archive/quality/aiworkflow/code_health/` (1.8k lines incl. the TypeScript sidecar) and the three
command docs; `archive/quality/README.md` records that four projects' copies had drifted and that
`refactor-audit` was the grader's only consumer — `quality-issue-finder` and `quality-improver`
never read it.

| the archive had | fate |
|---|---|
| `python_analyzer.py` (AST: SLOC, params, nesting, class methods, inline imports) + radon | **replaced** by `qlty smells` + `qlty metrics` |
| `ts_analyzer.py` + `cognitive/` (`tsx` sidecar; KubeCoder's variant used `complexipy`) | **replaced** — cognitive complexity is qlty's native measure, every language |
| `config.py` thresholds and weights; `PYTHON_PARAMETER_COUNT_OVERRIDES` (`__init__`: 10) | thresholds → the project's `.qlty/qlty.toml`, per language. Weights → the ranker's own, one table for every project (as the close-out's routing table is). The `__init__` exception → the one override the ranker carries, keyed on `partialFingerprints.function.name`, because qlty has no per-function threshold and DI constructors were the archive's documented false positive |
| `inline_imports` rule | **dropped** from health; it is a lint rule (ruff `PLC0415`) for a project that wants it |
| `class_method_count` rule | **dropped**; `metrics` gives `functions`, `classes` and `lcom4` per file, and `file_complexity` is the better file-level signal |
| `models.py`: score = Σ (excess over threshold × weight); `score_to_rating` with breakpoints `[2, 5, 10, 15, 25, 35, 50, 75, 110]` | **kept** — this is the ranking, and the breakpoints were fixed on purpose so ratings compare across runs |
| `formatting.py`: top-N table, findings-by-rule summary, `--json` | **kept**, trimmed (no pager, no colour: an agent reads it) |
| `.codehealthignore`, `.gitignore` loading | → qlty's `exclude_patterns` |
| `health: ignore <rule> — <reason>` first-10-lines comments | no qlty equivalent that works on smells today (§ 2); § 4.6 |
| `refactor-audit.md` (run the grader, spot-check the top files, group into themes, rank by impact/risk/effort/coupling, write a dated audit, propose threshold changes) | **kept** as the audit agent's procedure — the prose is good and the archive README says to read it before rebuilding |
| `quality-issue-finder` / `quality-improver` (duplicated patterns and reinvented utilities, by LLM) | **stays archived**. Syntactic duplication is now `identical_code`/`similar_code`; the semantic "this reimplements `slugify`" lens is a reading the audit agent can be asked for in a later version, not a tool |

What was the grader's real value was never the measurement — it was the *ranked list a reader
could start from* and the audit on top. Both are kept; what is replaced is what qlty does better
and in every language at once.

## 4. Place 1 — the lint-time delta

### 4.1 Why not qlty alone

Three facts from § 2: `check` has no smells; `smells --upstream` is file-level; `smells` cannot
fail. A bare `qlty smells --upstream` after `kc project lint` would print pre-existing smells in
every file a phase touched, to an exit code of 0 — the writer, told to fix every lint violation,
would start refactoring legacy files (the per-phase tax the test-only gate was ruled to avoid),
and the loop-tail sweep would never go red. The thing the operator wants — *this slice made
nothing worse* — is a delta, and qlty does not compute one.

### 4.2 The delta tool — `qlty-delta`

Stdlib Python, ~150 lines plus a suite. What it does:

1. Resolve the base (§ 4.3), take the changed files between the merge-base and the working tree.
2. `qlty smells --json --no-snippets <changed files>` at HEAD; the same command for the same
   paths at the base, in a temporary `git worktree` (qlty needs a git checkout; the worktree is
   removed after). Both sides run the same binary, so a qlty upgrade cannot fake a delta.
3. Join on `(path, ruleKey, partialFingerprints.function.name)`; classify each HEAD smell as
   **new** (absent at base), **worsened** (`value` rose), **unchanged**, and list the base's
   smells gone from HEAD as **fixed**.
4. Print a short table (new and worsened first, with `actual`/`threshold` and line), then one
   JSON summary line so a readout script can read it from the sweep logs.
5. Exit per `--fail-on {new,worsened,none}` — 1 when a smell of that class exists, 0 otherwise.
   Default `none` to start (§ 4.5).

Duplication smells are included in the counts and the table but never in the exit code: their
join is the pair of locations, which moves with every edit, and their suppression is broken
upstream (#2902). Run from the component's cwd it finds the git root itself (qlty resolves paths
against the cwd when run from a subdirectory, #2878) and scopes the changed-file set to that cwd.

### 4.3 The base ref

A `lint:` statement cannot be told the slice's base by the driver, so the rule is the tool's and
is simple: **on a branch, the merge-base with the local default branch; on the default branch,
`origin/<default>`.** Checked against where lint runs:

| where | branch | base | the delta is |
|---|---|---|---|
| the writer's own lint run | `phase/P<n>` off the local base | local `main` (holds the slice's earlier phases) | this phase's |
| the loop-tail sweep | local `main`, phases merged, nothing pushed yet (the test phase pushes) | `origin/main` | the slice's |
| the doc gate | `main` after the test phase pushed | `origin/main` | empty — green |
| the wrap-up gate | the wrap-up branch off `main` | local `main` | the wrap-up's own fixes |

`--base <ref>` overrides it. The one case the rule misreads: a project with `push.enabled =
false`, whose local `main` leaves `origin/main` behind for good — the slice's delta then
accumulates every unpushed slice's. Say so in the contract; such a project runs the tool at
`--fail-on none` or passes `--base`.

### 4.4 Where it runs — and why the loop changes nowhere

```yaml
# .kubecoder/project.yaml of a project that adopts it
projects:
  backend:
    lint:
      - cexec python ruff check .
      - cexec python qlty-delta
```

`kc project lint` runs every statement and exits non-zero if any failed, so the second statement
rides the first: the writer runs it once itself before handing back (`agents/code-writer.md`
item 7), the driver runs it in the loop-tail sweep per component (its log beside ruff's in
`<slice>/sweeps/r<N>/<repo>_<component>_lint.log`), the doc gate and the wrap-up gate run it
again. A red at loop tail is the existing path — the completion consult appends one fixing
phase for the slice — and an `accept` ruling for `lint` covers it like any other lint red. This
is the same argument `residual-sweep.md` makes for the generated slice: the plugin's contract
is "the manifest declares the curated automation", and a project that adds a statement to its
lint has changed nothing the driver reads. No `SWEEP_VERBS` change, no driver knowledge of qlty,
nothing to port when a project does not want it.

The alternative — the driver running qlty itself as a fourth sweep row — was weighed and is
not proposed: it would make the driver know one tool and one tool container by name, against
the portability rule, for no behaviour the manifest route lacks.

### 4.5 Advisory first, then red for new smells

Thresholds are judgment, and a fix round over a function that crossed 18 by one point is the
bickering the operator ruled out for comments (0.4.2). So the bar is set from evidence:

- **Phase A — advisory.** `--fail-on none`. The table reaches the writer in its own lint run,
  the sweep log holds it per slice. The writer's instruction (one sentence added to
  `code-writer.md` item 7): *a smell the lint reports as new or worsened on code you wrote in
  this phase is yours to fix before handing back; a pre-existing smell in a file you touched is
  not.* That is the writer in context, where a fix is one turn — not a review round.
- **Readout after ~10 slices** on two projects (`t4_readout.py`'s shape, reading the sweep
  logs): how many slices had a new smell at loop tail, how many the writer had already fixed by
  then, what the thresholds would have cost in fixing phases, which rules fire on code the
  operator would not refactor.
- **Phase B — red on `new`.** Thresholds adjusted from the readout, `--fail-on new` in the
  manifest. `worsened` stays advisory: a function already over the bar that a slice had to touch
  is debt the sweep (§ 5) ranks, not a slice's to pay mid-run.

### 4.6 Suppression, until qlty's works

Thresholds per language in `qlty.toml` and `exclude_patterns` are what qlty honours for smells
today. For the per-file, per-rule case the grader's `health: ignore` served (a state machine with
justified branching), the proposal is: **the project writes qlty's own `[[ignore]]` blocks, and
`qlty-delta` and the ranker apply them to the smells JSON themselves** — `file_patterns` and
`rules` as qlty defines them. One config, in qlty's vocabulary; when qlty applies `[[ignore]]`
to smells the filter becomes a no-op and is deleted. Inline `qlty-ignore` comments are not
emulated: a comment the tool honours and qlty does not is a drift trap.

### 4.7 Per project: onboarding

`/dev:onboard` gains a step after the manifest's automation (its § 3): `qlty init --skip-plugins
-n` at the repo root, then **read the generated `exclude_patterns` against the tree** and remove
the ones that hide application code (`config/`, `templates/`, `db/` are ordinary package names),
set the per-language thresholds (§ 7 proposes a starting set), commit `.qlty/qlty.toml`, add the
`lint:` statement per component. `qlty check`'s linter plugins are **not** enabled: the project's
lint stays the project's. A component that has no lint at all (Architecture's `viewer` and
`service`) may adopt `qlty check` with eslint/tsc as its lint — a manifest decision for that
project, not plugin policy, and not in this proposal.

### 4.8 The toolchain

qlty is in no sidecar today. The catalog images are `pvginkel/DockerImages`'s
`kube-coder-<name>-toolchain/Dockerfile`; `python` installs ruff and uv into `/usr/local` with the
note that `~/.local` is a read-only mount in a sidecar and `~/.cache` a writable overlay. The
change, in the `python`, `frontend`, `modern-app` and `go` images:

```dockerfile
ARG QLTY_VERSION=0.651.0
RUN curl -sSf https://qlty.sh | QLTY_VERSION=$QLTY_VERSION QLTY_INSTALL_BIN_PATH=/usr/local/bin sh
ENV QLTY_TELEMETRY=off
```

plus `qlty-delta` itself into `/usr/local/bin`, fetched from AIWorkflow at a pinned commit — the
source of record stays here (`tools/qlty/qlty_delta.py` with its suite, run by `kc project
test`; stdlib because the sidecar's Python is the base image's 3.13), the image carries a copy
the way it carries ruff. Pinned, because qlty releases daily and the embedded plugin definitions
and smell counts move with it; `qlty upgrade` is never run in a sidecar.

Open: whether `~/.qlty/cache` is writable in a sidecar. The home overlays a toolchain declares
are listed in `kc catalog` (`frontend` declares `.npm`, `.pnpm`, …; `python` declares none), so
`.qlty` likely needs declaring as one, or qlty needs pointing elsewhere — the spike (§ 8, B0)
answers it by running the binary from `/work/scratch` under `cexec python` before any image
changes.

### 4.9 Cost

Mechanical: ≈ 2 s per lint run (two qlty invocations on the changed files). Model: in phase A,
whatever the writer spends fixing a new smell in context — one or two turns, inside a session
already open — and nothing elsewhere; in phase B, a fixing phase at loop tail for a slice that
hands back new smells, which the writer's own run should make rare. No reviewer involvement, no
new session.

## 5. Place 2 — the refactoring sweep

### 5.1 The ranker — `code_health.py`, rebuilt

`plugins/dev/tools/code_health.py`, stdlib, with `test_code_health.py` beside it. Input: `qlty
metrics --all --json` and `qlty smells --all --json --no-snippets` over the repo (the skill runs
both through the project's tool container and feeds the files in — the ranker never calls qlty,
so its suite needs no binary). Output: the archive's report — per file a score, a 1–10 rating,
its findings sorted by points; the top N; findings by rule — as a table and as `--json`.

The score keeps the archive's form, Σ (`actual − threshold`) × weight over the file's smells,
with a weight table of the tool's own: `function_complexity` the heaviest (it was 0.8 against
0.5 for parameters in the archive and is the signal the operator trusted), `file_complexity` for
size, `function_parameters` with the `__init__` exception, the rest light, duplication counted
once per file. Thresholds are the project's (`qlty.toml`, so the ranker and the delta agree on
what a smell is); weights are not a project's to tune — one policy, like the close-out table.
The breakpoints are the archive's, unchanged, so a 5/10 means in October what it meant in July.

### 5.2 The audit agent — `refactor-auditor`

`plugins/dev/agents/refactor-auditor.md`, Opus at `xhigh` (a new main role; the ruling against
weaker models for main roles applies). Its procedure is the archived `refactor-audit.md`,
phases 2–5, with these changes:

- It starts from the ranker's JSON, not from running anything; the dispatch hands it the file.
- **Phase 2's spot-check is the job** — is the score justified, what is the disease behind the
  symptom, what would the refactoring look like — and reading 20 files is its Explore
  sub-agents' work, as the archive says.
- Phase 3's groups get a **stable id** (a slug from the file set) so later audits can say
  "proposed 2026-11-01, filed as slice 240" or "proposed twice, not taken".
- Phase 3b's false positives become **proposed config edits** — a threshold, an
  `exclude_patterns` line, an `[[ignore]]` block — listed, not applied. Config is the operator's.
- Phase 5 writes to the spec repo, not the code repo: `<spec-repo>/quality-audits/<date>.md`
  with the JSON beside it, committed by name. The report's shape is the archive's (summary,
  groups in priority order, false positives, execution order, thresholds review), one addition:
  a **since-last-time** section — the previous audit's groups and their fate, read from
  `slices/*/slice.md` (a filed group's slice quotes the audit) and from the previous audit.
- It writes **no cards per group** and files nothing: an audit is a findings document, and
  `/dev:triage` is where the operator rules on findings.

### 5.3 The skill — `/dev:refactor-sweep`

`plugins/dev/skills/refactor-sweep/SKILL.md`. Runs in the project's environment, at the repo
root; optional argument: component names, to scope. Steps:

1. Preflight (`preflight.py --for triage` — it needs the spec repo and the manifest, nothing of
   the run profile).
2. `kc project list` for the components and their tool containers; run `qlty metrics` and
   `qlty smells` through them (`cexec <tool> qlty …`) into a scratch dir; the ranker over the
   result; `--top 25` (the archive's 20 plus room for grouping).
3. Dispatch `refactor-auditor` with the ranker's JSON, the previous audit's path, and the
   output paths.
4. Verify the audit exists, parses, is committed in the spec repo; file **one** intake card —
   "Refactoring audit <date>: N groups" with the audit's path — via the host's tracker
   convention, so the next `/dev:triage` sitting finds it.
5. One notification; the final reply is the report's summary.

The operator then runs `/dev:triage <spec-repo>/quality-audits/<date>.md`: every group on a
line under its proposed fate, the operator's words into `slice.md`, one slice per group taken
— the plan route, always: a refactoring group is design by definition, never the residual
sweep's Solution Known lane (`residual-sweep.md` excludes anything with an open choice).

### 5.4 Scheduled

A timer belongs to a project and runs as a fresh headless session in one of its environments
(starting a stopped one and stopping it after), capped at `runTimeoutMinutes` — 240 on prd —
with no env vars and no memory of earlier runs. The prompt is the skill: *"In /work/<Repo>:
`git fetch && git pull --ff-only` if clean and behind; then run `/dev:refactor-sweep`."* Monthly,
per project, `kc timer create --title "Refactoring sweep" --cron "0 4 1 * *" --prompt-file -`;
a `timers/refactor-sweep.md` record in the project, as Automation keeps one per timer. Nothing in
the sweep ends its turn to wait: the qlty runs are seconds, the audit agent is a sub-agent the
skill waits on, and a run is well inside the cap. A scheduled run produces exactly what a manual
one does — an audit and a card — and nothing moves until the operator triages; a run that
succeeds is silent except for its notification.

Cost: the mechanical part is seconds; the audit agent reads 20–25 files plus Explore fan-out —
about a plan-writer session, to be measured on the first run and put in the readout.

### 5.5 Where it lives

In `dev`, not a second `upkeep` plugin. `plugin-plan.md` § 7a parked the quality capability for
an `upkeep` plugin that was never built; a second marketplace entry is a second install and
update step in every environment, for one skill, one agent and one tool that use the same
preflight, spec repo and tracker convention as the rest. If codebase maintenance grows a second
capability (KubeCoder's `update-docs` is the candidate), the split can be reopened then.

| Refactoring sweep | `dev` plugin (this proposal) | per-project timer, the skill as the prompt | proposed | § 8 |
| Architecture update | `pvginkel/Architecture`: `architecture-update` skill over `tooling/fleet.py update` | operator-invoked; drives producer repos through `kc session create-headless` from clones under `/tmp` | built, not scheduled | a full-fleet run is "30 minutes to hours" under a 12-hour backstop, against the 240-minute timer cap; and the skill backgrounds the tool and ends its turn to be re-invoked — in a timer-run session (no `CLAUDE_AUTO_BACKGROUND_TASKS`) that hand-back is not guaranteed. Unverified in a timer; the detached run loop (0.9.69: detach, check back on a cadence inside the turn) is the shape that would fit. `JENKINS_TOKEN` is in every environment per `kc catalog`, so that is not a blocker |
| Software updates | nowhere yet | — | an idea | note that `project.yaml` already reserves `autopatch: cycle: 2w` — parsed, nothing acts on it — so the manifest hook for a per-project update cadence exists |

Two shapes are in use: **fleet-level**, one timer in Automation fanning out to environments
(the card pass, and what the architecture update does by hand), and **per-project**, a timer of
the project running its own skill in its own environment. The refactoring sweep is per-project
by nature — it needs the project's tool container and spec repo and does nothing across
projects — so the per-project timer is the proposal: zero orchestration code, the skill is the
prompt. The price is N timer records to keep (there is no update verb: a change is delete and
create), which is also the argument for consolidating the schedules into one Automation fan-out
when the fourth job arrives: one place that knows the calendar, N environments doing the work,
the card pass's `start_environment(wait="settled")` + `start_headless_session` + `get_session_response(wait_ms=…)`
pattern already written. Not now.

Two lessons from the two jobs that exist, for any of the four: a timer session has **one
turn and 240 minutes**, so anything longer is detached and checked on, never backgrounded and
waited for by ending the turn; and a run reports **once**, by notification, with the artefact
(a card, an audit, a report in the spec repo) as the durable record — "a run that succeeds
tells you nothing by itself".

## 7. Risks and open questions

1. **`~/.qlty` in a sidecar.** Unknown whether qlty can write its per-repo state there (§ 4.8).
   The spike answers it; the fallbacks are a declared home overlay or an env var, if qlty has
   one (`QLTY_HOME` was not found in the research — to check in the source).
2. **Suppression** (§ 2, § 4.6): tool-side `[[ignore]]` until upstream; duplication smells never
   gate. If `[[ignore]]` also fails for the ranker's purposes in practice, `exclude_patterns`
   is the coarse fallback.
3. **Default `exclude_patterns`** hiding `config/`, `templates/`, `db/`, `generated/`: an
   onboarding read, every project, and a line in the contract.
4. **Thresholds.** qlty's defaults are higher than the archive's (18 vs 15 cognitive, 6 vs 5
   parameters, 5 vs 4 nesting). Starting set for the spike: the defaults, with Python
   `function_parameters` at 8 (the `__init__` exception covers the rest) — then the readout.
5. **Version churn.** Pinned in the image; the delta compares both sides with one binary, so an
   upgrade cannot fake a delta, but it can shift an audit's trend between months — the audit
   states the qlty version in its header.
6. **Subdirectory runs** (#2878): `kc project` statements run in the component's cwd; the delta
   tool and the skill resolve the git root and scope by path. Monorepo behaviour otherwise
   untested — the spike runs on Architecture (`tooling/`, `viewer/`, `service/`).
7. **`boolean_logic`'s counting** is unverified (did not fire on a five-term condition);
   immaterial to the delta, worth a look for the ranker's weight.
8. **Licence**: BSL 1.1's grant covers internal pipelines; the plugin is not offered to third
   parties as a service. Noted, not a blocker.
9. **The writer's instruction** is one sentence on a bar it reads from the tool's output; whether
   it tells "new on my code" from "pre-existing in a file I touched" is what the table's
   classification is for — the readout checks that it did.
